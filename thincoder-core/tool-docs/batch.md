Batch-record lifecycle tool: a record has six sections, one author each. The author has two actions on that one section — `append` adds text at its end, `edit` rewrites its lines in place — and the section's status line has a single writer, `status`.

Writing a record is never silent: every write runs the document-check gate first and can be refused. A pre-write refusal leaves the file byte-for-byte unchanged (`Nothing was written.`); a later failure rolls the record back, or names the rollback failure and points at `check`.

- create (depth-0 only): write a new six-section skeleton record — `path` (where it lands), `topic` (the subject the header and the file name share), `source` (REQUIRED: the record's origin line), plus optional `ledger` / `board` that fill the record's `台账` header line at creation, and `date` / `prev` for the record date and its predecessor pointer.
  - `ledger:"#N"` takes over an existing row. Omitting it opens a new row — but only when no unsettled row exists on the same board; otherwise create is refused with the candidate list, and you pass `newDebt:"<why this is a new debt>"` or `ledger:"#<id>"`.
  - Omit both and a **reserved** row for this very path is claimed instead: register the intent first with `ledger add` (`task_book` = `docs/batches/<x>.md（预定）`, marker at the value's tail), and creating that path later takes that same row over — no second row, and the pointer is rewritten to the plain form. Two reserved rows for one path are refused and named one by one.
- attach (depth-0 only): hang a ledger row on an ALREADY EXISTING in-flight record — a reopened record taking on a new piece of work, where create cannot go (the file exists) and a settled row has no way back.
  - `title` is required and opens a new row (the row's own subject, never the batch's original one); or take over an unsettled one with `ledger:"#<id>"`. The real number lands at the end of the header `台账` list; the parenthesis group (board · trigger) stays where it is and is not rewritten — a parenthesis that must change is a plain document write.
  - Its ledger parameters are create's own, with the same meaning and the same same-face rule: `ledger` / `newDebt` / `board`. Replaying the same attach is zero-write once the number is in that list, and a settled row is never reopened here.
  - attach skips the dead-placeholder gate on purpose: a record whose header still carries `#<编号>` is already real on the ledger side, and attach is how that placeholder becomes a real number.
  - Refused with nothing written: the record is frozen (§1 `已收口` — reopen first, or start a new batch), its §1 status line is unreadable, the header has no `台账` line, a new row without `title`, or a face that already has unsettled rows with no `newDebt` reason.
- append: add `text` to the END of YOUR section — the lines already there are left byte-for-byte as they stand. A line that starts with the status-line form (`**状态行**：…`) is refused: that line has exactly one writer (`status`), and the tool channel may only make such lines fewer, never more. Quote it with a leading `> ` instead, or write it as prose.
- edit: replace one anchored range inside YOUR OWN section — `oldText` must match exactly once, byte for byte (line endings included), inside the section body; `newText` replaces that range, and an empty `newText` deletes it. Limit 20000 characters per call, the same cap append enforces. Refused with nothing written: a blank `oldText`, zero hits, two or more hits (the matching lines are named), an anchor crossing the section boundary, an anchor touching the section's **first** `**状态行**：` line, and any replacement that introduces a status line or leaves more of them than before. Deleting a surplus status line is allowed — that is the repair path for a section that reads as unset.
- status: update YOUR section's `**状态行**：` line. `value` must carry exactly ONE legal keyword of your section's own word list (the schema enumerates them) and nothing else but decoration — surrounding symbols, a trailing ISO date, whitespace; prose goes to the separate `note` field and lands as a parenthetical.
  - A section's status is read only when its header zone holds exactly one status line; with two or more it reads as unset and `status` refuses, naming the repair order (edit the surplus line away, then rewrite the remaining one; on §1 the main agent repairs it with an ordinary document write).
  - Writing §1 `已收口` closes the record and runs the closeout-chain gate: every section must carry content (§5 exempt) — the `不适用` declaration is retired, so any `> 不适用：§N` line in §1 is refused outright.
  - This closing path requires `completed` and `closeEvidence`, with the same rules as `close`. It is the only `status` call that accepts those two, and it takes the same repair-close split.
  - Reopening a frozen record = §1 → `进行中` with `note` = the reason: the tool rewrites the §1 status line and appends a `重开记录` line — no other existing line is touched.
  - A reopen reverses a recorded decision, so it is all-or-nothing too: if the ledger rows cannot be brought back to 在途, the record is rolled back to the frozen bytes and the call is refused with the reason named. A record that reads as open while its rows stay 待核销 refuses every write, and that state is never left standing silently.
- close (depth-0 only): freeze the record — §1 → `已收口 <date>`; every further write is refused except the reopen conjunction. It runs the same closeout-chain gate as status, so an incomplete chain is refused, naming the missing sections.
  - **Repair close (`补关`)**: when this record's own ledger rows are all archived already — non-empty, every row `已核销` / `已废弃` — and the only reading against it is `open-but-settled`, the chain content gate and the §3 pass arm are skipped and the record is frozen. Whether this record qualifies is a reading, not a guess: when its §1 status line reads 进行中, run `check` first — the qualifying reading is `open-but-settled` as the only inconsistency, with the exit line 直接收口（活已做完、档未冻结）. The work is already recorded on the ledger side; what was missing was the freeze. One `**补关记录**：<date> · 行集全归档（<N> 行）· §3/§4/§6 未补写 · 操作者 = 主 agent` line is appended to §1 (nothing else in the record changes) and the receipt carries a `[ledger repair]` line. No ledger row is rewritten and no section content is invented.
  - Everything else still runs on that path: the unit-test-file gate, the document-check gate, `completed` and `closeEvidence`, design-token consumption, and the reanchor. A row set that still holds in-flight work is not a repair case — the chain gate applies as usual; an all-archived batch that also reads as any other inconsistency (`header-row-missing` etc.) is refused with every reading listed and a pointer to `check`; a record whose §1 status line is unreadable cannot enter repair close — repair §1 first.
  - `completed` is required: a number array listing every completed 在途 row. Ids must be unique, belong to this record, and currently be 在途. `[]` is valid only when no 在途 row remains.
  - `closeEvidence` is required too: one line saying what this batch actually did. It lands in every settled row's evidence behind a `收口 <YYYY-MM-DD>：` prefix. Blank is refused before anything is written — the machine never writes this sentence for you, or the close-proof gate would be decoration.
  - Closing settles the batch in the same action: each listed 在途 row goes 在途 → 待核销 → 已核销 inside one transaction, and the batch's existing 待核销 rows are settled with them. Closing therefore leaves zero 在途 and zero 待核销 behind.
  - A missing, duplicate, unknown, foreign, or non-在途 id is refused before design tokens, the record, or the ledger are written. Return unfinished 在途 rows to 待讨论 first.
  - Waiting rows still reanchor to `条件`, with the resume sentence 「原批 <record> 已收口，须另起批次接手」. A non-empty resume_when is preserved and the sentence is appended to evidence; non-active `认账不排期` rows stay untouched.
  - Every settled row is named in a `[ledger reanchor]` receipt line, and the two starting points read differently: `#N 「title」在途 → 待核销 → 已核销` and `#N 「title」待核销 → 已核销`. The second form is a row that was already done and merely unbooked — naming it is what stops a silent write-off.
  - The record is written first and the ledger second; the irreversible side (settlement) goes last. If the ledger write fails, the record is rolled back to its pre-write bytes and the call is refused, so you can retry as it stands. If that rollback fails too, the refusal says so and points at `check`: inconsistent rows need repair, while a closed and fully settled batch must not be retried.
- supersede (depth-0 only): freeze a record whose object is gone, that will never be implemented, and that can name its successor — this is the third closeout edge, and it exists because neither other edge can take such a record: `close` needs the whole chain, a repair close needs every row archived, so the finished rows of a dropped batch would stay unsettled forever.
  - `supersededBy` is required and is a fact only you can give. Three forms, each machine-checked: a batch record path (on disk), a document plus a section (`docs/<area>/<name>.md §<N>` — the number must hit a heading line, and neither side of the number may be a digit or a dot), or a commit (40 hex, reachable in the version store). A planned or never-done successor does not resolve and is refused; naming this very record is refused too (keeping it alive is the reopen path).
  - `closeEvidence` is required here exactly as on close — one line of what this batch did before it was dropped; blank (missing / empty / whitespace) is refused before anything is written, and it lands in every settled row's evidence behind the `收口 <date>：` prefix.
  - It does not fill §3 / §4 / §6 in to make `close` pass — that would be fabrication — and it does not leave them blank either: one `**取代记录**：<date> · 由 <successor> 取代 · 本批无实施记录（§5 未写）· §3/§4/§6 未补写 · 结算 <N> 行 · 改挂条件 <M> 行 · 操作者 = 主 agent` line is appended to §1, and the status line becomes `已收口 <date>（被取代）`.
  - The rows go where they belong: this batch's `待核销` rows are settled to `已核销` (evidence behind the `收口 <date>：` prefix), and each unnamed `在途` row goes back to `待讨论` with trigger `条件` and the resume sentence — the work was not done, and the receipt says so instead of claiming it. `completed` is therefore optional here: list a row only if this batch really finished it.
  - Refused with nothing written: the record is not open, its ledger cannot be read (the all-archived case cannot be judged without it), every row is already archived (use `close` — repair close covers it), §5 already carries content (that batch was implemented; the "no implementation record" line would be a lie), or `closeEvidence` is blank.
  - Everything else still runs: the unit-test-file gate, the document-check gate, `closeEvidence`, design-token consumption, the record-first ledger-second write order with rollback. The receipt carries a `[ledger supersede]` line naming every settled and every returned row.
  - The six inconsistencies it can name: `closed-but-open-rows` (frozen, with 在途 rows or 待讨论 / 待设计 rows whose trigger is neither 条件 nor 认账不排期) · `closed-but-settling` (frozen, rows still 待核销) · `open-but-unwritable` (open, no 在途 row left but 待核销 rows exist — nothing can be written) · `open-but-settled` (not frozen — `open`, or a §1 line that cannot be read — with a non-empty row set entirely archived: the expected reading after reopening a fully settled batch. It is the entry condition for a repair close only when the §1 line reads 进行中 — an unreadable §1 line is a reading here, not an entry) · `pointer-stale` (a row whose task_book does not resolve) · `header-row-missing` (a number on the header 台账 line has no same-id items row).
  - `header-row-missing` judges existence only: a row that still exists but was legitimately unbound does not count. Drop the missing number from the header with an ordinary document write; rerunning attach is the secondary path and remains subject to the same-face rule.
  - A reserved pointer (`…md（预定）`) is not `pointer-stale`: its record does not exist yet, and that is its legal state.
  - Every `status` and `close` receipt ends with one `[ledger consistency]` line: `一致（本批 N 行）`, or the inconsistent items with their way out. It reports; it never repairs and never blocks.

Who may write what — identity decides, and a write outside your own section is refused:
- main agent (depth 0) — create / attach / close / supersede.
- append / status domains are mode-dependent: engineering — append §1/§4/§6, status §1; normal — append §1/§2/§4/§5/§6, status §1/§2/§5 (the main agent holds the designer and implementer seats there).
- edit reads the same whitelist as append — one table, two actions: the section you may append to is the section you may rewrite in place. Depth-0 gains §2 and §5 on edit in normal mode.
- eng-designer — §2; eng-coder — §5; a normal-mode coder bound via `batchDoc` — §5; design review (review binding) — §3.

Skeleton placeholders are dead literals in the record header's structural lines — `#<编号>` / `<板块>` and the older `<BATCH-ID>` / `<讨论来源>`. They block append / edit / status until they are filled:
- create with ledger / board fills them at creation.
- On an in-flight record that still carries them, attach fills the number.
- Otherwise the main agent fills the header by file edit (citing these literals in a section's prose is fine — only the header is checked).
- `<§N 模板占位：…>` template lines are legal and never blocked.

Target record:
- Sub-agents and design reviews have NO path parameter in practice — the record arrives via the spawn binding or the review instance key, and passing `path` is refused.
- Depth-0 MAY pass `path` on any action (a value passed must be readable); omitting it picks the unique in-flight record (0 or ≥2 in flight ⇒ refused — pass `path`).

§3 has its own rules:
- A §3 append must carry exactly one verdict on its own line — `VERDICT: pass` or `VERDICT: changes-required`; the localized whole-line forms count too (`结论：通过` / `结论：不通过`, and their 需修改 variants, with an optional trailing 。). A §3 write that reads as no verdict line, or as both at once, is refused with nothing written — no round number is consumed, so resend the same text with the verdict line added.
- A design review's §3 append carries the round's conclusion table — one row per finding (`#` / severity / status / evidence) — plus the VERDICT line and the counts. An evidence cell holds a pointer: a section number, a symbol name, or the exact words of the line — never a line number; the report's own paragraphs stay out of the record.
- A design review's append is stamped by the tool with a `### 轮次 N（评审子代理）` heading — N is tool-counted; do not write your own heading (it would be dropped).

A hit inside an evidence cell that only fails existence still lets the write land: the receipt lists it as a pointer reading, not as a refusal — the cell points at something, it does not prove the file exists.

Every refused hit line names four things: the file, the position, the offending text and the root it was resolved under — the token for an anchor hit, the paragraph or the line itself for a length hit.

A cycle hit is a repo-level fact with no line number: its position reads that way, and its text is the repo chain.

Document-check gate — every append and every edit runs it before the write, any section, depth-0 and sub-agent and design review alike; so does closing a record, or setting §1 to `已收口`.
- `append` judges the text you are appending, the change region of the markdown files already touched in this run, and the record itself — only the first two can refuse the write.
- `edit` judges the paragraph / line-length classes on the `newText` you pass, and the anchor classes (`档缺` / `节缺` / `引缺`) on the whole record as it will stand after your edit — so a dead citation anywhere in the record refuses an unrelated edit, and replacing that very line is the way through.
- A hit in a touched file but outside its change region is earlier debt: the receipt prints one count line and the write goes through. A hit in a section that has already landed is named with its section and author and never blocks the write — the close face is where it is enforced.
- An append receipt reads `[doc-check gate] DOC-CHECK GATE: PASS · 范围 N 档` — N = the documents actually judged, the record itself always one of them. `ERROR` lets an append land but refuses a closeout; with no `PROJECT-MANIFEST.json` the gate does not run and the receipt says so.

Failures are hard and visible (no silent fallback): if a write is refused or fails, say so in your report — “§N not written”.
