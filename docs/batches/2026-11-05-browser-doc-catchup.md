### 机制设计（两句的落面与理由）

**条目 1（放弃腿摘位）**：机制正文住「原子领取」新增条（单源，别处只指路），「持有」形态的动作格补半句「两条放弃腿（门槛命中 ∥ 拉起失败）⇒ 各自先摘掉自己刚建的位再报错」。

为什么必须写：不摘位时，后来的实例读到「pid 活 ∧ 端口答不通」，按四形表进「等待」，耗满一个启动窗才转「接管」——一次失败的领取变成下一个人的等待。

 依据 thincoder-core/browser/pool.mjs「d.remove(paths.lock)」——门槛腿与拉起失败腿各一次（领取成功之后、报错之前）。

**最近先例（条目 1）**：同节已有两处摘位动作 = 「末关删锁」（关成功后 `unlink`）∥「接管」的 `rename` 摘陈旧位。

- **对齐**：摘位只由「建它的那一方」∥「已判陈旧」执行；共享浏览器一律不动（`failSession` ∥ 开启段中止都不碰 `session.lock`）。
- **偏离**：这两条腿的摘位在**报错前**——时间点不是生命周期终点而是失败收尾；理由是位是本实例刚建的那一份，摘它 = 撤回自己刚发的申请，不是处置共享物。

**条目 2（模式定句）**：围栏英文定句进「锁无记录时的模式来源」+ 补消费者指路；「模式（硬后果）」条改标「下句是生效值读得到的那一支」并指路；AC-M2 量法加界；§10 第 9 条的接入注记同加界；§8 U74 补用例锚。

为什么必须写：同节其余回执句式全是围栏英文逐字句，只有这一支是中文描述 ⇒ 实现席只能自创文案；且 `the shared browser is running headless=` 在这一支本就不成立，不写清则验收判据读起来像覆盖了它。

 依据 thincoder-core/browser/pool.mjs「[note: the shared browser is already running — ${tail}]」——定句头与「只报关系」的分支就在这一行，`tail` 与「模式」条那句同源。

**最近先例（条目 2）**：同节「模式（硬后果）」的沿用句形 = `headless=<actual>` + `(started by pid <N>)`。

- **对齐**：同一注记位、同一发出时机（首条回执尾行、发出即清）。
- **偏离**：本支去掉值与拉起者 pid，只留关系句——依据从句里只有 `typeof actual === "boolean"` 那一支带值，读不到时值无从写。
