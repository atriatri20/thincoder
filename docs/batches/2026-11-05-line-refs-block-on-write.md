### 机制设计（三段）

**判据落点 = `doc_check` 的 `gate` 面第三条判据**：`thincoder-core/doc-check/index.mjs` 的 `runDocCheck` 在两条判据之后采集一次行号坐标（字段 `lineRefs`），`gate` 面把 `total` 计入 `hits.lineRefs` 并加进 `hits.total`；首行判决串多一节 `行号坐标 N 处`，命中行形 `✗ 行号坐标 <源档>:<行> <形别> <片段>`——与锚 ∥ 段同形，`REFUSED` 照判。两条既有判据一字不改。

**为什么不挂写前门（理由按用户第三轮订正）**：写前门判的是**本笔触碰的段落**，行号判据加进去会把每一笔正常写作顶住（段落里有存量行号就炸，哪怕本笔一个行号没写）。

而清存量要的判集是**整档**，那是 `gate` 面的事。两道门的分工有成文：只有写前门则旧账没人清，只有轮末检查则问题攒到交付才炸（`docs/core/requirements/DOC-CHECK.md` F14）。本条要的正是清旧账那一半。

**判集 = 合计（正文面 + 围栏内）**：与 `report` 清单的清账口径同源；举例形（`x.md:12` 类）由档名豁免谓词挡掉（单源 = §3.24 条目 X）；围栏块里的改前 / 改后对照同样入判——它们同样是位置引用。

**抽取式零改**：两条正则仍只住 §3.23；`thincoder-core/doc-check/line-refs.mjs` 的清单面与判据面共用同一段逐行判定，不另立第二套。
