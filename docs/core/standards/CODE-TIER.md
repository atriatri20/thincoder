# 代码结构档位（CODE-TIER）· 标准

> 本档规定代码文件和函数何时需要拆分。规则正文只在这里维护，其他文档和提示词引用本档。
> 关联标准 = `docs/core/standards/METHODOLOGY.md` 的 F3 与 F-R24a。

## 1. 判定对象

对象是源代码文件和测试文件，不是文档。需求、设计、批次和其他文档没有行数拆分义务。

文档长度可以作为阅读时的观察，但不触发本档的任何拆分判据。

## 2. 文件档位与两个时点

### 2.1 设计时：500

设计前测量本次将修改的代码文件：

- `> 500`：基准是修改代码前的长度。设计席自觉判断，并在过程记录里写下处置：拆；或写明不拆的理由。
- `≤ 500`：不进入拆分讨论，不写“因此不拆”的冗余结论。
- 新建文件使用其本次落盘长度。
- 拆的方案写当前过程记录的受影响文件清单，不写成设计状态文档的一次性施工表。
- 收口时不判这条线（那一刻的判据是 §2.2 的 800）。

### 2.2 收口时：800

收口检查当前代码文件：

- `> 800`：先拆分再完成收口。
- `≤ 800`：不因长度要求拆分。

同一收口面还检查过程记录是否缺方案或缺读数。每个改动代码文件都必须在当前过程记录中携带批起快照的内容行数；快照没有该文件时写字面 `新`。

读数量法 = `countContentLines`，实现位于 `thincoder-core/agent-tools/batch-tier-gate.mjs`。基线判定与拒绝语义见 `docs/core/design/DOC-CHECK.md` §8。

机器面判的是过程记录里那一行的方案格；拆分本身由设计席与实施席履行，机器不取「拆了没有」这个读数（边界同 `docs/core/design/DOC-CHECK.md` §8.5）。

### 2.3 中间不判

实施、代码评审和其他中间环节不另设代码文件长度检查。不得新增第三条阈值。

两条线各归各的判者：500 归设计席自觉执行；800 归收口门。把 500 搬进收口门，或让两条线在同一时点都判，都是漂移。**收口门的越线方案支按收口线量收口时的当前长度**——它问的是「现在多长」，与 §2.1 的改前基准不是同一个问题；判法见 `docs/core/design/DOC-CHECK.md` §8.5。

## 3. 函数档位

先检查函数，再检查文件。文件较短不能豁免函数，声明较多也不能豁免理解成本。

| 函数长度 | 处置 |
|---|---|
| ≤50 | 正常 |
| 50–100 | 审视是否应拆出独立概念 |
| ≥100 | 主动审视并提取有独立语义的子函数 |
| ≥300 | 必须拆成可复述的骨干与细节 |

函数拆分按概念和可独立验证性，不为满足数字而切碎连续逻辑。

## 4. 数值与语义的归属

- 语义、时点、对象和处置归本档。
- 数值的直接实现位于 `batch-tier-gate.mjs` 和相关提示词。
- 修改数值时同步所有实际实现和当前提示词。
- 修改判法时只改本档，再同步引用面。

`500` 与 `800` 分别对应设计时与收口时，不能交换或复用为中间门槛。

## 5. 漂移判定

漂移看一句话把长度判定派给哪个时点，不看它是否恰好提到某个数字。

- 派给设计时或收口时，符合本档。
- 派给实施、代码评审或其他中间环节，属于漂移。
- 把硬性判据改写为可选建议，属于漂移。
- 过程记录描述某次历史判断，不应被误读成当前规则；若它会被当作当前规则执行，则按当前规则修正。

## 6. 检索与复核

需要检查现有写法时，至少覆盖：

1. 名称面：设计时线、收口线、软线、硬线、拆分触发及对应英文表述。
2. 数值面：500、800 与代码长度语义的共现。
3. 产品文档、提示词、工具描述和代码头注等实际会下派规则的文本。

检索只产生候选，判定仍按 §5。工具找不到的新名称通过写者同步义务和人工复核补足，不声称机械检索完备。

## 7. 量法

代码和测试文件的内容行数只由 `countContentLines` 计算。末尾换行产生的空尾段不计为一行。

不得混用手数、编辑器行号或另一脚本作为同一门槛的判据。

## 8. 边界

- 本档不决定具体拆分的模块名和切点。
- 本档不新增检查点或独立门禁。
- 本档不保存逐文件的一次测量结果。
- 本档不限制文档长度。
- 不用相对大小、文件类型或“都是声明”作为豁免理由。
