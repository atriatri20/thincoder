# 提示词系统（PROMPT-SYSTEM）· 设计

> 需求 = `docs/core/requirements/PROMPT-SYSTEM.md`。
> 最近先例：`CORE-UNIFICATION.md` 的资源随包与 `AGENT-LOOP.md` 的稳定 system。对齐 = 单副本、稳定前缀、显式注入。
> 勘察证据：已读分层、装配矩阵、overlay、工具描述、记忆边界与自动注入。相关 = 当前核内唯一文本面和三档提示词消费。

## 1. 资源与加载

prompt-files.mjs 以 import.meta.url 定位 prompts、prompts/knowledge、core/knowledge 和 tool-docs。loadPrompt、loadAdvisorPrompt 与 DESC 保持当前硬加载/降级语义。

`tool-docs/*.md` 与 prompts 母版同级：`DESC` 读出的是母版原文，不清锚；展开发生在 schema 装配期（§7）。

知识主题是随包静态 Markdown 资源，分两类：prompts/knowledge 是完整档可内联的提示词主题；core/knowledge 是三档都不内联的纯查询主题。加载器按全局唯一的主题标识读取，不以进程 cwd、项目根或用户记忆目录作为知识来源。目录说明 README 不注册为知识主题。

prompts/knowledge、core/knowledge、极简槽文件及知识工具描述都进入 @thincoder/core 包。VSIX 与 Desktop 物化资源时沿用同一边界。

## 2. 完整档与知识单源

完整档源文件同时是完整与极简的母版：正文由必须常驻的硬规则、详细知识主题和内部包含锚组成。装配器从 prompts/knowledge 读取主题，完整档把锚替换成正文，极简档移除锚及其独占正文位置，最后执行既有 overlay 和运行时注入。

母版与知识相关的有两件东西：主题锚，和一段不带锚的常驻查询指引。指引是普通正文，三档装配都看得见——完整档内联 prompts/knowledge 的主题正文，core/knowledge 的纯查询主题在完整档同样不内联，完整档也只有经工具才能取回。极简档移除锚与主题正文，这段指引留下，就是需求 §4 末条与 §9.2 要求的那个入口。它只交代什么时候查、三个动作各做什么、search 只是定位，不搬回任何主题正文，也不改工具集合、schema 或每轮注入项。

包含锚只在装配器内部使用，不发送给模型。主题不存在、标识重复或锚无法解析时明确失败，不把残缺提示词当成可继续运行的结果。

tiny 槽不使用这些包含锚。knowledge 工具与完整档装配读取同一主题文件，因此不存在“完整档一份、知识库另一份”的漂移面。

主题文件保存可独立理解的正文。主题标题用于 list/search，get 返回该主题正文，不叠加另一份机器生成摘要。首行可另带一行 `aliases:` 别名声明（§3），它不算正文：`get`、完整档内联与锚回填看到的都是去掉声明之后的正文。

同一包含锚机制覆盖工具描述。一份工具描述被拆成两块：常驻面留在 `tool-docs/<档名>.md`，展开面整块搬进 `prompts/knowledge/tool-<档名>.md`，原位置换成独占一行的锚。

常驻面只写一句用途：这个工具干什么。动作细则、分支、错误形、选择规则、示例与背景解释都在展开面，占多长都算。

判据是内容，不是长度：一份描述只剩这一句用途，整档留常驻面，不拆；多出任何一条细则，那一段就搬进展开面。每份描述都要有处置，不按名单抽样——一份该拆却整档留着的描述，就是漏判。

端侧运行期注入锚（`{{inject:…}}`）按内容归属留在常驻面：它注入的是执行器行、提问 UI 面这类运行期事实，不是这个工具干什么的说明，也不是可搬的细则——搬进展开面，极简档就丢掉这一行，那属行为改动而不是描述改写。

动作名搬走不构成能力回退：schema 的 `action` 枚举不因档位改写，极简档仍看得见一个工具能做什么；每个动作的调用期契约在展开面，一次 `knowledge get` 取回，需求 §4「不确定工具约定先查 knowledge」是这条的兜底。所以动作细则一律进展开面，不留常驻面。

宿主端对某端不存在的动作做的行级剔除落在装配之后，见 TOOLS 设计档 §1.1。

锚回填是逐字的，三个条件同时成立才算：锚独占一行、主题正文逐字等于 `prompts/knowledge/tool-<档名>.md` 的正文（首行 `aliases:` 声明不计入正文，见 §3）、主题文件不以换行结尾（`prompts/knowledge` 的主题文件都按此写）。

逐字说的是「正文原样回填到锚的位置」，不是「装配结果与拆分前的旧描述逐字相等」。常驻面已按一句用途重写，完整档与拆分前语义等价即可，不要求逐字复刻旧文（需求 §7）。

工具描述的锚与提示词母版的锚共用同一文法、同一重复标识失败、同一未解析失败。差别只在装配点：提示词的锚在 assemblePrompt 里展开，工具描述的锚在 schema 装配处按档展开（§7）。

工具面经 `expandToolDescription(text, mode)` 薄壳转交同一展开器（`thincoder-core/prompt-files.mjs` 的 `expandKnowledgeTopics`）：壳只校验 mode 并选极简支，不复刻锚文法——另起一套展开器就是两处各写一遍逐字一致那条规则，漂一处查不出。

极简档里展开面缺席，模型需要时用 `knowledge get` 取回；展开面主题与提示词主题同一清单、同一 `get` 行为，不另设入口。

## 3. 知识主题目录

主题按两类目录、同一标识空间组织（§1）：prompts/knowledge 是完整档可内联的提示词主题，core/knowledge 是三档都不内联的纯查询主题。当前清单由 `knowledge list` 现读——设计档不复制一份会漂的名单。

主题按现有连续内容块拆分。get 的读取粒度就是单主题，不把多个大章节重新合并成巨型知识文件。

读取成本是这条目录设计的已知代价：读清单要读完每份主题全文取标题，`get` 与锚展开每次都重扫全部主题，所以 `knowledge list`、每次锚展开和每次 `get` 的读取量随主题总数增长，`tool-*` 展开面按同一口径计入。现状不加索引或缓存；主题总数再上一个量级时，改为清单只存标识与标题、正文按需读。

主题文件可在**首行**带一行别名声明：`aliases: 词一, 词二`。声明是元数据而不是正文——加载器在读出主题时就把它剥掉，`get`、完整档内联和锚回填都只看剩下的正文，模型可见文本不因为多一行声明而改变。别名进检索索引，让中文查询能命中英文标识的主题（§6）。

声明只在一个地方解析：加载器读主题条目时（`readKnowledgeEntries`）剥掉首行声明，把别名挂回同一条目。条目面是加载器对外导出的一层读取面：`list`、`get` 与 search 都经它读主题，前两者再各自收窄成标识标题与正文。`listKnowledgeTopics` 仍只回标识与标题，search 从条目面一次取齐标识、标题、别名与正文，不为取别名把目录再读一遍。

分隔符是**半角逗号、全角逗号与顿号**三种（`,` `，` `、`）：作者按中文习惯写 `，` 或 `、` 时切得开，不会整行落成一条永不命中的长别名。每个词两端空白去掉，词内其余字符原样保留——`aliases: batch record, 批次记录` 是「batch record」与「批次记录」两个词。

别名声明只有两种形态：没有这一行（该主题没有别名），或首行是一行 `aliases:` 加至少一个非空词。首行以 `aliases` 开头却不成形时，加载期明确失败并点名该主题——「不成形」有两种：`aliases` 之后没有冒号，或冒号后切不出一个非空词。非首行的 `aliases:` 是正文，不参与声明解析。

**为什么两种都拒**：无冒号那一种若按「一个词」宽松解析，一条散文首行会静默变成一条永不命中的别名，与「只有两种形态」当场矛盾；取不出词那一种静默丢掉，会把「别名写坏了」说成「这个词本来不命中」，两者在模型的失败回执上长得一模一样。

工具描述展开面的主题标识 = `tool-<工具描述档名>`，档名里的 `_` 换成 `-`（`doc_graph-read` → `tool-doc-graph-read`）。标识撞车按重复主题失败，不按目录顺序覆盖。

## 4. 极简槽

极简主会话沿用普通 persona，并使用同一公共与普通纪律母版的极简展开结果。母版只保留需求所列硬规则、具体查询触发指引和 knowledge 查询入口。

极简子代理沿用各自身份档与 subagent-base，并使用同一公共母版的极简展开结果。explore、plan、coder、tester 等角色分别保留自己的读写权限、任务书输入和报告要求，不因为文本精简而把只读角色变成可写角色。

tiny 始终使用普通工作流，不加载工程 discipline，也不启用工程设计令牌或工程写门。normal 与 engineering 继续使用既有完整场景槽。

tiny 的有效上下文窗口取 `CONTEXT-COMPACTION.md` §2.1 的有效窗口（上限数值与算式以该节为唯一出处）；本档只裁定 tiny 用这条预算，不另立窗口规则。

consult 与 advisor 的独立基底不经过极简槽替换。工具面同一口径：advisor 与 consult 装配的工具描述取完整档，不随会话 mode 变化——独立基底被极简装配改写，就与 requirements §9.1 的「不被极简装配改写」当场矛盾。

## 5. 装配入口

assemblePrompt 接收场景和当前互斥 mode。场景继续表达主代理或子代理角色，mode 只决定完整或极简资源组合。

prepareRun 在每次运行时读取当前会话的 mode，并将它同时用于：

1. 系统提示词装配。
2. 文档、记忆和项目大纲的自动注入策略。
3. knowledge 工具准入（三档均提供）。
4. 派生的 engineering 工作流事实。
5. 工具描述的分档装配（§7）。

配置或会话命令在运行中切换 mode 后，下一次 prepareRun 自然使用新值；不修改历史消息，也不回写旧请求。

## 6. knowledge 工具

knowledge 使用第一方内置工具实现，资源读取由 prompt-files 的知识加载函数提供，并在 tiny、normal、engineering 三档工具表中提供。工具对主代理与子代理同样开放，只读且不写记忆；检索与取回全程在本地随包资源上完成，不需要嵌入服务或外部网络（需求 §6）。

| 动作 | 实现行为 |
|---|---|
| list | 从两类随包主题清单返回全局唯一标识与标题 |
| search | 把查询按空白切词，对标识、标题、别名与正文做 OR 匹配，按命中强度排序返回有界定位片段；结果受主题数与字符数双上限约束，被截断时如实报出；行动前必须再用 get 读完整主题 |
| get | 按精确主题标识返回完整正文 |

未知动作、缺少必要参数和未知主题都显式失败。两个资源目录出现同标识时也明确失败，不按目录顺序覆盖。search 无匹配返回明确的空结果并给出下一步，不伪造主题。工具不执行主题中的命令，不把主题文本当成工具调用指令来源。

search 的检索面是标识、标题、别名（§3）与正文四处的并集。查询按空白切词、转小写并去重，任一词命中即入选（OR），不要求全部词命中——`compact threshold` 只在命中 `compact` 的一篇里也照样返回它。空查询与只有空白的查询在切词之前就按缺少必要参数失败并点名 `query`。切词、转小写、去重之后还要去掉停用词（`SEARCH_STOPWORDS`），剩不下一个词时显式失败并点名 `query`，报文给出下一步（换成具体名词重查）——全虚词查询（`the`、`a of the`）走的就是这一支，不退化成「零命中」。

排序按命中强度：先比**标题级命中数**（命中的不同词数，标识、标题与别名都按标题级计），再比**总命中数**（各词在全文中出现次数之和），最后按标识升序。别名按标题级计入，因为别名的存在就是为了把查询词引到该主题，命中它与命中标题是同一个信号。查询词序不影响结果，同名次结果不随目录遍历顺序抖动。

停用词表是代码内常量 `SEARCH_STOPWORDS`（`thincoder-core/tools/knowledge.mjs`）：中英各约二十个高频虚词，大小写不敏感，分词后、计分前过滤。**为什么**：它治的是排序噪声而不是体积——`the` 这类虚词几乎命中全部主题，会把 `evidence` 这种真信号顶下去；体积已由两个上限兜住。词表不进 `prompts/knowledge`：它属于检索逻辑，做成数据文件就多一份资源边界与热加载成本。中文不另做分词：按空白切，中文整句本就是一个词，虚词过滤对它无效，中文查询靠别名（§3）解决——两条并行、不重叠。

两个上限同时生效，常量分别命名 `SEARCH_MAX_TOPICS`（10 个主题）与 `SEARCH_MAX_CHARS`（6,000 字符），整份返回按紧凑 JSON 计量（含外层字段）。先到者截断：下一个主题会越过任一上限时不再加入。上限是成本门而不是相关性判断，所以截断必须看得见——返回的外层字段报 `matched`（命中总数）、`shown`（返回数）与 `truncated`；把「返回了 10 条」读成「只有 10 条命中」会让模型停在第一个上限上，而真实答案可能在第十一条。

单主题的定位片段仍是至多 3 段、每段 240 字符（`SEARCH_SNIPPETS_PER_TOPIC` / `SEARCH_SNIPPET_CHARS`）；同一主题内多个词命中同一段时只取一次，不重复计入字符预算。两个上限常量与单片段字长常量（`SEARCH_MAX_TOPICS` / `SEARCH_MAX_CHARS` / `SEARCH_SNIPPET_CHARS`）随工具模块导出，用例与其它消费面读同一份数——抄一份常量会在生产改数时静默过期。

0 命中给下一步，而不只是给一句否定：回执点名可以换成单个英文关键词，或先 `list` 看全部主题标识。中文查询只能经别名命中，一条零命中的回执若不指路，模型往往按同一形态重试一次。

工具描述保持短小：常驻面只说明何时查询及三个动作，检索语义（分词、排序、两个上限、空结果回执）写在展开面。知识正文不进入工具 schema。

检索链按概念拆成三个具名函数：切词与去停用词（`tokenizeQuery`）、按条目计分（`scoreTopic`）、按两个上限收集（`boundedHits`）。`execute` 只做动作分派与回执成形，函数档位按 `CODE-TIER.md` §3 判。

## 7. 自动注入策略

tiny 下 prepareRun 跳过相关文档、历史记忆和项目目录大纲的自动注入。模型需要时使用 doc_search、memory、repo_outline 主动查询。

项目 AGENTS、项目规则与 skills 能力清单仍按现有入口提供。环境、时间和 git 等短事实继续通过既有用户上下文通道注入。

normal 与 engineering 的自动注入保持现状。injectDocs、injectProjectRules、injectMemories 等既有键不在 tiny 中形成第二套互相矛盾的模式状态；tiny 的注入策略由唯一 mode 决定。

工具 schema（参数、必填、枚举、校验）不因档位改写。工具描述按档装配：完整档把常驻面与展开面在锚处拼成一份完整描述，语义等价于拆分前而不要求逐字复刻旧文；极简档只给常驻面，展开面经 `knowledge get` 取回。

极简档描述的目标文本 = 母版经同一极简展开后的字符串：锚及其后至多两个换行被移除。展开面落在描述末尾时，结果尾部余一个空行，属目标文本的一部分——判据是「不含锚字面、不含展开面正文」，不追加行尾清理。

体量分四项分别测量——系统提示词、工具声明、自动注入、完整请求——不互相冒充。

## 8. 内容归属

| 面 | 内容 |
|---|---|
| 完整 persona/common/discipline | 公共与普通纪律母版的硬规则及知识包含锚 |
| 极简槽 | 必须常驻的硬规则与查询指引 |
| prompts/knowledge | 完整档与 knowledge 工具共享的提示词主题正文 |
| core/knowledge | 三档均不内联、只供 knowledge 查询的参考知识 |
| subagent-base | 各极简与完整子代理共同使用的完整角色边界、范围和报告义务 |
| advisor/consult | 各自完整评审或会诊规则 |
| tool-docs | 工具描述的常驻面：这个工具干什么的一句话用途，以及随它留下的端侧运行期注入锚 |
| prompts/knowledge 的 tool-* | 被拆出的展开面：动作细则、分支、错误形、选择规则、示例与背景解释 |

规范正文由负责设计档管理；提示词内不引用它来解释规则。执行坐标可以指向批次 §2 等实际工作对象。

## 9. 变更与验证

改规则时同步负责设计档、运行文本、schema/工具行为和受影响测试。不得为省上下文删除业务门、角色权限或验证义务。

验证包括：

- 完整 normal/engineering 渲染对照，确认主题内联没有改变模型可见内容。
- 极简主代理与子代理角色矩阵、硬规则标记、常驻查询指引在场、知识正文缺席和 knowledge 准入。
- 包含锚缺档、重复主题、未知主题、坏别名声明的加载期失败（无冒号 ∥ 冒号后无词两种形态）、别名命中与排序键序、全虚词查询的显式失败、搜索无匹配、search 双上限截断与披露、资源打包。
- tiny 自动注入收窄与项目规则保留。
- 运行中切换后下一轮 prepareRun 使用新 mode。
- 系统提示词、工具声明、自动注入和完整请求分别计量。
- 完整档工具面：逐份渲染，确认常驻面与展开面正文在锚处拼成一份完整描述，且展开面正文逐字等于其主题文件的正文（首行 `aliases:` 声明不计入正文）。
- 极简档工具面只含常驻面，工具数量与 schema 键集不缩水；目标文本按 §7 判，不按尾空行判。
- advisor 与 consult 装配点的工具描述取完整档，极简会话内不变。
