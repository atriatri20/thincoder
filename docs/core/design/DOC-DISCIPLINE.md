# 文档纪律（DOC-DISCIPLINE）· 要求

> 本档只写**要求**：文档该长什么样、工作该怎么做。每条 = 一句要求 + 一句为什么。
> **怎么检查**（只判三件事：一段太长 · 拿行号做锚 · 悬空指针）= `docs/core/design/DOC-CHECK.md`。
> 需求层 = `docs/core/requirements/ENGINEERING-MODE-V2.md` §13.1。批次流程与六段 = `docs/core/design/BATCH-RECORD.md`；台账 = `docs/core/design/LEDGER.md`；落点与命名 = `docs/core/design/DOC-SYSTEM.md`。

## 1. 文档更新纪律（D1–D23）

### D1 写权矩阵

**要求**：同一文档在同一轮只有一个写者。工程模式下：批档按段分作者——§1 ∥ §4 ∥ §6 = 主 agent，§2 = eng-designer，§3 = 评审（设计轨由设计评审结算落笔，代码轨与普通模式由评审席位写），§5 = eng-coder（段写权单源 = `docs/core/design/BATCH-RECORD.md` §4.1）；需求档 ∥ manifest ∥ 台账 = 主 agent，设计档 = eng-designer，提示词 = 产品代码面 = eng-coder。普通模式下，主 agent 兼写需求与设计。角色分工不改变文档的权威归属。

**为什么**：多一个作者，同一个事实就有两种写法，而没人能说哪一版是准的。

### D2 单一权威源

**要求**：一条机制只在一处详述，别处只引用、不重述（模板同理）。

**为什么**：两处详述迟早各改各的，读者读到哪一份全凭运气。

### D3 计数·枚举纪律

**要求**：说「N 项 ∥ 处 ∥ 条」时，数与列表同轮改；只改数不改列表即违规。

**为什么**：数走了列表没走，读者按数去数，数不上就是整段不可信。

### D4 指针纪律

**要求**：指针写「文档:节」；行号不作指针形态；档名与代码坐标都写到能解到盘上那一件；不写「见上」「见该节」式相对指针。

**为什么**：行号指向位置不指向内容——上面插一行，它以下每一处一起漂；而写错的 token 与解不到的 token，在读者眼里一模一样。

### D5 冻结窗口

**要求**：一支评审在途期间，被审内容不改（设计档与批档的整档改写按机制拦；批档 §3–§6 照写）。要改在评审之后，也就是修正轮。

**为什么**：评审读的是点火那一刻的对象；改完，它判的东西就不在了。

### D6 回读核对

**要求**：任何写入后回读核实，再报完成。

**为什么**：写入静默失败、编辑吞标题，两样都实证过。

### D7 变更留痕 + 核销同步

**要求**：每批收口跑一次核销同步清单——角色表 · 状态行 · 计数 · 指针 · 待办勾销（含前批遗留）· 修正轮落地 · 搁置与暂缓批复核 · 用户文档面 · 落地核对 · 台账可见面。槽位与口径见 `docs/core/design/BATCH-RECORD.md` 的收口一节。

**为什么**：不收口就换批，上一批的欠账没人认领。

### D8 失效表达必删

**要求**：现役规范面（功能点 · 验收 · 判据句 · 纪律句 · 边界 · 现状陈述）里的表达一旦失效，**删除**——不留划改、不留「原记 X ⇒ 收正 Y」、不留「已作废 / 已裁撤」；历史去处 = git 提交。记录面（批档 · 台账 · 提交信息）照留。

**为什么**：读的人会把死条文当成活待办——实测：一条划改残留被重新立批，三轮空转。

### D9 知其然知其所以然

**要求**：改规范文本先有来源（用户原话 ∥ 实证 ∥ 评审）；要求之外写清因果与教训；理由的来源要能指认；从简，不逐句配理由。

**为什么**：没有来源的改动，既不能被检查，也不能被推翻。

### D10 过程面坐标不进交付物

**要求**：交付物（需求档 · 设计档 · 签字件）不引批档路径、批档段号、台账行号；要报一个量，写量法 + 结论。

**为什么**：那些坐标与批档同寿命，批档一删，指针就地死亡。

### D11 规则同轮同拍

**要求**：一条规则变了，凡声明它的地方同轮改——判据句、编号与闭枚举、代码符号名、命中处。分属不同写权的，同批各写域各落，不许「下批再说」；落不完就上抛。

**D 族两份载体**：提示词面 `thincoder-core/prompts/discipline-engineering.md` 的 D 清单写可执行的一句话规则，且不指回本档——提示词面必须自足；本档写要求 + 为什么。同一条 D 在两处各有一份，改一条就同轮改两处。

**为什么**：留下一层不改，下一个人读到旧层就照旧层做，而且没有一处会报。

### D12 读数住在哪

**要求**：读数 = 命令的输出，留在输出里，不转抄进任何文字。文字只携三样：怎么量（命令 ∥ 工具名）、阈值（规则本身）、结论（关系句）。规范面零绝对读数；绝对值的合法落点只有可丢弃载体（批档、命令输出）。手数的不算读数。

**为什么**：抄进去那一刻它开始陈，陈了没人知道，而下一个读者会照它判活。

### D13 「待裁」不是终态

**要求**：带「待裁」的行三件齐才算标——谁裁、按什么裁、到期条件。缺一件就改写成已裁陈述，或改成台账行。

**为什么**：标本四样齐着（症状、坐标、处置、归属），只差有人去做；「待裁」四个字让它不必有人做。

### D14 退役对象一次扫完

**要求**：键 ∥ 入口 ∥ 常量退休，同一笔全仓扫它的名字（域由执行者写死并写明），逐处归**删** ∥ **改指** ∥ **转台账并给到期条件**三类之一，并事前写明预期残留数；实测命中数 = 事前写明数才算收口。

**为什么**：一个退役对象被拆成多行、多个批、多个「零触」，每一行都以为别处在管。

### D15 一把尺子量一种读数

**要求**：同一件事的读数取之同一把尺子。本项目的两把：长度类由 `doc_check` 报出；文本类由 `node` 行扫描 ∥ 内置 `grep` 取。落在这两把之外的读数，先问「它的尺子是哪把」，定不出记 `unverified`。谈口径、定义、量法的段落，下笔前先量一次。

**为什么**：别的取法是另一套解码标准——错尺子给出的零与真的没有，印出来一模一样。

### D16 示例进围栏

**要求**：成块示例写进围栏块；行内假设名走尖括号占位形（如 `<area>/<name>.md`）。

**为什么**：假路径写在正文里就是一条悬空指针，读者与门都会当它是真的。

### D17 载体边界

**要求**：设计档与需求档只写目标态——不写这一批怎么改、不写「将新增 / 待验证」、不把机制记成「计划中」。这一批要做什么住批档 §2，改成了什么住 §5。落地后设计档与实现不符，只有两种处置：代码写错了（修代码，设计档不改），或目标变了（走设计变更）。没有第三种。

**为什么**：计划句在写下的那一刻为真，落地后只剩两种下场——句子过期，下一个人照着再做一次；或者批收口了、事没做，没人接着办。

### D18 文档不标行数

**要求**：文档不声明自己有多少行、不写尺寸档位；行数与体积的档位判据只约束源码与单元测试档。

**为什么**：文档的行数不是读者关心的事，而标注它只会在每次编辑后过期——过期数字比没有数字更坏，读者还得先判断它是不是真的。

### D19 不拿行号指路

**要求**：要指某一份档的某一处，写那一节的标题，或直接引那一句原文；不写行号，也不写「上面第三段」「倒数第二行」这类相对说法。

**为什么**：行号指向位置、不指向内容——上面插一行，它以下每一处一起漂；读的人照着去翻，翻到的是别人。

### D20 依据必须引原文

**要求**：写「依据 X」时，后面引的那句必须是 X 里逐字连续的原文——不改写、不省略、不拼接。引不到原文就不写「依据」。

**为什么**：引二手当依据已经真出过两次，一次把不存在的条文挂到档名下，一次把代码注释当契约；两次都读起来完全合理，坏在落地之后。

### D21 文字太长，标准挂在工具面

**要求**：一段文字读起来是一堵墙，就重写这段文字——拆成几个短句，能枚举的转成列表或表格，什么也不承载的删掉。判「太长」的标准是 `doc_check` 的判定，不是某个字数：阈值住在工具里，跑工具取判定，不自己量。

**取判定跑诊断面**：`mode` = `report`，它判整份档。`gate` 面只判本批变更区；没有绑定批档时它印一行裸 `PASS`、一档也没判——拿它当写作标准等于没量。

依据 `thincoder-core/agent-tools/doc-check.mjs` 里真正做判定的三行，每段引文逐字连续，中间不删字、不改写：

- 「const bound = typeof ctx?.agent?._batchDoc === "string" && ctx.agent._batchDoc.trim() !== "" ? ctx.agent._batchDoc : null」
- 「const sha = bound ? baseShaOf(bound) : null」
- 「const regions = sha ? changedRegionsOf(root, sha, absDocs).regions : new Map()」

没有绑定就没有基线，`regions` 是空表，逐档没有条目。

**长而结构清晰的形态不算太长，一个字都不要改**（判据面 = `docs/core/design/DOC-CHECK.md`）：

- 表格行——表体延续到第一个无竖线的非空行
- 列表项（`-` `*` `+` · `数字.` ∥ `数字)` ∥ `数字、` · `·` ∥ `•` · 圈号 `①`–`⑳`）与它的懒惰续行——续行仍属列表
- 围栏代码块（三反引号 ∥ 三波浪号）与四格空格或 Tab 起头的缩进代码块
- 标题行（1–6 个 `#`）与引用块（`>` 起头）：引文逐字连续，**不许折行**；两面都不计入段。长原文放进围栏块仍是更好的形态，与 D16「示例进围栏」同一路数

**要重写的只有一种**：长且要逐字读的散文——一句接一句，读者读不完。

**文档面：只插空行、只换行不改字，不算重写**：同一串字断开成几行，读起来仍是一句长话；空行在这一面真的断段，插空行只是把命中从门里藏起来。命中消掉而一个字没改的段落仍不合规——机器判不出来，判它的人是评审与收口人，读的是改动过的那个段落。

**提示词面：句读处断行是合法排版，不是冒充**：那一面按行判段、换行排的是版式，所以一句或一个分句一行、一个字不改，那里合法（判据面 = `docs/core/design/DOC-CHECK.md`「提示词面每行自成一界」）。判它是写那一面的人与评审，问的是「这一行读得完吗」，不是「有没有插空行」；要重写的仍是那条读不完的句子——分行不改变它，重组句子才改变它。

**为什么**：字数只是表征，根本问题是太长的文字难读。把注意力放在字数上，下一步就是自己造一把量尺，量出一堆不该拆的段落，再用插空行、断句去凑数——绕的是门，可读性一点没修。

### D22 推断须标来源

**要求**：按形推出来的格子——顺着标题、邻行或行的形状补的值——是推断，写成 `inferred from …`，不写成读数。

**为什么**：靠标题猜出来的节号，会把一次派单送到写着别的内容的那一节；推断落到纸上，与当天真取到的那条读数一模一样。

### D23 引用失效的处置

**要求**：处置一条坏引用，先认它的语义目标，再动文字——读引用句、目标档与它所属的那一节，确认这句话原本要把人送到哪里；改完再读一遍改后的句子，看它是否还把人送到那里。`doc_check` 转绿只是结果之一，不当目标：不拿占位档、不拿无关的同名档，也不靠删掉必要含义去换绿。

**分类处置**：

| 情况 | 处置 |
|---|---|
| 目标仍在，路径不完整或已移动 | 阅读上下文后改到真实当前路径 |
| 同一档名有多个候选 | 按板块、章节与引用语义选定；判断不了就停下并报告 |
| 目标已删除，规则仍有效 | 指向当前负责该规则的文档与章节 |
| 文档正确而检查器误判 | 报检查器问题，不改坏正确文档 |

**操作纪律**：

1. 语义修改由作者用文档写工具完成，不用脚本批量替换。
2. 同轮查反向引用与同一主题的其他现行档，一并处置。
3. 不新增无意义文件去填死指针。
4. 检查与真实句子冲突时，修检查或其适用范围，不改记录去迎合检查。

**为什么**：引用坏掉时改字最省事，而改出来的句子往往形上对得上、送的人已经换了——一处假绿比一处红难发现得多，下一批照着它判活。

## 2. 边界（本档不写）

- **不写怎么检查**：判据、阈值、报面句形一律住 `docs/core/design/DOC-CHECK.md`；本档只在需要时指一句。
- **不写用例与验收**：改写面用例的判据在批次档 §5；收口那一次整档跑就是验收。
- **不写流程**：六段、审批、核销的顺序住 `docs/core/design/BATCH-RECORD.md`。
- **不写台账机制**：L1–L4 判据住 `docs/core/design/LEDGER.md`。
- **不写落点与命名**：文档放哪、叫什么、怎么归属，住 `docs/core/design/DOC-SYSTEM.md`。

## 3. 机器那一面在哪

一段多长算长（段怎么断、字怎么数）· 行号形怎么认 · 档名怎么认、在哪儿找、仓外为什么不管 · 报面句形，全部住 `docs/core/design/DOC-CHECK.md`。本档提到「找得到」时，指的正是那一档的「在项目根下找一次」。
