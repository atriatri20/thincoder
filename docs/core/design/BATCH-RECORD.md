# 批次档与段写入（BATCH-RECORD）· 设计

> 需求 = `docs/core/requirements/ENGINEERING-MODE-V2-SPEC-BATCH-SEGMENT.md`。
> 最近先例：`docs/core/design/LEDGER.md` 的逐行写核和 `PATH-RESOLUTION.md` 的统一解析。对齐 = 写前校验、失败零假成功；偏离 = 本档负责六段与生命周期。
> 勘察证据：已读当前 batch 工具契约、批次需求与联动设计。相关 = 动作、段写权、状态行和收口。

## 1. 载体机制

批次档贯穿一轮工作的讨论、设计、评审、批准、实施和收口。路径由 docRoot.batches 与显式参数决定，不假定本仓布局。

批次档是过程记录，可清理；长期规则必须进入状态文档。

## 2. batchDoc 与 spawn 门

eng-coder 与 eng-designer 必须携带可读 batchDoc。普通模式 coder 可选绑定，绑定后获得自己 §5 的记录通道。

子代理 append/edit/status 不接受任意目标路径，目标来自绑定。depth-0 可显式 path；缺省时只有唯一在途批才可省略。

评审的 batchDoc 通过评审实例键传递，不使用全局“当前批次”状态。设计评审必须有当前账链；代码评审不强制设计凭证。

## 3. 交界面

- 任务、凭证和批次路径通过参数传递。
- 子代理写自己的段，父侧不代写为常态。
- 需要用户决定时上报主 agent。
- 写不进去时明确说哪段未写入。
- 多批并发不得串档。

## 4. batch 工具

### 4.1 动作与段写权

动作 = create、attach、append、edit、status、close、supersede、check。

| 身份 | 可写段 |
|---|---|
| 主 agent | 工程：§1/§4/§6；普通：§1/§2/§4/§5/§6 |
| eng-designer | §2 |
| eng-coder | §5 |
| 普通 coder，已绑定 | §5 |
| 工程模式代码轨评审席 | §3 |
| 普通模式评审席 | §3 |

工程模式的设计轨 `§3` 没有席位写者：轮次块只由设计评审结算写（§4.4）。工程模式的代码轨评审与普通模式评审仍写 `§3`——那两条路没有设计结算可代写，而收口门读的是 `§3` 的段级状态行。

create/attach/close/supersede 只由 depth-0 主 agent 执行。check 只读。

append/edit 使用同一身份段域。append 在段尾添加；edit 用 oldText/newText 精确替换自己段内区间，newText 空表示删除。

### 4.2 档绑定

| 调用方 | 绑定来源 |
|---|---|
| eng-designer / eng-coder | spawn batchDoc |
| 普通 coder | 可选 spawn batchDoc |
| advisor（绑定评审：设计轨 ∥ 代码轨 ∥ 普通模式） | 当前评审实例 batchDoc |
| 主 agent | 显式 path 或唯一在途批 |

绑定之外的批次档写入按跨批写门处理。批次自己的合法伴随件按当前规则处理，不借此扩大授权。

### 4.3 工具挂载

工程角色获得相应 batch 变体；绑定评审的**设计轨**在工程模式不获得批档写通道（§4.4），**代码轨**与普通模式仍获得 `§3` 通道。未绑定的普通 coder 不获得 §5 写通道。工具是否存在与动作是否允许都要符合当前角色。

挂载判据住 `advisorToolsFor`（`thincoder-core/advisor/loop.mjs`）：绑定、且不是「工程模式 ∧ 设计轨」时追加该工具。模式与评审轨两项输入缺一即判不出，故不许用默认值顶替。

两层守卫各管一个问题。挂载面判「这个评审实例拿不拿得到 batch 工具」：工程设计轨拿不到，工具不存在，调用到不了写函数。段白名单面（`allowedSegment`）判「拿到工具的调用方能不能碰这一段」：评审实例取 `§3`、eng-designer 取 `§2`、eng-coder 取 `§5`，depth-0 按模式取自己的段域。两处判据同源——同一对输入（模式 × 评审轨），不是两套规则。

工程设计的 `§3` 拒上，起作用的是挂载面；白名单那一支在那一路不可达，但仍要判：批单测直接调 `appendBatchRecord`、传评审 profile 打 `§3` 即走到它，评审实例越段打 `§2` 也由它拒。只守挂载面会留下「工具在、段不拒」的缺口，而代码轨 ∥ 普通模式的分岔正是从这里进来的。

### 4.4 §3 评审记录

工程模式的**设计轨**：`§3` 的轮次块只由设计评审结算写，评审席不写它，批工具的任何席位通道也不写它，`§3` 对那一路的一切工具通道只读，记错由新一轮覆盖，不靠 `edit` 修。**代码轨**与**普通模式**的 `§3` 不由结算写——代码轨没有结算进场，普通模式的结算整段跳过（不读档、不写 `§3`）；绑定评审席位照旧写 `§3`，块形与裁定规则同下；那条路上的伪戳丢弃（`dropStamp`）与两个状态行计划一并保留。

块形三件，按序：

1. 工具戳 `### 轮次 N（评审子代理）`——`N` 取骨架档 `nextRoundNumber`，不另立第二套计数。
2. 结算头一行：`**结算**：<已签发|未签发>（<原因>）· <日期>`。
3. 本轮结论三件，按序：结论表行 → 裁定行 → 计数行。评审的推理正文不进块——它留在评审报告里。

**结论表行**：取评审体里**最后一块**连续表行（行首允许前导空白、首字符 `|`，块内每行同形不中断）；该块首行切格、逐格按归一口径处理后须逐字等于 `#` ∥ `severity` ∥ `status` ∥ `evidence` 四格，第二行是分隔行（每格只含 `-`、`:` 与空白）。整块原样进块，一字不改、列不增删。取不到这样的表 ⇒ 块内写恒定标记 `本轮无结论表`，不回退整段落原文。

围栏代码块与四空格缩进块里的行不参与认表：报告里复述块形、举出表头样例都不构成结论表。同一立场见 `ADVISOR-GUARDS.md` §1.1——匹配块首行，避免把表格、引用或围栏里的相同文字当成失败尾。

**表头归一只做三件**（去两侧空白、去两侧反引号、小写化）：归一后逐字等于 `#` ∥ `severity` ∥ `status` ∥ `evidence` 四个词才认表。规范字面形 = `| # | Severity | Status | Evidence |`。为什么归一：评审实写的表头是大写 `Severity`，也可能裹反引号；逐字小写比对会把它们全判成「无结论表」，fail-closed 从兜底变成常态。三条归一都是格式噪声，不改语义——无关表仍要凑齐四个词才命中，闸不松。

报告侧契约把结论表钉在报告末尾：报告最后一块表就是它，表头逐字 `| # | Severity | Status | Evidence |`，一条 finding 一行；`Severity` 是 🔴 ∥ 🟡 ∥ 🔵，`Status` 首轮记 `New`、复核前轮时记 `Fixed` ∥ `Accepted` ∥ `Unfixed`，`Evidence` 放指针——节号、符号名或该行原文，行号不是指针。

承载面 = `thincoder-core/prompts/` 的 `advisor-design.md` ∥ `advisor-round1.md` ∥ `advisor-round2.md` ∥ `advisor-round3.md`，各带一段，首句逐字 `**Your report ends with the conclusion table**`；缺这一段，报告末尾就没有这张表，认表落到 `本轮无结论表`。

各轨自己的明细表（findings 表的 `Category` ∥ `Issue` ∥ `Suggestion`，复核表的 `Orig#` ∥ `Notes` 那类列）保持原形，不进块；进块的只有报告末尾那张四列结论表。

生产端与认表判据是同一条列形的两端：块内 `本轮无结论表` 记的是那一轮报告里没有这张表——承载面缺这一段，或报告没按契约写，落块都是这一句，不另设判据区分。

为什么按四列认表：只按首格认表挡不住报告结尾另起的无关表（核对记录那类）——块里看着有表、内容却是别人的记录，比空着更坏。为什么取最后一块：契约把结论表放在 findings 之后、裁定行之前。

**裁定行**：由结算按本轮处置写出，不从评审体里挑——`pass` ⇒ `VERDICT: pass`（命中 `VERDICT_PASS_LINE`）；`changes-required` ⇒ `VERDICT: changes-required`（命中 `VERDICT_CHANGES_LINE`）；`no-pass-line` ⇒ `本轮无裁定行（评审未给出 VERDICT 行）`；`no-valid-echo` ⇒ `本轮未回显有效 token（评审回执不完整）`。

为什么由结算写：块内裁定、结算头与凭证结局必须三处同源；从评审体里挑会造出「块说 pass、结算头说未签发」的第三态。后两处置的说明行不命中任何一个裁定锚——未签发的轮次不许在 `§5` 门那一面读成一个裁定。

**计数行**：由结算按取到的表体算。表体 = 表头行与分隔行之后的行，这两行不计。逐行一次：先取 `severity` 那一格，格内命中的标记即该行档位；该格为空才落到行内最先命中的标记；三者皆无记「未标」。形 = `计数：🔴 <a> · 🟡 <b> · 🔵 <c> · 未标 <d>`，表取不到 ⇒ `计数：不可得出`。

为什么先取 `severity` 一格：那一格就是档位列；证据格里引用的档位标记（引判据、复述上一轮那类）不该改这一行的计数。格子空着是表没写全，那时才退回扫行。

为什么不取评审自己写的计数：那是一句自由文本，解析自由文本会漂——换一种说法、换一个位置，取法就得跟着改；表行是结构，按格取标记是确定性取行。

**整块全取**：结论表有几行进几行——一条 finding 一行，行数由评审自己的结论决定，取行不截断、不设行数常量。

为什么：截断要连带一条省略行与它自己的省略计数，等于在结论之外再造一层要维护的形态；撑大块的是推理正文，那一层已经挡掉。

结算头的原因两个族：处置四词与宿主不完整族的 kind 词。评审完整时取处置词——`pass` = 签发支；`changes-required` 与 `no-pass-line` = 裁定闸 `verdictGateFailure` 的对外拒因；`no-valid-echo` 见下段。评审不完整时取该 kind 词：那一轮的正文可能缺半，处置词读不出可信的结论。

`no-valid-echo` 由 `settleDesignReview` 的回显失败支派生：那支只返回消息常量 `NO_VALID_ECHO_MARK`「未回显有效 token——未签发」，没有自己的词，故与两个拒因词并列单列一个。

结算头说的是引擎怎样处置本轮，不是评审的裁定。读法：裁定看 `VERDICT:` 锚所在的那一行，`VERDICT: pass` ∥ `VERDICT: changes-required` 才是裁定；结算头那一行只说引擎处置。

缩进保留，两条理由：整块成为缩进代码块，文档检查的段长判据排除代码块；裁定锚允许前导空白，缩进后照旧命中，故状态行计划与 `§5` 门读的是同一份正文，零新解析。段标题锚 `^## §N` 与轮次块锚 `ROUND_HEADING_RE` 只认行首——块内三类行（表行、裁定行、计数行）都不以 `## §` 或 `### 轮次` 起头，两枚锚不会命中块内内容。

判的是当前状态的评审都落一块：`pass` ∥ `changes-required` ∥ 无裁定行 ∥ 未回显 ∥ 宿主不完整族。判据不看凭证结果——记录的是本轮说了什么，凭证结局写在结算头。被审档在结算前变了（封印算不出）或评审陈旧时不落块。

宿主不完整族（`context_limit` ∥ `turn_cap` ∥ `timeout` ∥ `empty` ∥ `interrupted` ∥ `review_failed`，判定见 `ADVISOR-GUARDS.md` §1.1）的块：结算头原因写该 kind 词，裁定行写恒定说明 `本轮评审不完整（<kind>），不产生裁定`，不命中任何裁定锚；结论表行与计数行按同一取法处理已产出的正文，正文没产出即 `本轮无结论表` 与 `计数：不可得出`；状态行不动。

状态行由结算按处置写：`pass` 走 `statusPassPlan`，`changes-required` 走 `statusResetPlan`，其余处置不动它。块文成形 = `designReviewBlock`（`thincoder-core/agent-tools/design-review-record.mjs`，纯函数、零 fs），写仍走结算的单通道。

代码轨评审的记录落点就是同一本批档的 `§3`：它没有结算可代写，故由绑定评审自己 `append` 块，裁定行闸 `R-G3` 照旧判它、置位仍由 `statusPassPlan` 那一笔。收口读的是 `§3` 段级状态行——块写不进就置不了「评审通过」，正常批收口门因此不放行（§4.18）。

### 4.5 提示词与工具描述

提示词说明各角色的写入手段、拒收、失败上报和当前记录形状。工具描述是参数与动作的即时使用契约。报告侧结论表契约的承载面 = 四份 advisor 提示词（§4.4）。

写到 `§3` 写者的句子按模式 × 评审轨判读：工程设计轨的写者只有结算，评审席既拿不到批档写通道（§4.3），也没有可写的块（§4.4）。于是一句给评审席一个 `§3` 写口的句子，只在代码轨与普通模式下成立；写成无条件形，读者照它去 `append`，落不成还要报一句「§3 not written」——把一件本来正确的事报成失败。

每一面的处置由「谁读得到这份档」推，不由「这句话真不真」推：同一句无条件的话，读它的人手里有没有那件工具，处置就不同。三份描述档的装配面：

| 描述档 | 装配面（`thincoder-core/agent-tools/batch.mjs`） | 读者 |
|---|---|---|
| `tool-docs/batch.md`，内联 `knowledge/tool-batch` | `PROFILE_DOCS` 没有这个身份 ⇒ 走全量面（`batchTool` 的 `profileKey` 为空那一支） | depth-0 主 agent；两种模式、两条轨都在读它 |
| `tool-docs/batch-review.md`，内联 `knowledge/tool-batch-review` | 评审实例（`review = true` ⇒ profile `review`） | 只发给已经拿到批工具的评审实例 |
| `tool-docs/batch-eng-designer.md` ∥ `tool-docs/batch-eng-coder.md` | 按角色取 profile | 两个工程席位；两者都没有 `§3` 写面 |

六面逐面判读：

| 面 | 载体（档 + 拥有该句的条目 ∥ 段名） | 判读 |
|---|---|---|
| 主 agent 的派单 | `thincoder-core/prompts/persona-engineering.md`「## Review convergence」条目的 reviewer 派单句 | 两支写清：代码轨评审自己 `append` `§3`；设计轨的块由结算写，评审席没有该工具 |
| 批工具写面表 | `thincoder-core/prompts/knowledge/tool-batch.md`「Who may write what」那一组里 `design review (review binding)` 的行 | 代码轨与普通模式成立；设计轨没有这一行对应的席位 |
| 批工具 `§3` 规则 | 同档「§3 has its own rules」块的两句：结论表句 · 轮次戳句 | 两句同判：限定到代码轨与普通模式。设计轨的块成形于结算，评审席没有 `append`；轮次戳在那一路仍由工具盖（§4.7「工具生成轮次」），只是盖在结算写的块上 |
| 评审席侧工具说明 | `thincoder-core/prompts/knowledge/tool-batch-review.md` 全档 | 不带模式限定：这句话随评审实例的工具一起发出，读到它的席位手里都有那件工具；设计轨既收不到这份描述，也没有能写的段（§4.3），限定句在那一路没有可执行的读者 |
| 评审席自身提示词 | `thincoder-core/prompts/advisor-design.md` ∥ `advisor-round1.md` ∥ `advisor-round2.md` ∥ `advisor-round3.md`「## Batch-record §3 landing」段末部 | 按轨分两支写清：有工具的轨（代码轨 · 普通模式）照写，落档失败要报；工程设计轨没有该工具，块由结算写，段内明写一路沉默、不报「§3 not written」 |
| 普通模式收口 | `thincoder-core/prompts/knowledge/normal-work-management.md` 的评审落档句 | 写的是普通模式收口，与 §4.4 普通模式那一支一致（那条路上结算整段跳过），不是残留 |

为什么写面表与 `§3` 规则要加限定、评审席侧说明不加：前两面住在 `tool-batch.md`，那是全量面的描述——读它的是派单的主 agent，两条轨都读，句子里不带轨，读到的就是「评审席总能有 `§3` 写面」；后一份住在 `tool-batch-review.md`，随评审实例的工具一起发出，读到它的席位手里都有那件工具，在这样一份描述里写「本轨不适用」与手里的工具相矛盾——而设计轨那一路既收不到它，也没有可写的段。

挂载面判「拿不拿得到」（§4.3），说明面判「拿到之后怎么用」，两件事分开写。

为什么 `§3` 规则块里的两句同口径改：它们坐在一份档的同一个块里，说的是同一件事——评审席会 `append` `§3`。只限定前一句，读者读到的是「上一句被限定了、这一句没有」，比两句都没改更难判；同一份档、同一机制的句子按同一口径收窄。

为什么 `persona-engineering.md` 一面写「code track only」而工具描述写「code track and normal mode」：那份档只在工程模式装配（`thincoder-core/prompt-overlays.mjs` 的 `SCENARIO_SLOT_FILES` 把 `persona-engineering.md` 列在 `engineering` 行，`normal` 行读的是 `persona-normal.md`），普通模式读不到它，故两句在各自读者面前说的是同一件事——限定只切设计轨，没有删掉普通模式。

为什么四份 advisor 提示词的落档段要写「无工具则不写不报」：这四份档是评审席动手前读的最后一段，而它的读者分两轨——同一段文字进到工程设计轨的评审进程里，那里的工具集根本没有批工具（§4.3）。职责句不带这一支，评审席照它去落档，落不成还要报一句「§3 not written」，把一件本来正确的事报成失败。

上表前三面的限定句还须保住原文里仍然成立的规则：代码轨与普通模式上，结论表四列、`VERDICT` 行、计数、「证据格放指针、推理正文不进块」与「轮次戳由工具盖、不自写标题」照旧成立。限定只收窄适用范围，不删这些句子。

### 4.6 文档与结构检查

append/edit 在写盘前执行当前文档检查。close/status→已收口检查本批变更区。

REFUSED 或无法形成有效通过结果时不得写成成功。检查范围按 DOC-CHECK，不另造规则。

### 4.7 不变量

- 段写权不削弱。
- 凭证不落档。
- 工具生成轮次。
- 工程模式设计轨的 `§3` 写者只有结算；代码轨与普通模式的写者是绑定评审席位。
- 状态行只有一个可读值（主动 status 与被动同笔写同一词表、同一段头区）。
- 失败明示。
- 并发批次隔离。
- 改动面按批判：绑定了批档的写记下它服务的批，收口只判本批的档（§4.18.1）。
- 普通模式不获得工程机械门。

### 4.8 验证面

验证段域、绑定、骨架、路径、凭证剥除、轮次、裁定、结算自写轮次块、块内结论表与计数、结算头、状态行、冻结、重开、收口、补关、取代和 check。

### 4.9 状态读取与冻结

段头区内恰一条 `**状态行**：` 才可读。零条或多条均为不可判，不能取首条猜测。

已收口档冻结。状态不可判时写门 fail-closed；修复由主 agent 按当前文档写面执行。

### 4.10 骨架

create 一次写入六段标题、档头、台账与前情行、状态行和合法占位。死占位必须在正常写入前被真实值替换。

`§1` 的状态行骨架写纯「进行中」，不带括注——骨架不产一个没有机制会清的假占位；`§1` 的括注仍由主 agent 人工写。`§2`/`§5` 的状态占位句留着，由 §4.12 的被动写覆盖。

档头台账行支持单行多编号。占位只用于骨架，不能长期充当真实编号。

### 4.11 create

create 需要 path、topic、source，可带 ledger、board、prev、date 或预定指针认领。

它通过批次—台账事务创建或接手工作项，写骨架，再把真实行号与 task_book 绑定。目标已存在时拒绝，不覆盖。

### 4.12 状态行：主动 status 与被动同笔写

`status` 只修改目标段受保护状态行。value 必须属于该段 STATUS_WORDS，note 只作为当前允许的附注。

写入面另有一条被动路：`append`/`edit` 往 `§2` 或 `§5` 写入非空正文，同一笔把该段状态行置成它的完成词——`§2` ⇒ `设计完成`，`§5` ⇒ `实施完成`。词表零扩（两态本就在 `STATUS_WORDS` 里），已是完成词则零写，写被拒则状态行不动。

「非空正文」用现成判空判据：排除空行、标题行、状态行、模板占位与「不适用」行之后仍有正文行（`batch-skeleton.mjs` 的导出面 `sectionContentState`，其排除类即 `EXCLUDED_LINE_RE`）。被动写不按模式分岔——两种模式下 `§2`/`§5` 都是同一台写面。

为什么被动而不靠纪律：状态行是 `§5` 写入门、收口门与核销门的唯一判据面，而「段属主记得回头调 `status`」是纪律，纪律在最忙的那一轮最先漏。`§3` 早就是这样被动写的（`statusPassPlan` 的 `Number(seg) !== 3` 守卫），`§2`/`§5` 挂同一条路。

append/edit 不得引入状态行——被动写是工具自己那一笔，不是正文里的行。edit 可删除非受保护的冗余形态行，但不得让段头区状态行数量增加。

### 4.13 close

close 需要 path、completed、closeEvidence。它先检查链完整性、文档、凭证和工作项，再写已收口并结算。

close 不代写 §6。正常收口、补关和取代有不同前置，不能互相冒充。

### 4.14 路径归属

路径使用 PATH-RESOLUTION 与 batch-paths。读面要求可读，create 要求落在声明基底内并防止二次拼接。

工作区不向下猜项目。显式目标按目标所属项目处理。

### 4.15 引用

批次指针使用可解析文档路径与节名。引用长期规则时指向状态文档，不让状态文档引用批次作为规范来源。

### 4.16 普通模式

普通模式主 agent 折叠设计与实施管理席；绑定 coder 可写 §5。没有工程 designToken、强制 spawn batchDoc 或父侧写门。

评审工具的参数与账链契约仍按评审机制执行。

### 4.17 重开

status 将已收口 §1 改为进行中时必须带 note。工具追加重开记录，并回收允许回收的待核销行。

已核销和已废弃不因此复活。再次收口重新通过完整门。

### 4.18 收口分流

- 正常批：链完整、评审通过、用户批准、验证与完成证据齐全。
- 补关：行集全归档且唯一读数为 open-but-settled；不补造历史段。
- supersede：对象已消失或永不实施，并有真实 successor；结算已完成行，退回其他在途行。

### 4.18.1 本批改动面的取材

档位臂要判的是「**本批**改动面里在盘的码档，§2 有没有它的行」。取材面若混进邻批的档，§2 那张表就从「本批的改动面」变成「窗口里所有批的改动面」，记录会说一件不真的事；两批同工作树并行时，任一方收口都会要求另一方补镜像行。

取材按批判，两腿，判据一在前：

- **判据一 = 写时归属**。记账那一刻「这笔写服务哪一批」在**绑定了批档的 agent 上**是已知的，所以每笔记账除路径之外同时写下它服务的批档——记账面 = `thincoder-core/agent/record-results.mjs` 与 `thincoder-core/agent/turn-loop.mjs` 里那两处 `agent._touchedFiles.push(abs)`，两处都按 `agent` 记、不看深度。
- **绑定只在子代理上有**。`agent._batchDoc` 的唯一赋值点是 spawn：`thincoder-core/agent-tools/subagent-spawn.mjs`「if (batchBound) child._batchDoc = batchDocAbs」；depth-0 主 agent 挂载时为 `null`（`thincoder-core/agent-tools/batch.mjs`「depth-0 主 agent 挂载时 = null——目标走 D-BR21 可选 path / 在飞扫描」）。未绑定的那一笔记路径、不入归属表（`recordAttribution` 对空绑定返回 `false`，不替它猜一个批），收口按本批判（见本文末段边界）。
- **归属表**。载体 = `thincoder-core/agent/batch-attribution.mjs`（纯函数、零 fs、零 import），挂 `agent._batchAttribution`，键 = 批档绝对路径、值 = 该批的绝对路径集。三个导出面：`recordAttribution(agent, paths, batchDoc)` 记账 · `attributedTo(agent, batchDoc)` 取某批的路径集（收口取「归属含本档」的那些）· `mergeAttribution(parent, child)` 并集合入（子代理的归属表随 `mergeChildMutations` 并回父侧，不靠路径再猜）。
- **判据二 = 提交 diff，按认领收窄**。`提交 diff` 是事后从 git 取的，天然没有批次标记；它的作用是兜住不经记账工具写的档（`bash` ∥ `execute` 落盘的档、脚本生成的档）。收窄方式 = 减去**别的批已认领**的档。两源对批档状态的要求不同（见下条）：观测源不看那一批收没收口，计划源只给未收口的批。
- **认领要有观测支撑**。认领两源，性质不同。本会话归属表里别的批档是**观测**：它记的是「那一批写了这一档」这件已发生的事，那一批收口之后这个事实不变，故这一源**不看批档状态**——同会话并行的两批，后收口的一方正是靠它减掉先收口那一方的档。盘上另一份批档的 §2 机读清单只是**计划面**：它声明打算改哪些档，不证明真改了。单凭计划认领，一条永不兑现的计划就能把一档从每一批的判据里摘出去，那正好是静默放过。故清单这一源另加三条：那份批档**可读地未收口**（状态词 = 进行中；状态不可读的按冻结处置，不给认领权）、该档确在**那份批档自己的**批起 sha..HEAD 之内（`baseShaOf` 取那份批档的批起 sha，`committedDocs` 给档清单），且那份批档与本次收口**同项目根**（路径按仓根相对归一后再比，win32 再折大小写）——跨项目同名的相对路径不认领。
- **认领的抽取面**。清单这一源须归到**具体那份批档**：认领要它自己的批起 sha，跨批合并后的路径集给不出这一条。两个面各取各的：批档目录 = `batchDirs`（`thincoder-core/doc-check/existence.mjs`）；机读清单行 = `machineListRowsOf`（`thincoder-core/agent-tools/batch-segment-vocab.mjs`，与档位门同一个解析面）。`existence.mjs` 另导出 `plannedPathsOf`，那是**跨批并集**，给不出「哪一份批档列了哪一档」。
- **两腿相反时判据一说了算**。同一档在归属表里属本档、又被邻批认领 ⇒ 本批的，判：一条直接的写记录不被另一个批的计划推翻。归属表里没有它、认领成立 ⇒ 不判，只报。两腿都不说话 ⇒ 本批的，判（认领不成立就当它是本批的，fail-closed）。
- **被别的批认领的档只报不判**：不判读数，但回执里留一行 `[changed surface]` 点名它们，请人确认「是否本批」。判据收窄了，这件事仍然看得见。

`agent._touchedFiles` 的形状不动（读者有 `recent_changes`、`verify`、子代理调度、审计块多处），归属记在它旁边那张表上。

`[changed surface]` 的承载面 = 收口那一笔返回给调用方的回执文本，与 `[doc-check gate]` ∥ `[ledger reanchor]` 同面：`batch-lifecycle.mjs` 的 `close` 与 `status → 已收口` 两条回执串各内联一行，串由 `batch-closeout.mjs` 出。读者 = 收口这一笔的调用者，他正是决定「这些档算不算本批」的人。不写进批档、不进台账：它不是规范，是一次收口的读数。

归属只能从记账面取：`thincoder-core/agent/record-results.mjs`「if (!agent._touchedFiles.includes(abs)) agent._touchedFiles.push(abs)」按 `agent` 记、不看深度。

三个面——归属表、认领表、改动面条目——共用一把比较键：`surfaceKey`（`resolve` 后统一 `/` 分隔符，win32 折小写）。归一不做在记账面：`thincoder-core/agent/batch-attribution.mjs` 只存放原值、不持第二把尺（「路径只做**存放**，不在这里归一」），收口那一笔才归一——`selfAttributedOf` 取 `attributedTo` 的原值，再按归一键补一遍。

子代理那一笔记在它自己的 `agent` 上，再由 `thincoder-core/agent-tools/subagent-async.mjs` 的 `mergeChildMutations` 并回父侧：同一笔里走「for (const abs of merged) if (!parent._touchedFiles.includes(abs)) parent._touchedFiles.push(abs)」并路径，也走 `mergeAttribution(parent, child)` 并归属表。

写门不提供这条信息：`thincoder-core/agent/write-gate-ledger.mjs`「if (!(depth === 0)) return null // 子代理走既有 token 门」。子代理的绑定来自 spawn：`thincoder-core/agent-tools/subagent-spawn.mjs`「if (batchBound) child._batchDoc = batchDocAbs」。

三个方向各自的静默失效面（取舍的依据就在这里）：

| 方向 | 判据 | 在什么情况下会静默放过一个真的漏登记 |
|---|---|---|
| 甲 只按写时归属 | 归属表 | 不经记账工具写的码档（`bash` ∥ `execute` 落盘的、脚本生成的）根本不在归属表里，门看不见它们 |
| 乙 清单即契约 | 只判 §2 清单内的档 | 漏登记且该档没进改动面时永远不报——门不再主动发现漏登记 |
| 丙 只按 diff 提示 | diff 只提示 | 跨会话并行时，别的会话的批不在本会话归属表里，而 diff 又只作提示，它改的档两边都不判 |

故选甲 + 丙的组合：归属作判据（唯一带「归属」这个事实的来源），diff 作兜底再按认领收窄、余下的照判。乙的发现能力不能削。

边界：

- 不改档位门第三列与批起基线的比对规则（那是读数基准，另一件事）。
- 不改 §2 机读清单的三列语义。
- 不改写门的拒绝行为与报文（它仍要求 `ledger:"#N"`）。
- `baseShaOf` 返回 `null` 时 diff 腿不启动：判据 = 归属 + 认领，diff 腿不贡献条目。
- 记账时没有绑定批档的路径（`agent._batchDoc` 为空——depth-0 主 agent 的写、以及不携绑定的子代理）按本批判：它们不入归属表，故邻批收口之后仍会被本批要行。这是 fail-closed 的方向，代价是主 agent 独占写并提交的档会被邻批要一次镜像行。
- 归属表不出会话：它挂在 `agent` 上，随会话结束消失。别的会话开的批所写的档不进本会话归属表，那一批收口之后计划源也不再认领它（计划源只给未收口的批）⇒ 跨会话并行时那一档仍会被要一行镜像行。与上一条是两个缺口：上一条是写入侧没有绑定，这一条是观测面只覆盖本会话。

末两条与「认领不成立就当它是本批的」是同一句话：拿不准就往判的方向倒。

### 4.19 edit

oldText 必须在作者段内精确命中一次。越段、触及受保护状态行、引入新状态行、超过当前大小限制或死占位均拒绝。

edit 改记录不等于追认实现；收口仍需对账 §2、§5 和当前设计。

### 4.20 指针形态

证据指针使用节号、符号名或逐字锚。行号不作为持久坐标。

### 4.21 状态行与 attach

状态行值由三条路写入：status/close/reopen 等生命周期动作；append/edit 对 `§2`/`§5` 的被动同笔写（§4.12）；`§3` 随带裁定行的追加同笔置位或重置（`statusPassPlan` ∥ `statusResetPlan`，§4.4）。其他文本通道只能减少冗余形态行，不能产生第二个可读值。

attach 给现有在途批次补挂新工作项。需要新 title，并更新档头编号列表。已收口档先合法重开或另起新批。

### 4.22 评审绑定

工程模式的设计轨评审没有批档写面：轮次块由结算写（§4.4）。工程模式的代码轨评审与普通模式评审仍写 `§3`——两条路都没有设计结算可代写。评审在途冻结窗与批档写是不同写路，按 ADVISOR-GUARDS 分别判断。

### 4.23 评审通过与凭证

设计评审结算判 pass 时，工具保证 §3 状态行与凭证签发一致。轮次块与状态行进同一笔写：写档或凭证持久化失败时一并回写写前原文，不留有块无凭证的假授权。

代码评审不签设计凭证。

## 5. 行为与生命周期

### 5.1 批次边界

交付目标、阶段或条目集变化时另起批次。单档过长是拆分信号，不在状态文档保存具体行数。

评审没有机械轮次上限；持续同一失败时停下上报。修复轮复用设计与凭证。

### 5.2 条目在别处完成

工作证据写进台账 evidence。锚批仍需收口；补关和取代不能伪造实施或评审记录。

### 5.3 §6 收口

§6 记录验证、文档对账、新债、用户确认和实际结算。没有文档改动时如实说明，不写虚假的 gate 通过。

### 5.4 落地核对

实施发现设计不成立时，修代码或走设计变更。不得把计划句留在状态文档后再以“陈旧”解释冲突。

## 6. 多端

core 提供同一工具与规则。端侧只负责宿主会话、权限和界面，不维护另一份批次状态机或段写权。

## 7. 关键决策

| # | 决策 | 理由 |
|---|---|---|
| D-BR1 | 路径由声明与参数决定 | 可移植 |
| D-BR2 | spawn 检查 batchDoc 存在与可读 | 内容质量由执行者与评审负责 |
| D-BR4 | 子代理路径来自绑定 | 语法上避免写别批 |
| D-BR7 | 工具剥凭证 | 不能依赖模型记得 |
| D-BR19 | 状态词分段单源 | 防止骨架与门漂移 |
| D-BR21 | depth-0 可显式 path | 多批在飞时需要定位 |
| D-BR26 | 段域模式感知 | 普通模式席位不同 |
| D-BR33 | 作者可 edit 自己段 | 修正引用和记录不能被迫只追加 |
| D-BR38 | §3 轮次块只承载本轮结论表、裁定行与计数，评审的推理正文留在报告里 | 按表头四列认表、按 `severity` 格计数都是结构性取行，不解析自由文本——自由文本会漂，同一条说法不止一处要跟着改；读块的人要的是每条 finding 的处置，独白不是结论 |
| D-BR41 | 状态行值的写者只有工具（模型的 `status` 与正文同笔都由工具落笔，§4.12） | 两个写路同一词表、同一段头区，读侧只有一个可读值，机器读取不必猜 |
| D-BR42 | 现役档用 attach 接新事 | 不复活已核销行 |
| D-BR43 | 正文写入同笔置段完成词（`§2` ⇒ 设计完成 · `§5` ⇒ 实施完成） | 状态行是下游门的唯一判据面，靠段属主记得调 `status` 就是靠纪律 |
| D-BR44 | 改动面取材按批判：绑定时的归属作主判据，提交 diff 只兜底、按别的批的**有观测的**认领收窄（观测源不看批档状态，计划源要求未收口），两腿相反时判据一说了算（§4.18.1） | 会话级触达账与工作树级 diff 都不区分「哪一批改的」，两批并行时任一方收口都要求另一方补镜像行；而归属在绑定时已知。认领要观测，因为邻批的 §2 清单是计划面——计划也能把一档从每一批的判据里摘出去 |

## 8. 边界

不把批次当长期规范，不为普通模式添工程机械门，不做跨仓批档，不用 files 作为授权，不用语义猜测代替状态机。

已冻结档的变更通过重开或新批；需要长期保留的内容进入状态文档。
