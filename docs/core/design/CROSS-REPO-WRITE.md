# 跨仓写权（CROSS-REPO-WRITE）· 设计

> 需求 = `docs/core/requirements/ENGINEERING-MODE-V2-SPEC-CROSS-REPO-WRITE.md`。
> 声明与校验 = `docs/core/design/MANIFEST.md`；目标写面 = `docs/core/design/PORTABILITY.md` §4。
> 勘察证据：已核 `thincoder-core/agent/write-gate-ledger.mjs` 的 `ledgerBindWriteConflict`、`declaredWritableRoots`、表外与表不可读拒文、execute 的 fallbackDeclared 接线。

## 1. 做法与理由

发起方项目在 `index.writableRepos` 中声明可写目录。调用显式携带该项目的 project 和在途 ledger 行后，写门可以改用发起方工作项验证外部目标。

该表只决定写权和记账归属。目标项目的 git 权限仍是实际协作边界。

## 2. 接口契约

### 2.1 声明面

- 键 = `index.writableRepos`，默认空数组。
- 每项是目录，从发起方项目根 resolve。
- 归一复用 `normalizePathList`。
- 非数组由 validateManifest 拒绝；元素由归一规则处理。
- `declaredWritableRoots(cwd)` 返回去重保序的绝对目录集。
- 目标与声明根按路径同一性比较，恰等或位于其子树内即覆盖。
- 不要求目标是 git 仓，不读取目标的授权配置，不做传递授权。

### 2.2 写门判序

对每个目标分别计算：

- `p`：目标绝对路径。
- `W`：调用显式 project 解析出的有效写方项目。
- `R`：目标自己的项目根。
- `tbl`：W 的 writableRepos 绝对目录集。
- `ok`：W 的 manifest 是否可读且合法。

判序：

1. project 非空但 W 无法有效解析 → 拒绝，不能当成未声明 project。
2. W 有效、ok 且 tbl 覆盖 p → 工作项在 W 上校验。
3. W 有效、R 存在且 R 与 W 不同 → 表外或声明不可读均拒绝，不查 R 的同号行。
4. R 存在且没有 W，或 R=W → 按 R 的当前项目规则处理。
5. R 不存在且 W 有效、ok、tbl 为空 → 才进入既有工作区窄口。
6. R 不存在且 tbl 非空但未覆盖 p，或声明不可读 → 拒绝。
7. 其他情况按既有“无项目拥有目标”规则拒绝。

多目标写入逐个判断，任一拒绝则整笔不执行。

### 2.3 记账归属

- 行号、在途状态和 task_book 在 W 上检查。
- 写方过程记录说明实际外部文件和原因。
- 目标项目台账与批档不被写入。
- 表内目标不豁免缺号、非数字、行不存在或非在途等原有校验。
- 本机制不改变跨仓交付、回滚和核销结构。

### 2.4 面判与门禁

`faceDetail(p)` 使用目标自己的项目归属和 docRoot：

| 目标情况 | 面结果 |
|---|---|
| 位于目标项目声明文档根 | doc-root |
| 位于项目内其他位置 | product |
| 目标祖先链无 manifest | out-of-jurisdiction |
| 目标恰为当前项目 manifest 本体 | manifest-state |

writableRepos 只改变工作项在哪本账上检查，不改变 face、设计令牌或其他工程约束。

写方 manifest 不可读影响授权表；目标 manifest 不可读影响目标面判定。两者是不同失败，不共用原因。

### 2.5 工具与提示词

manifest 工具描述必须解释读名单与写名单的区别，以及表内写入使用哪本项目账。

工程提示词必须要求显式 project、写方在途号和表内目标。不得让子代理把 files 调度清单当作授权边界。

`manifest` 工具本身不进入本写门；其 target、init、write 规则由 MANIFEST 工具契约执行。

## 3. 失败语义

| 失败 | 必须指出 |
|---|---|
| project 无效 | 声明项目无法自证 |
| 外部项目表外 | writableRepos 未覆盖目标 |
| 无根目标未被非空表覆盖 | 工作区窄口不适用 |
| 写方 manifest 不可用 | 无法读取 writableRepos，不等于空表 |
| 行号无效 | 当前工作项行规则 |
| 目标为产品面 | 设计门仍适用 |

不得把“读不到”写成“没有声明”，也不得列出无法读取的在途行清单。

## 4. 关键决策

| # | 决策 | 理由 |
|---|---|---|
| KD-X2 | 写方声明，而非目标反向授权 | 保持单向、明确、可执行的写权来源 |
| KD-X3 | 目录前缀包含 | 支持非仓目录，避免仓库识别改变授权 |
| KD-X4 | publicRepos 与 writableRepos 不互派 | 读和写是不同授权面 |
| KD-X6 | 面判使用目标项目声明 | 授权与目标业务分类是正交问题 |
| KD-X8 | 表外不回落目标同号行 | 项目各自编号，同号不是授权 |
| KD-X9 | 空表才允许既有工作区窄口 | 非空表必须真实覆盖目标 |
| KD-X11 | 文件写入与 execute 使用同一判序 | 不给另一入口留下回落路径 |
| KD-X12 | project 无效直接拒绝 | 防止无效声明静默退化成无 project |
| KD-X13 | 声明不可读不是空表 | 未知授权不能当成明确无授权 |

## 5. 验收对照

- 表内、表外、同项目、嵌套项目、无根目标分别验证。
- 目标项目存在同号在途行时，表外仍必须拒绝。
- 只有 publicRepos 时必须拒绝写入。
- 表不可读与空表的输出和结果不同。
- 写方与目标 manifest 失败分别验证。
- 文件写入和 execute 都验证副作用未发生。
- 目标文档面与产品面按目标项目规则验证。

## 6. 行为矩阵

| 场景 | 预期 |
|---|---|
| 表内外部目录 + 有效 project + 在途号 | 允许，使用写方账 |
| 表外另一项目 | 拒绝 |
| 同项目目标 | 按同项目规则 |
| 只有读名单 | 拒绝写入 |
| 声明 B 后写 C | 拒绝 |
| 无根目标 + 可读空表 | 按既有窄口 |
| 无根目标 + 非空表未覆盖 | 拒绝 |
| 写方 manifest 不可用 | 明确拒绝 |

## 7. 边界

不做目标反向许可、目标仓记账、仓库识别、依赖环检测或跨仓批次结构改造。不改变 publicRepos 语义。

## 8. UI / 交互

没有独立 UI。拒绝消息必须指出是 project、声明覆盖、声明可读性、工作项还是目标面失败，并给出对应下一步。

## 9. 集成场景

常驻集成只覆盖真实用户入口：跨目录文件写入、execute 工作目录、工作区无根目标和目标项目面判。

具体新增、修改或删除由当前业务 delta 与 RTM 决定，历史增量和用例编号不住本档。
