# 测试基建（TESTING）· 设计

> 需求层 = `docs/core/requirements/TESTING.md`。本档描述当前测试分层、执行入口、生命周期、runner、散文锚边界和 RTM。
> 最近先例：`docs/core/design/DOC-CHECK.md` 的「判据—调用面—实现落点」组织。对齐 = 当前机制与实现坐标分层；偏离 = 测试文档不保存用例施工表和一次运行读数。
> 勘察证据：已读需求的分层与寿命规则、仓根 `test/run.mjs` 的入口约定、批次单元测试门的实现坐标。相关 = 当前测试契约；外部公共源只用于术语定义。

## 1. 分层纪律与测试门

### 1.1 分层纪律

| 面 | 时机 | 内容 | 执行者 |
|---|---|---|---|
| 改动内 | 实施与修正时 | 只跑本任务相关的单元测试档或子集 | 实施者 |
| 链终收口 | 收口或发布时 | 运行适用前端的集成测试集 | 父侧 |
| 单文件调试 | 需要定位单个用例时 | `node --test <档>` 直接运行 | 当前开发者 |

未执行集成测试时，报告必须携带需求 F2 的原句。`verify` 只接收验证声明，不代跑测试。

工作树含其他改动时，零回归只能按同一命令的前后增量判断，不把他人既有失败算成本次回归，也不把未运行的集合写成全绿。

### 1.2 slow 标注

`thincoder-cli/test/slow.mjs` 将 `slow` 导出为 `test` 的纯别名。它不跳过用例，也不切换执行集合。

仓根 `node test/run.mjs` 是集成测试入口。批次单元测试通过 `node --test docs/batches/<档>.test.mjs` 直接运行，不进入仓根集成收集面。

各包自己的测试入口必须遵守其当前包契约；没有集成集或没有用例时不得把空集呈现为通过。包的发布钩和 CI 入口按各自 package 配置执行，不借用批次单元测试。

### 1.3 判据与读数

- 判据必须能够在正确实现上通过。判据与事实冲突时，先检查判据，不为凑绿修改正确行为。
- 判断既有内容前先问它现在是否仍为真，不以“可以不动”为保留理由。
- 读数必须能指出测量者和测量时刻；旧读数不能自动作为新工作的判据。
- 状态文档写关系、规则和阈值，不写一次扫描的绝对读数。
- 需求回答要什么，设计回答当前如何实现，过程载体回答某一轮实际运行了什么。

| 文档类 | 应包含 | 不应包含 |
|---|---|---|
| 需求 | 业务规则、边界、验收关系 | 一次读数、实现步骤、变更史 |
| 设计 | 当前机制、理由、判据、文件与符号坐标 | 施工清单、一次读数、用例迁移记录 |
| 过程记录 | 当轮命令、结果、试错和证据 | 需要长期独立存在的规则正本 |
| 提示词 | 当前执行规则和必要理由 | 依赖外部文档才能理解的规则引用 |

## 2. 测试库存治理

单元测试是批次本地文件，用毕即删，不进入常驻集合。集成测试按业务或生产来源常驻于仓根 `test/integration/`。真实端点 smoke 独立手工运行，不混入自动集成入口。

重构迁移保持断言语义和数量；存量清理由明确的删除清单授权。两种工作不使用同一计数规则。

### 2.1 防膨胀机制

| 约束 | 实现 |
|---|---|
| 单元不累积 | 批次目录、用毕即删、零常驻收集 |
| 集成有上限 | 仓根常驻集、业务来源审查、规模窗口 |
| 成本按失败代价 | 新增场景必须对应真实业务或生产问题 |

规模窗口是纪律约束，不新增独立计数服务。收口记录中给出当次实际读数。

### 2.2 单元测试的模块解析

批次单元测试经 `@thincoder/*` 消费共享包时，必须使用与产品消费面相同的链接或物化路径。不得一边从仓根兄弟目录直取，一边从包名取件后做 `instanceof`、单例或注入缝比较。

需要验证两个路径指向同一文件时，使用 canonical realpath；跨路实例相等不是有效判据。Windows junction 由 `scripts/dev-link.mjs` 产生，机制见 `docs/core/design/CORE-UNIFICATION.md`。

### 2.3 入口与空集语义

仓根集成入口只收集 `test/integration/` 的集成用例。批次单元测试不进入该集合。

包级入口可以是包内检查器或空集说明器，但不得把没有执行任何用例报告为通过。包级入口的实际行为由各自 runner 和 package 配置决定；本档不维护一次盘点的结果表。

### 2.4 单元测试为什么住批次目录

批次收口门只在批档所在目录识别本批单元测试文件。文件住错目录或名称无法关联批档时，收口门无法正确履行零留存检查。

包内测试目录有自己的收集和错位检查。临时批次文件放入这些目录会污染包级收集面。因此，批次目录同时是生命周期归属和执行边界的载体。

## 3. 测试生命周期

技法、来源和执行时机是三件不同的事：单元与集成是技法；业务与生产是集成来源；改动内与收口是执行时机。不得因为文件位置或运行命令相同就混为一层。

### 3.1 来源与寿命

| 层 | 落地物 | 来源 | 寿命 |
|---|---|---|---|
| 单元 | 批次目录中的测试档 | 当前开发改动 | 用毕即删，不进常驻集合 |
| 集成·业务 | `test/integration/` | 真实业务场景 | 常驻并进入发布验收 |
| 集成·生产 | `test/integration/` | 真实生产问题 | 常驻并进入发布验收 |

### 3.2 两层界线

单元与集成永不互转。需要长期验收时，从业务入口重新定义集成场景，而不是保留或改写批次单元测试。

### 3.3 收口测试记录

收口记录中的测试项包含：

1. 本批单元测试文件的清理结果和当次运行证据。
2. 集成场景是新增、修订还是无变化，以及原因。
3. 当前集成集规模与窗口的关系。

该记录由主 agent 负责，内容和实现引用必须能对应当前设计与实际文件。

### 3.4 演进与生产收编

需求变化、业务行为变化或发布前评估都可能触发集成集调整。主 agent 判断是否触及既有业务场景，以及是否出现需要长期保留的新场景。

生产问题处理后，只有具备持续业务验收价值的部分才转成集成场景。单纯内部实现变化不产生集成用例。

### 3.5 零留存收口门

`thincoder-core/agent-tools/batch-unit-test-gate.mjs` 提供：

- `batchUnitTestFiles(abs)`：识别属于指定批档且仍在盘的单元测试文件。
- `assertUnitTestFilesCleared(abs, action)`：存在此类文件时拒绝收口。

归属规则：

1. 候选集是批档同目录下的 `.test.mjs` 文件。
2. 以批档文件名前缀判断归属；多个批档前缀都匹配时取最长者。
3. 只检查当前批档拥有的文件，不扫其他批档或无主文件。

`batch close` 和 `status → 已收口` 都执行此门，且位于文档机械检查之前。目录无法读取时同样拒绝，因为无法确定是否仍有文件不等于已经清空。

拒绝时点名文件和删除要求，不自动删除。实现调用点位于 `thincoder-core/agent-tools/batch-lifecycle.mjs` 的 `statusBatchRecord` 与 `closeBatchRecord`。
## 4. 集成测试集：承载、执行与发布门

集成测试集位于仓根 `test/integration/`，覆盖 CLI、VSC 和 Desktop 的用户可见业务。core 与 render-core 不另设集成集，由前端场景经过共享实现。

### 4.1 承载

集成用例按场景文件组织，目录本身就是收集边界。临时单元测试、helper 和 fixture 不依赖人工标记来躲避收集，而由位置和命名约定区分。

### 4.2 runner

仓根 `test/run.mjs` 收集 `test/integration/*.test.mjs` 并交给 Node 测试运行器。它不收嵌套目录，也不收批次单元测试。

### 4.3 接口契约

| 项 | 取值 |
|---|---|
| 目录 | 仓根 `test/integration/` |
| 文件命名 | `<场景名>.test.mjs` |
| 收集 | 单层 glob，不收第二层 |
| 入口 | 仓根 `node test/run.mjs` |
| 单元调试 | `node --test <档>`，不经集成入口 |
| 发布接线 | `thincoder-cli/scripts/release-check.mjs` |
| 不变量 | 收集面反查、软链目录拒绝、空集非零 |

### 4.4 多端场景

同一业务场景在各端从真实入口实例化。驱动方式可以不同：CLI 可使用真子进程，VSC 可使用扩展宿主替身，Desktop 使用 `docs/desktop/design/E2E-TESTING.md` 的驱动与隔离机制。

语义一致不要求源码逐字相同。端差涉及业务语义时必须显式消解，不用镜像复制掩盖。

### 4.5 覆盖划分

单元测试可以断言内部实现；集成测试只断言业务可观察结果。集成测试可以读取状态文件、产物或机械判定旗位，但不锁私有实现形状。

同一断言不在单元与集成两层重复持有，集成用例不由单元测试改写。

### 4.6 用例收尾

`test/teardown.mjs` 的 `removeTempDirBestEffort(p, opts)` 是集成用例的共用清理助手，支持目录和单文件。

清理采用尽力面：有界重试后仍失败时，向 stderr 写出一行包含绝对路径和错误码的信息并返回 `false`，不抛出以改变业务断言结果。

该兜底只改变清理失败的表现，不改变业务判定。清理失败必须可见，不能静默吞掉，也不能把用例改为 skip。

### 4.7 用例隔离

每条用例拥有自己需要的临时 HOME、cwd、端口、子进程或设备会话。执行顺序和并发方式不得改变业务结论。

需要共享的只读 fixture 可以复用；可写状态、运行句柄和临时目录不得成为跨用例隐式输入。浏览器或终端 profile 的隔离按其驱动文档执行。

## 5. 集成场景基线

集成集至少考虑以下真实业务面；实际用例只从当前业务需要和生产问题中设立：

| 场景 | 正常 | 边界 | 错误 |
|---|---|---|---|
| 普通模式完整工具流 | 从用户输入完成读取、修改和验证 | 纯文档改动走文档检查路径 | 代码改动验证失败时不得完成 |
| 工程模式全链 | 评审、凭证、spawn、消费链闭合 | 同设计修正复用规则 | 无凭证或已消费后不得继续 spawn |
| 子代理生命周期 | 异步执行、报告送达、池清理 | 文件冲突排队 | 取消后无孤儿和残留状态 |
| 会话恢复 | 重载后历史和计数连续 | 中断后的已知前缀保留 | 损坏会话不导致崩溃 |
| TUI 或面板基本盘 | 输入提交并进入 agent 循环 | 审批与提问回调正确 | 退出时清理资源 |
| commit 与验证 | 只提交目标文件 | 跳过验证必须有理由 | 验证失败必须拒绝完成 |
| 配置与 provider | 请求到达所选本地替身 | 不存在的 provider 明确报错 | 坏配置提供可读诊断 |

### 5.1 最小起步

普通模式完整工具流是必选场景。每个适用端都要覆盖正常、边界和错误；某端结构性不适用时，必须在 RTM 说明，而不是生成空通过项。

新增场景继续遵守业务或生产来源，不从单元测试库存扩展。
## 6. 散文锚禁令（PROSE-ANCHOR-RETIRE）

### 6.1 判定与分类

散文锚同时满足：对象是非测试文件文本；断言其内容、次数或顺序；对象不属于明确的结构或行为保留面。

| 类别 | 判定 |
|---|---|
| 执行产物 | 函数返回、工具返回、子进程输出和渲染帧属于行为面 |
| 静态文本 | 直接读取或 import 非测试文件中的文案属于文本面 |
| 提示词 | 断言提示词句子属于文本面，装配结果不豁免 |
| 工具契约 | 模型实际收到的工具描述和参数说明属于契约面 |
| 结构与数值 | 集合、成员、长度、旗位和退出码属于结构或行为面 |
| 产品资源 | locales 文案按产品行为处理 |
| 测试文件 | 测试自己的 helper、fixture 和常量不是非测试文件文本 |

分类只使用三种结果：保留、改写为行为断言、移除。分类依据必须指出实际被断言的对象，不能只按搜索关键词决定。

### 6.2 修改纪律

混合用例只处理文本锚部分，保留行为断言。验收描述和引用同步更新。删除或改写后运行相关测试，证明保留面仍然有效。

文本清理不以用例数量变化作为目标，也不要求保留一份历史行号清单。需要审计时，以当前 diff 和实际测试结果为准。

### 6.3 新增禁令

新增测试只写业务可观察结果、执行产物、工具契约或结构自洽。不要把需求或提示词中的一句话复制成测试中的固定 needle。

子进程输出、协议帧和工具返回文案可以是行为契约；它们与读取文档句子不是同一类对象。

### 6.4 边界

本规则不改变 `doc_check` 的判据，不要求修改台账内容，不改变 slow 标注，也不授权删除无关行为测试。

## 7. 验收标准

| 面 | 必须证明的结果 | 需求回指 |
|---|---|---|
| 分层与执行 | 改动内运行相关单元测试；收口或发布由父侧运行集成测试 | F1–F5 |
| 生命周期 | 单元测试用毕即删；集成场景按业务或生产来源常驻 | F6–F11 |
| 集成入口 | 正常执行目标集合，错位文件与空集均不会被误报为通过 | F12–F14 · N20 |
| 收尾与隔离 | 清理失败可见且不改变业务结果；用例不共享可写状态 | F27 |
| 散文锚 | 新测试不锁非测试文件措辞，混合用例不丢失行为断言 | F15–F22 |
| 判据与读数 | 判据能在正确实现上通过，状态文档不携带一次读数 | F34 |
| RTM | 故事、用例、证据和覆盖状态可以相互定位 | F29–F33 |

验收不能只检查规则文本是否在盘。必须运行相应行为或结构验证；未运行时明确报告未验证。

## 8. 边界

- 不把真实付费端点放入自动集成测试。
- 不为集成测试另建平行 runner。
- 不把批次单元测试接入常驻门。
- 不把内部模块交互自动当成项目级集成场景。
- 不以文本搜索命中代替业务行为验证。
## 10. 测试入口与门禁

测试入口按当前分层提供单一职责：仓根入口运行集成测试，批次单元测试由 `node --test <档>` 直达。慢用例标注不改变执行集合。

`lint` 或语法检查是独立门面，不冒充测试。包的发布钩和 CI 按各自契约调用语法检查或集成入口。

### 10.1 清单与在盘检查

使用显式清单的包必须保证清单条目在盘。清单失效时在启动测试前失败，并指出缺失文件。

清单检查与收集机制是两个维度：显式清单包检查登记关系，glob 收集包检查文件是否落在实际收集面。两者都不能让未执行文件静默存在。

### 10.2 收集面反向自检

runner 在启动测试前递归检查自己的 `test/` 树：

1. 每个测试文件必须属于该 runner 的实际收集面。
2. 收集面外的测试文件导致非零退出。
3. 软链目录无法被收集面可靠覆盖时明确拒绝，不静默漏跑。
4. helper、fixture 和 smoke 文件通过命名与测试用例区分，不建立逐文件豁免清单。
5. 自检失败发生在测试启动前，不输出看似已经执行的通过记录。

仓根、CLI 和 core 的共用失败前缀为 `✖ test manifest check failed: `。具体失败原因分别指出未收集文件或软链目录。

### 10.3 执行层与空集

| 面 | 当前行为 |
|---|---|
| 仓根 `test/run.mjs` | 收集 `test/integration/` 单层用例；收集面外文件或空集均非零退出 |
| CLI `test/run.mjs` | 不执行集成用例；检查错位文件，并非零退出且指向仓根入口 |
| core `test/run.mjs` | 无集成目标集合；检查错位文件，并非零退出且说明 N20 |
| 批次单元测试 | 不进入以上集成入口，使用单文件直达 |
| VSC、Desktop、render-core | 按各自包级 runner 契约执行；空集不得被表述为已经验证 |

空集非零不是产品发布门本身永远失败。没有集成职责的包可以使用独立语法门，但其测试入口不得声称空集已经通过验证。

验收至少覆盖：正常收集、错位文件、软链目录、空集、单文件直达，以及包级语法门与测试门的区别。
## 11. UAT 验收总表（RTM）

RTM 是交付侧的验收文档。它记录业务故事、集成用例、异常和签署，不记录批次内部单元测试。

### 11.1 方案与理由

全仓持有一个索引和能力族分册。一个故事只在一个分册中出现，一个集成用例只占一行。

证据直接指向可复跑的 `test/integration/` 用例。RTM 随代码进入 git，不依赖可删除的过程记录。

### 11.2 落点、命名与份数

| 项 | 约定 |
|---|---|
| 索引 | `test/RTM.md` |
| 分册 | `test/rtm/<族>.md` |
| 标题 | UAT 验收总表（RTM） |
| 签署面 | 只在索引中保留一份 |
| 异常与更正 | 只在索引中保留一份 |

RTM 文件进入适用的文档检查清单。表行不为了缩短而删除验收断言；内容需要缩短时应重写措辞，而不是损失判据。

### 11.3 故事与用例结构

一个 H2 是一个业务故事，标题形为 `<端名> <故事号>. <故事名>`。故事节内只有一张用例表。

| 列 | 内容 |
|---|---|
| 编号 | `<端名> <故事号>-<用例号>` |
| 怎么做 | 从用户可见入口开始的业务操作步骤 |
| 怎么算通过 | 可观察、可复核的通过条件 |
| 异常 | `无` 或索引中的异常编号 |
| 证据 | 集成用例文件路径；尚未落地时写 `未落（用例待补）` |

不在每行手抄执行日期、执行人或结果。一次交付的实际结果来自当次测试运行和签署记录。skip 与未运行不算通过。

### 11.4 与集成用例的双向对应

- 故事节回指需求条目和业务故事。
- 证据列指向 `test/integration/<场景名>.test.mjs`。
- 用例标题以完整 RTM 编号开头。
- 先确定编号，再写入用例标题。
- 待补行没有证据文件时保持待补，不伪造路径或通过状态。
- 同一用例不在多个故事或分册中重复登记。

### 11.5 签署面

签署面包含产品标识、结论声明、验收方、供方、日期和页码。签署顺序为：运行适用集成集、核对 RTM、冻结正文、形成签字版、双方签署、归档签署版本。

签署后不改既有正文。更正通过索引的「异常与更正」追加新行，记录异常、严重程度、纠正日期、纠正者和再测结果。

### 11.6 一致性约束

| 约束 | 当前解法 |
|---|---|
| 过程记录可清理，交付物需长期存在 | RTM 住 `test/` 并进入 git，不引用批档 |
| 单元测试零留存，验收报告常驻 | 两者分开：内部开发证据与外部验收交付物 |
| core 不设独立集成集 | core 能力通过前端业务故事覆盖，证据仍在仓根集成用例 |

### 11.7 标准使用边界

RTM 字段参考公开测试文档标准中的用例标识、步骤、预期结果、通过判据、异常和证据概念。标准仅作结构参考，本项目不因此声称符合性认证。

未实际读取的标准条款不作为依据。当前项目选择五列用例表，并通过签署面承载一次交付的执行结论。

### 11.9 关键决策

- 一个故事一张表，一个用例一行。
- 索引与分册按能力族组织，端进入编号和覆盖矩阵。
- 证据指向可复跑用例，不用人工填写的行内状态替代运行。
- 签署后只能追加更正。
- 待补和缺是不同状态，均不能写成已通过。

### 11.10 验收标准

| 面 | 验收 |
|---|---|
| 结构 | 索引、分册、故事标题和五列表符合当前约定 |
| 追溯 | 索引故事与分册故事一一对应；用例行与标题按编号对应 |
| 证据 | 文件路径存在，或明确标为待补 |
| 覆盖 | 矩阵正确区分有、待补、缺 |
| 签署 | 签署面唯一，签后更正只追加 |
| 检查 | 适用文档通过 `doc_check`，语义关系另行人工复核 |

### 11.11 正常、边界与错误

- 正常：故事和用例按编号双向定位，证据可复跑。
- 边界：故事暂时没有某端用例时，矩阵明确写缺或待补。
- 错误：缺少通过条件、重复归册、索引登记用例正文、签后改行均不合格。

### 11.12 当前约定

RTM 采用仓根单索引、能力族分册和单一签署面。默认使用中文业务语言；多语言交付物需要独立需求。

RTM 不设置质量特性等额外列。若验收方要求增加字段，应先变更当前契约，再全量同步结构。

### 11.13 术语

| 词 | 含义 |
|---|---|
| RTM | Requirements Traceability Matrix；本项目用于 UAT 验收总表 |
| 业务故事 | 用户从产品入口完成的一件可验收事项 |
| 用例 | 一个可执行、可判定结果的集成验收场景 |
| 证据 | 对应用例文件及实际运行结果 |
| 待补 | 用例行已登记，但集成用例尚未落地 |
| 缺 | 该端没有此故事的集成用例 |

### 11.14 边界

- 不改变集成 runner 和测试分层。
- 不把 RTM 变成自动签署或机检系统。
- 不引用批档作为长期证据。
- 不以单元测试代替集成用例。
- 不在设计档复制当前故事清单。

### 11.15 设计时的 RTM delta

每次业务改动先读索引和相关分册，再回答：

| # | 问题 | 动作 |
|---|---|---|
| D-1 | 哪些既有行业务结果发生变化 | 修订步骤或通过条件，编号不变 |
| D-2 | 哪些行已经冗余 | 经业务判断删除行和对应冗余用例 |
| D-3 | 缺哪些真实业务场景 | 先定编号，再建立用例和证据行 |

三项均不成立时，明确写业务行为未变及理由。编号只增不复用，删除的编号不回收。

### 11.16 证据与编号一致性

对账至少检查：

1. 分册用例编号集合与用例标题编号集合一致。
2. 编号没有重复。
3. 证据文件与标题所在文件一致。
4. 用例表保持五列。
5. 待补行单独列出，不计入已有证据。
6. 无编号标题作为缺口报告，不自动造号。

这些是关系判据，不在设计档保存一次扫描的绝对数量。

### 11.17 提示词与执行面

设计、评审和收口提示词必须让执行者先读 `test/RTM.md`，再进入相关分册并完成 delta。提示词直接说明要读写的对象，不依赖本设计档的节号才能理解。

集成用例标题示例必须使用完整编号。提示词中的规则变化与当前 RTM 契约同步。

### 11.18 索引与能力族分册

#### 11.18.1 索引

`test/RTM.md` 只包含导读、故事索引、端覆盖矩阵、异常与更正、签署面。用例正文位于分册。

索引故事号 = `<端名> <故事号>`；标题与分册故事标题一致；属册值等于分册族名。

矩阵三值：`有` 表示该端有用例证据，`待补` 表示行已登记但用例未落地，`缺` 表示该端没有此故事用例。

#### 11.18.2 分册

每册包含册标题、索引回指和故事节。一个故事只在一册中，册内按故事号稳定排序，不因其他内容调整而重编号。

#### 11.18.3 编号与族归属

编号形 = `<端名> <故事号>-<用例号>`。端名可为单端、已定义的端组合或 `全部`，当前闭集由索引和校验规则共同使用。

| 族 | 机制范围 |
|---|---|
| `guard` | 文档检查、写门、收口门和判定守护 |
| `batch-ledger` | 批档、台账、评审和凭证 |
| `tooling` | 工具实现与工具结果回路 |
| `loop` | 会话环、provider、压缩、断流和后台投递 |
| `paths` | 路径、工作区和项目根解析 |
| `ends` | 主题本身是端能力或呈现差异的故事 |
| `testing` | 测试基建；首个真实故事出现时建册 |

归册看断言守护的机制，不看它碰巧在哪端运行。

#### 11.18.4 三条纪律

1. 跨端同源行为只写一行。
2. 端差通过编号和矩阵显形。
3. 索引始终持端覆盖矩阵，不把空缺藏进分册。

#### 11.18.5 增删与引用

移动或重排不改业务断言。删除编号不回收。册内可以使用短号引用同册行，跨册引用必须带册名；跨端和用例标题使用完整编号。

异常格只写索引中的异常编号，不写易漂移的位置。

#### 11.18.6 与用例的对应

用例标题以完整编号开头。修改编号时同步修改标题前缀，不改业务断言。

没有对应表行的用例标题是缺口；没有证据文件的表行是待补。两者不得互相掩盖。

#### 11.18.7 不按端拆的理由

按端拆会复制同源规则、隐藏其他端的空缺，并让措辞独立演化。能力族分册使规则只有一份，端差只在显式矩阵中表达。

#### 11.18.8 当前分册

当前分册为：

```text
test/rtm/guard.md
test/rtm/batch-ledger.md
test/rtm/tooling.md
test/rtm/loop.md
test/rtm/paths.md
test/rtm/ends.md
```

`testing` 是按需族，没有真实故事时不建空册。新故事先按 §11.18.3 归族，再更新索引和分册。

#### 11.18.9 文件责任

| 文件 | 责任 |
|---|---|
| `test/RTM.md` | 故事索引、矩阵、异常、签署 |
| `test/rtm/<族>.md` | 故事正文和用例行 |
| `test/integration/<场景>.test.mjs` | 可执行用例和带编号标题 |

修改任一文件时同步检查另外两面，不留下单向断链。

#### 11.18.10 验收

- 索引故事集合与分册故事集合一致，零重复。
- 签署面和异常区只位于索引。
- 分册故事标题符合编号形，不按端设节。
- 用例标题以完整编号开头。
- 证据文件存在，或行明确标为待补。
- 传入的索引和分册通过适用文档检查。

#### 11.18.11 正常、边界与错误

正常：新故事只落一个族，索引矩阵同步。

边界：某端用例待补或缺失时，矩阵如实显示。

错误：同一故事进两册、索引塞入用例行、为凑数删行、用例标题无完整编号，均不合格。

#### 11.18.12 与 RTM delta 的关系

结构调整本身不产生新业务场景。涉及现有行业务语义时，按 §11.15 修订；仅改变文件归属或标题编号时，明确记录业务结果未变。

#### 11.18.13 边界

不按端建册，不改五列结构，不自动生成或签署 RTM，不为空缺创建虚假证据，不把 RTM 变成新的测试执行门。
## 12. 仓根集成布局

### 12.1 结构与理由

集成用例、runner 和 RTM 统一位于仓根 `test/`。集成场景可以跨越多个产品包，因此测试码不受生产码的跨包引用限制。

仓根布局：

```text
test/
├── run.mjs
├── teardown.mjs
├── RTM.md
├── rtm/
└── integration/
```

### 12.2 接口契约

| 项 | 当前约定 |
|---|---|
| 收集根 | `test/integration/` 的单层测试文件 |
| 入口 | 从仓根运行 `node test/run.mjs` |
| 包引用 | 仓根没有包解析拓扑时，测试使用仓根相对路径引用产品代码 |
| 自检 | 收集面反查、软链目录拒绝、空集非零 |
| CI | 需要集成验收的工作流从仓根调用同一入口 |
| 发布 | 发布检查调用同一入口，不维护另一套集成命令 |
| RTM | 索引 `test/RTM.md` + 能力族分册 `test/rtm/` |

### 12.3 实现坐标

- 收集与执行：`test/run.mjs`。
- 共用清理：`test/teardown.mjs`。
- CLI 空集说明：`thincoder-cli/test/run.mjs`。
- core 空集说明：`thincoder-core/test/run.mjs`。
- 发布接线：`thincoder-cli/scripts/release-check.mjs`。
- CI 接线：`.github/workflows/test.yml`。

### 12.4 关键决策

- 单一仓根 runner 避免多个包各持一份收集面和 cwd 规则。
- 仓根测试引用采用实际可解析路径，不为测试另建包管理拓扑。
- 包内不保留容易被误认为现役集成入口的空目录。
- RTM 只有一个索引和一个签署面，端覆盖由矩阵和编号表达。

### 12.5 验收

验收必须分别证明：集成目录中的文件被执行；收集面外的测试文件导致失败；空集成集导致非零退出；单文件调试不经过仓根 runner。
## 13. 测试纪律的提示词契约

提示词必须同时携带测试规则和必要理由。只写结论而不写成本与适用边界，会让执行者把一次性规则误读成可商量的偏好。

### 13.1 当前规则

- 单元测试用毕即删，避免临时反馈文件积累成永久维护面。
- 需要长期验收时，判断真实业务或生产场景，不保留单元测试充当集成测试。
- 集成用例只从真实业务需要和真实生产问题产生。
- 跨组件实现变化但没有用户可见结果变化时，不因此新增集成用例。

### 13.2 行为契约

工程、设计、评审和普通模式提示词都要按各自职责表达上述规则：

- 工程与设计面负责单元测试寿命和集成 delta。
- 评审面检查缺失或虚构的集成场景，不要求无业务变化的改动造用例。
- 普通模式遵守同样的分层与来源规则。
- 提示词自身不引用本设计档的节号作为运行期规则来源。

### 13.3 实现坐标

- `thincoder-core/prompts/discipline-engineering.md`
- `thincoder-core/prompts/persona-eng-designer.md`
- `thincoder-core/prompts/advisor-design.md`
- `thincoder-core/prompts/discipline-normal.md`

这些是运行期产品文本。修改规则时同步修改相关文本，但不以文本命中测试代替行为验证。

### 13.4 关键决策

| # | 决策 | 理由 |
|---|---|---|
| KD-T5 | 定义、用例行字段和新增判据分属不同轴 | 把三者混写会让内部组件变化被误判成业务集成场景 |
| KD-T7 | 新集成用例只从业务和生产两个来源产生 | 防止测试数量随想象和代码量膨胀 |

### 13.5 验证

- 阅读四个当前提示词面，确认规则与职责一致。
- 对修改文本运行适用的 `doc_check`。
- 不用提示词句子在场测试作为行为正确的证明。
- 新增或修改业务集成场景时，回到 `test/RTM.md` 核对真实 delta。
