# 单仓多产品（TWO-REPO-MERGE）· 设计

> 需求 = `docs/core/requirements/TWO-REPO-MERGE.md`。
> 最近先例：`PORTABILITY.md` 的项目归属与 `ARCHITECTURE.md` 的 core/端壳边界。对齐 = 单仓不等于无边界。
> 勘察证据：已读当前仓目录、文档地图与 core 架构；相关 = 产品目录、共享核、独立发布与声明式写权。

## 1. 当前布局

仓根包含 thincoder-cli、thincoder-vscode、thincoder-desktop、thincoder-server、render-core、thincoder-core、docs、test 与共享配置。

各产品保持自己的包、发布链与端壳。core 提供可复用业务与工具机制。

## 2. 构建与发布

- CLI 使用自己的 npm 包与发布链。
- VSC 使用自己的扩展包与 VSIX 链。
- Desktop、Server 和其他产品按各自文档发布。
- 仓根集成入口按 TESTING 组合各前端集成面。
- 产品包只依赖自己能打包或动态加载的 core 产物。

## 3. 提示词与共享资源

运行期提示词唯一副本在 thincoder-core/prompts。需要进入不同产品包时，通过当前打包闭包和加载机制提供，不维护第二份手写副本。

缺少硬加载资源时按对应产品规则显式失败，不静默空载。

## 4. 文档与台账

文档地图以 docs/README.md 为入口，产品域文档回答端侧问题，core 文档回答共享机制。

台账按项目根存储在用户数据目录。文档图与台账同库，不放进 git 工作树。

历史批档可清理；长期规则只能住状态文档。

## 5. 项目与外部目录

manifest 发现沿祖先链确定项目根。工作区根不向下猜项目。

index.publicRepos 决定可读与可引用的外部仓；index.writableRepos 决定可写外部目录。两者不能互换。

## 6. 文档检查

doc_check 使用内建三类判据与项目排除声明。旧双仓锚检、行宽脚本和 check-ledger 不构成当前检查面。

RTM 只在真实业务或生产问题需要时增加永久集成场景。

## 7. 关键决策

| # | 决策 | 理由 |
|---|---|---|
| D2 | 产品目录名稳定 | 降低引用与打包成本 |
| D5 | 产品文档分域 | 端侧问题与共享机制分开 |
| D6 | 删除无对象的双仓判据 | 防止旧前提反向生效 |
| D14 | 提示词住 core | 共享语义且可进入产品包 |

## 8. 验证

结构或打包变化时验证对应产品构建、发布闭包、集成测试和文档检查。纯文档治理只运行文档验证并如实说明未跑产品测试。

## 9. 边界

本档不承载 core 统一的产品差异清单，不复制 CORE-UNIFICATION 的演进内容，不保留历史迁移步骤为当前规则。
