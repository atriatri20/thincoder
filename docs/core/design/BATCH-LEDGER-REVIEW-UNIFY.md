# 批档 · 台账 · 评审三链统一（BATCH-LEDGER-REVIEW-UNIFY）· 设计

> 本档只描述三个机制的交界：批次、工作项、评审与凭证。
> 各自正文 = `BATCH-RECORD.md`、`LEDGER.md`、`DESIGN-TOKEN-SETTLEMENT.md`。
> 勘察证据：已读当前三档、PORTABILITY 与 CROSS-REPO-WRITE 的写门契约。相关 = 当前写序和一致性边界。

## 1. 做法与理由

一件工作从开批到核销需要三个载体一致：批次档记录过程，台账行记录工作事实，评审与凭证记录设计授权。

判据尽量来自持久事实和显式参数，不依赖某个进程内的“当前批次”。

## 2. 接口契约

### 2.1 面分类

设计门使用 faceOf，而不是 classifyPath。文档面由目标项目的 docRoot 决定；当前项目 manifest 本体有单独放行格；其余为产品面。

无 manifest 祖先链是出辖，不是第三个面值。

### 2.2 开批与绑定

batch create 将批次与工作项绑定。接手必须指定有效 ledger；新工作需要说明与既有同面项的关系。

档头记录真实行号，行 task_book 指回批次。写档、写指针和状态迁移的逐步顺序与失败恢复见 §2.20。

### 2.3 写锁

工程模式 depth-0 的适用写操作必须携带有效 ledger 行号和可判定的项目。

- 行必须在声明项目的台账中且在途。
- bash、execute 和文件写入使用同一行号规则。
- project 是纯归属声明，不代替 bash 的执行目录。
- execute 的 workdir 才是子进程工作目录。
- git 与 manifest 不进入本写门。
- memory 只有 project 层写入需要该项目归属。
- depth>0 使用自己的角色与凭证约束。

跨仓按 CROSS-REPO-WRITE 的 writableRepos 判序。

### 2.3.1 工作区窄口

目标无项目根时，只有当前工作区窄口条件全部成立才可使用声明项目账。

writableRepos 可读且为空才保留该窄口；非空表必须覆盖目标，不可读不等于空表。

### 2.4 建档即建账

create/attach 共用 ledgerBindBatch 的 SQLite 事务：事务内先准备台账行，再写档，随后把行迁到在途并写 task_book，最后 COMMIT。文件写入与 SQLite 不存在分布式事务；失败清理与半状态恢复见 §2.20。

待核销、已核销、已废弃和指向他批的行不能作为新接手对象。已在目标档头且已在途的合法行允许幂等重放。

### 2.5 评审状态

§3 状态由工具根据当前轮裁定维护。pass 置评审通过，打回重置进行中。

最新轮次必须与状态一致；仅手改状态行不能开启 §5。

### 2.6 实施与关闭门

§5 需要评审通过和最新轮次 pass。正常 close 需要链完整、用户批准、验证和有效 completed/closeEvidence。

批次关闭与凭证消费、工作项结算按同一当前收口链执行。

### 2.7 收口重锚

completed 点名的在途行结算到已核销；既有待核销行一并结算。未点名在途行阻止收口。

待讨论/待设计等待行按 `LEDGER.md` §6.2 改挂条件与复启说明；认账不排期的非活跃行不被机器改写。

### 2.8 状态迁移

唯一迁移表归 LEDGER。本档不另写第二套边集。

### 2.9 工作项证据

closeEvidence 由调用方提供，机器不代写。它追加到结算行 evidence。退回理由来自本次调用，不复用旧证据。

### 2.10 目标写面

faceDetail 的顺序 = 出辖、doc-root、当前项目 manifest、product。分类器 temp/aux/state 不形成写门豁免。

### 2.11 设计凭证

凭证由评审结算签发，绑定 designId、会话和生命周期。缺失、不匹配、过期、已消费均不能实施。

### 2.12 排除与索引

文件遍历排除名单由对应共享模块维护。写门面判定不读取搜索跳过表。

### 2.13 重开回收

重开只回收允许回收的待核销行。归档终态不复活。回收失败时按 §2.20.4 回滚档并抛错。

### 2.14 核销

核销需要工作证据与已收口锚批。评审状态和 token 槽归属不是额外核销条件。

### 2.15 评审绑定

绑定 batchDoc 的评审只写该档 §3。评审在途时，文件工具修改被审文档或批次按 ADVISOR-GUARDS 的冻结窗处理；batch 段写是否进入该面按当前工具契约。

### 2.16 新债与范围

当前任务内的新缺陷应修复或明确入账。范围外猜测不入账。当前任务被事实阻断时停止并上报。

### 2.17 一致性读数

batch check 与收口回执可报告：

- closed-but-open-rows
- closed-but-settling
- open-but-unwritable
- open-but-settled
- pointer-stale
- header-row-missing

读数只报告，不自动修复。补关只接受当前规定条件，不用 consistent 替代实际状态行。

### 2.18 微批

小批仍需真实记录、评审和验证。可以减少无关勘察与重复工作，不能删除状态、凭证、证据或业务门。

### 2.19 冻结窗

评审在途时，被审设计档和绑定批次的文件写入按冻结窗规则处理。批次工具的正常 §3 记录与文件工具修改不是同一通道。

### 2.20 写序与补偿

文件与 SQLite 之间没有跨存储事务。所有生命周期动作先做写前预检。create/attach 在 SQLite 事务内先准备或插入待讨论行，再写档，随后写行状态与批次指针并提交；close/reopen/supersede 先写档、再改账。台账失败必须显式报错并补偿档，补偿也失败时保留可见半状态。

`batch({action:"check"})` 是统一只读恢复入口。它报告 record、行集、档头号集、半状态与出路，不改档或改账。close、reopen、supersede 的回执也必须带同一一致性读数。

#### 2.20.1 create

1. create 在 `BEGIN IMMEDIATE` 后按需 INSERT 一条无 task_book 的待讨论行；接手既有行时不新建该行。
2. 回调用 `wx` 独占创建六段骨架，档头写入真实行号；随后在同一事务把行迁到在途并写 task_book，最后 COMMIT。
3. 台账事务内任一步失败都不提交。只有本笔已经成功创建的档才执行删除清理；写前拒绝和 `EEXIST` 不删除既有档。
4. 删除成功后可修正原因并重试 create。删除失败会留下档头有号、台账无提交行的残档；用 check 的 `header-row-missing` 读出它，人工清理本笔残档后再重试，不得覆盖别人的档。

#### 2.20.2 attach

1. attach 只处理已存在且 §1 为进行中的档。事务开始后按需 INSERT 待讨论行，再把真实行号补进既有档头的台账行，随后迁到在途、写 task_book 并 COMMIT。
2. 行号已在档头且已在途时是幂等零写。已收口、状态不可读、缺档头台账行或行状态不允许时，档和账均不写。
3. 档头已写而台账事务失败时，SQLite 回滚，并用调用开始时的全文回写既有档；回写成功后报错，可修正原因再试。
4. 回写也失败时，档头可能留号而台账无对应提交行。check 以 `header-row-missing` 点名；按拒文删除失效档头号或重跑适用的 attach，不把既有档当新建档删除。

#### 2.20.3 close

1. close 与 status 写 §1 已收口共用收口链。先完成内容、评审、测试档、文档检查、档位和完成清单预检，再消费本批设计凭证；这些步骤失败时档和账均不变。
2. 预检通过后先写 §1 已收口；全归档补关同时追加补关记录。随后执行 `ledgerReanchorBatch`，结算 completed 点名的在途行与既有待核销行，并重锚等待行。
3. 台账事务未提交时，用写前全文回滚档并抛错；回滚成功后可在故障消除后原样重试。
4. 档回滚也失败时，档可能仍为已收口而台账未完成。先用 check 判读：`consistent=true` 表示已经关闭且结算，不重试；不一致时先修账，再按读数重开或完成收口。

#### 2.20.4 reopen

1. 只有 depth-0 主 agent 以 status 把已收口档的 §1 改为进行中，并提供非空单行 note，才触发重开。
2. 档面一次写入状态行与重开记录，再调用 `ledgerReclaimBatch`，把本批待核销行回收到在途；已核销和已废弃终态不复活。
3. 回收事务失败时，用写前全文把档恢复为已收口并抛错；回滚成功后可在台账故障消除后原样重试。
4. 档回滚也失败时，残态是档已开而行仍待核销。check 报 `open-but-unwritable`；先修复台账，再进行其他写入。

#### 2.20.5 supersede

1. supersede 先要求 §1 进行中、台账可读、行集未全归档、§5 为空，并解析出不是本档的已存在取代者。随后跑保留门、完成清单预检和设计凭证消费。
2. 档面先写 §1 已收口（被取代）并追加取代记录，再以 `requireAllInFlight=false` 调用重锚。completed 点名的在途行和既有待核销行结算；未点名在途行退回待讨论，等待行按规则改挂条件。
3. 台账事务未提交时，与 close 共用 `ledgerAfterRecordWrite`，用写前全文回滚档并抛错；成功回滚后可修正原因再试。
4. 回滚也失败时，用 check 区分已经一致关闭与仍有开放行的半状态。后者先修账，再按读数重开或完成收口；不得补写 §3、§4、§6 来伪装未发生的流程。

## 3. 实现归属

| 交界 | 实现面 |
|---|---|
| 开批绑定 | batch-ledger-bind 与 ledger 写核 |
| 写锁 | agent/write-gate* |
| 评审状态 | batch-record-write 与 design-token |
| 收口 | batch-lifecycle、batch-closeout、ledgerReanchorBatch |
| 重开 | batch-reopen 与 ledgerReclaimBatch |
| 一致性 | batch-ledger-view 与 batch check |

具体函数和参数以当前代码与工具描述为准。

## 4. 关键决策

| # | 决策 | 理由 |
|---|---|---|
| U1 | 用显式批次和项目参数 | 避免运行态当前值串批 |
| U2 | 写锁按在途工作项 | 让每次写入能归因到具体工作 |
| U3 | 评审、凭证和实施同链 | 防止未批准设计进入实现 |
| U4 | 收口显式 completed | 不把所有在途行当完成 |
| U5 | 工作证据与锚批双门 | 防止只有文本或只有状态 |
| U6 | check 只读 | 查询不能暗中修账 |
| U7 | 不承诺跨存储事务 | 文件与 SQLite 无共同事务协议 |

## 5. 验收

- 开批、接手、预定、attach 的事务结果。
- 写锁的项目、行号、状态和工具入口。
- 评审裁定、状态、§5、凭证签发。
- 正常收口、补关、取代和重开。
- 回滚成功与补偿失败的 check 读数。
- 普通模式和 depth>0 不被错误套用父侧写锁。

## 6. 行为矩阵

| 状态 | 预期 |
|---|---|
| 无有效在途行写产品面 | 拒绝 |
| 有有效行但项目不符 | 拒绝 |
| 评审通过但最新轮打回 | 不开放实施 |
| 锚批未收口单独核销 | 拒绝 |
| 全归档且唯一 open-but-settled | 可补关 |
| 收口漏列在途行 | 写档前拒绝 |
| 重开遇已核销行 | 不回收 |

## 7. 边界

不复制六态、段写权、凭证 TTL 或跨仓算法。不把读数当授权，不把冻结窗当核销门，不用历史批次作为当前规范。

## 8. UI / 交互

没有独立 UI。回执必须指出当前失败在哪一环，并给出可执行的下一步。

## 9. 集成场景

真实入口包括 batch、ledger、advisor 和受控写工具。集成用例按业务 delta 进入 RTM，不在本档保存历史增量清单。
