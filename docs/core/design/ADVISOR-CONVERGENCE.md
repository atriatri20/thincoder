# Advisor 评审收敛协议（ADVISOR-CONVERGENCE）· 设计

> 需求 = `docs/core/requirements/ADVISOR-CONVERGENCE.md`。
> 最近先例：`ADVISOR-GUARDS.md` 的宿主确定性判定。对齐 = 状态由宿主产生；分工 = 本档负责轮次、会话、响应与覆盖，守卫档负责边缘判定。
> 勘察证据：已读当前 advisor 工具契约、需求与守卫设计；相关 = type、documents、batchDoc、异步和评审对象声明。

## 1. 目标

独立评审通过轮次衰减、新会话和证据校验收敛。宿主不把自然语言报告当作状态机输入；设计凭证回显与 §3 工具记录是唯一受控例外链。

## 2. 轮次定义

### 2.1 轮次表

| 轮次 | 提示词 | 范围 | 新问题 |
|---|---|---|---|
| Round 1 | code/design 首轮 | 全量审查 | 建立完整发现表 |
| Round 2 | round2 | 以验证 prior 为主 | 仅明显崩溃、数据丢失、逻辑错误 |
| Round 3+ | round3 | 严格只验 prior | 不寻找新问题 |

每轮用户消息带机械生成的 Review-object declaration。设计首轮还包含 Approval Signal。

### 2.2 轮次映射

已完成尝试数决定下一轮提示词；有 prior 且已有完成尝试才进入 round2+。拒绝启动不消耗轮次。

轮次属于评审实例，同步与异步共用实例事实。没有 prior 且本 run 未改代码时可开始新周期；本 run 改过代码则保留轮次。

轮次只用于提示词、显示和争议窗，不作为拒发上限。

### 2.3 工具轮预算

提示词给收敛预算，宿主另有单场工具轮硬帽。硬帽用于打断失控循环，不等于封禁后续评审。

### 2.4 通过与阻断

- 无未解决红项才能 pass。
- 红项可以 Fixed 或经争议窗 Accepted。
- 黄蓝项不当然阻断，但被标为必修的项按当前评审标准处理。
- 机制级矛盾按严重度规则处理。
- 宿主不扫描 all-clear 短语决定状态。

### 2.5 争议窗

不修项必须给技术反驳与证据，或明确认账不修的理由。

Round 2 可评估理由并打回；Round 3+ 对有理由的不修项列 Accepted，不再重新裁决同一争议。零理由项列 Unfixed。

Dispatched 仍是 Unfixed。声称 Fixed 的项目必须对照当前文件核验。

## 3. 终止与失败

### 3.1 无会话级轮次封禁

每实例 round 保留，用于提示词衰减与显示。宿主不因第几次发起而拒绝。

单场工具轮帽、墙钟预算、completion guard 推回预算和异步池上限是不同机制，不得被解释为评审轮次封禁。

### 3.2 失败结论

机械失败逐次产生原因、当前判据和恢复选项。父侧看到同一判据反复机械失败时停止重跑并报告用户。

### 3.3 事实载体

路径归一和文档集合键属于纯事实。结算分类使用纯函数，输入只来自宿主可见状态。

## 4. 会话与证据

### 4.1 陈旧上下文

Round 2+ 把旧消息视为历史快照，只信本轮重新读取的文件。follow-up 不注入 git diff 作为当前证据。

Unfixed 或 New 必须给本轮读取证据。行号只用于本次定位，证据本体是引文。

### 4.2 fresh session

每轮重建 system 与 user 消息，不复用上一轮会话数组。旧 read 输出不进入新会话。

### 4.3 prior 注入

Round 2+ 注入上一轮完整评审原文，防止只按被审方自选响应表验证。

Agent Response 只作聚焦参考。取件按本评审投递水印隔离；索引不可用时按当前降级文本处理，不驱动控制流。

只有评审形态输出才作为 prior；空回复和纯工具进度不能成为下一轮清单。

## 5. host-verified citations

citations 解析评审输出中的文件、当前行定位与引文，再由宿主比对磁盘。

路径经过 realpath 围栏；引文必须是实际行的连续子串。未通过校验的引用不能支撑打回。

引文候选根与失败分类由 ADVISOR-GUARDS 定义。状态文档中的长期引用仍使用稳定名称，不因为评审解析器需要行号而把行号写成持久坐标。

## 6. 评审触发与覆盖

### 6.1 触发范围

文件写工具和子代理代码合并使既有评审与验证覆盖失效。普通 bash/git 副作用主要使验证快照失效，不在内容追踪之外另猜评审范围。

只读操作不使评审失效。产品代码树、文档、临时件和无路径修改按当前内容判定处理。

### 6.2 completion guard

guard 默认关闭，只在顶层普通模式生效。工程模式由设计凭证、批次和结算链承担。

核心问题是“本 run 是否有尚未被有效评审覆盖的代码修改”。异步在途不是已覆盖；陈旧或不完整结算也不置覆盖。

### 6.3 事件表

| 事件 | 评审覆盖 | 验证覆盖 |
|---|---|---|
| 文件写工具改代码 | 失效 | 失效 |
| 子代理代码合并 | 失效 | 失效 |
| 只读工具 | 不变 | 不变 |
| 文档/临时件 | 按内容分类 | 按当前规则 |
| 有效代码评审结算 | 置覆盖 | 不代替验证 |
| 异步在途 | 未决 | 不变 |

### 6.4 推回预算

推回预算只在被审对象真实变化时恢复。成功文件写与子代理合并推进写序；只读搜索不恢复。

未评审周期有提醒上限；到顶时必须产生诚实提醒，不能静默把未评审交付为已评审。自动回合和续跑按当前 guard 快照规则保持连续性。

## 7. 响应表与批准

表头固定为 `| # | Action | Detail |`。每项使用原 issue 编号。

Fixed 表示已落地，Dispatched 表示在途，Not an issue 表示技术反驳，Deferred 表示有理由的暂不修。

请求用户批准前，Dispatched 必须收敛为实际 Fixed 或其他有证据的终局。修正轮不得夹带新范围。

## 8. 评审维度

### 8.1 需求契合

对照用户原话、需求文档、实现者声称和实际行为。没有证据的需求偏差不能作为高置信发现。

### 8.2 设计与文档

设计评审检查同类先例、勘察证据、分支依据、业务验收、当前状态载体和稳定引用。

设计文档不应承载某一批的受影响文件清单、执行计数或一次性过程。缺少必要设计内容与把过程放错载体分别判断。

### 8.3 工具返回归一

评审循环调用工具时把同步值与 Promise 归一为 Promise，使超时竞速和拒绝处理一致。

## 9. 配置

- 项目 `.thincoder/advisor.md` 提供评审准则覆盖。
- advisor.provider / advisor.model 覆盖评审模型。
- advisor.guard 控制普通模式 completion guard。
- 轮次提示词硬加载，缺失即失败，不静默降级。

## 10. 验证

验证轮次选择、无轮次封禁、新会话、prior、引文、覆盖失效、guard、响应表语义、争议窗、需求契合和工具返回归一。

提示词文本可用逐字阅读或结构检查；文档变化本身不需要制造业务集成用例。真实业务或生产问题按 TESTING 决定永久集成覆盖。

## 11. 边界

轮次语义归本档；不完整族、启动门、预算、冻结和失败文案归 ADVISOR-GUARDS；异步实例生命周期归 AGENT-LOOP-ASYNC-POOL；凭证槽归 DESIGN-TOKEN-SETTLEMENT。
