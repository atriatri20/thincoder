# 文档—代码对账（DOC-CODE-RECONCILE）· 设计

> 本档规定文档、代码和测试如何保持一致，以及发现不一致后如何处置。
> 文档归属与引用形态 = `docs/core/design/DOC-SYSTEM.md`；写作与失效删除 = `docs/core/design/DOC-DISCIPLINE.md`；机械检查 = `docs/core/design/DOC-CHECK.md`。
> 最近先例：`docs/cli/requirements/FEATURES.md` 的「对外文档契约面」。对齐 = 对外文档必须与实装可达能力一致；偏离 = 本档同时覆盖需求、设计、代码和测试之间的语义对账，不定义另一套检查器。
> 勘察证据：已读 `docs/core/requirements/PHILOSOPHY.md` 的「设计文档是 spec」、`docs/core/requirements/DOC-CHECK.md` 的检查边界、`docs/cli/requirements/FEATURES.md` 的对外契约规则。外部公共源无相关需求。

## 1. 定位

文档—代码对账回答三个问题：

1. 当前意图是什么，权威文档在哪里。
2. 代码和用户可见行为现在是什么。
3. 两边不一致时，应改实现、改文档，还是由用户重新裁定需求。

对账是语义工作。文件存在、引用能解析或检查返回通过，都不等于文档描述的机制仍然正确。

## 2. 权威与判序

| 对象 | 权威与处置 |
|---|---|
| 需求文档 | 规定已经批准的意图。实现不满足时，优先修正实现；需要改变意图时由用户裁定。 |
| 设计文档 | 规定当前架构、接口和边界。实现偏离时先修正实现；确认设计本身需要变化时，先更新设计再实施。 |
| 对外使用文档 | 描述用户实际可执行的命令、配置和格式。能力存在但说明错误时修正文档；能力不存在时属于需求缺口，不得把缺能力写成已支持。 |
| 测试与 RTM | 说明覆盖对象和验收证据。用例文件存在不等于当前运行通过，运行结果必须来自实际执行。 |
| 批次记录 | 描述一轮工作的执行过程，不取代需求和设计的当前状态。 |

同一事实存在两种说法时，先停止沿其中一边继续实施，列出两处原文和影响，再消解冲突。不得用“代码一直如此”或“文档写得更早”代替判定。

## 3. 对账对象

对账至少覆盖改动实际触及的以下事实：

- 用户可见命令、配置键、环境变量、文件格式和提示。
- 需求功能点、验收条件和明确边界。
- 设计中的模块归属、接口、事件、状态机和异常语义。
- 代码中的导出符号、调用方、注册入口和运行路径。
- 测试文件、RTM 行及其覆盖状态。
- 文档之间的文件、章节、符号和公共源引用。

不为了对账而扫描与本次改动无关的全部代码。发现另一处问题阻断当前判定，或当前改动使其失效时，才纳入当前处理。

## 4. 对账流程

### 4.1 定位权威来源

通过 `docs/README.md` 找到主题所属需求与设计。先读规则正文，再读实现。只有目录或文件名而没有规则正文时，不得凭文件名推断机制。

### 4.2 取得双边证据

文档侧记录当前原文和章节。代码侧读取实际定义与调用路径；需要外部 API 或协议行为时读取官方资料。没有实际读取的内容标为未验证，不写成确定事实。

### 4.3 判定差异

| 判定 | 处置 |
|---|---|
| 实现偏离有效需求或设计 | 修正实现，并更新受影响的调用方和测试。 |
| 对外说明与现有可达能力不符 | 修正说明，保持用户契约的真实可达性。 |
| 需求或设计本身需要改变 | 停下并交用户裁定，不用代码现状自动改写意图。 |
| 两边证据不足或互相矛盾 | 标出未验证部分并上报，不猜测一个结论继续实施。 |
| 文档之间仅是重复或失效表达 | 保留唯一权威正文，其他位置改为引用或删除。 |

### 4.4 同步修改

同一轮完成规则正文、直接引用方、调用方和验收资产的同步。需求、设计和提示词不得各自保留一份会独立漂移的判据。

过程记录按当前工作模式承载；状态文档不留下“下次再对齐”或“本批待处理”作为终态。

### 4.5 验证

按改动性质选择验证：

- 文档改动：运行 `doc_check`，并人工复核节号、引文和语义。
- 代码改动：运行对应测试，并核对其结果与文档承诺。
- 接口或用户行为改动：从实际使用入口验证，不只检查内部函数。
- RTM 改动：核对指向的用例文件和覆盖状态；未运行时保持未验证。

## 5. 对账结果

### 5.1 判定与记录

每项对账结论必须能回答：

1. 对账对象是什么。
2. 权威来源和实际证据分别是什么。
3. 判定是实现偏离、文档漂移、需求变化还是证据不足。
4. 实际修改了哪些文档、代码或测试。
5. 运行了什么验证，结果是什么。
6. 还有什么没有得到验证。

记录只保留当前事实和必要理由。一次性清单、排查过程和读数由当前过程载体保存，不写入长期状态文档。

### 5.2 完成条件

一次对账完成，必须满足：

- 改动面的权威文档已经确定。
- 所有已确认差异都有处置结果。
- 没有留下相互冲突的当前规则。
- 直接引用和调用方已经同步。
- 验证结论没有超出实际运行范围。
- 未解决项已明确告诉用户，不以“基本一致”掩盖。

## 6. 工具边界

| 工具或文档 | 能证明什么 | 不能证明什么 |
|---|---|---|
| `doc_check` | 段长、行号锚和悬空指针在其判域内的结果 | 节号、引文、代码行为和业务语义是否正确 |
| `doc_graph` | 文档、需求、用例和符号之间已采集的引用关系 | 关系两端的内容是否仍然一致 |
| RTM | 故事、用例和覆盖状态的登记 | 未实际执行的测试是否通过 |
| 测试运行 | 当次被执行断言的结果 | 未覆盖场景和文档中其他事实的正确性 |

不得为了满足对账而新增平行检查器。现有工具不能判定的语义，由阅读、运行和评审补足。

## 7. 边界

- 不用全仓关键词替换代替语义对账。
- 不把批档或归档内容当作当前规则的权威来源。
- 不用一次历史读数证明当前状态。
- 不把“文档与代码一致”简化为“文档里点名的文件存在”。
- 不在证据不足时选择对当前修改最方便的一边。
