# 文档体系（DOC-SYSTEM）· 需求

> 板块 = 文档体系。设计档 = `docs/core/design/DOC-SYSTEM.md`。
> 当前文档地图 = `docs/README.md`；文档写作纪律 = `docs/core/design/DOC-DISCIPLINE.md`；机械检查契约 = `docs/core/requirements/DOC-CHECK.md`。
> 本档只规定本仓文档必须满足的状态，不承载迁移计划或某次修改的执行安排。

## 1. 总体需求

为 ThinCoder 的所有产品和共享模块提供一套可定位、可维护、可复核的项目文档体系。

维护者必须能够回答三个问题：这个主题由哪份文档负责；它描述的是当前规则还是一次执行过程；引用的目标是否仍然存在。

## 2. 功能性需求

| # | 需求 | 验收 |
|---|---|---|
| FR1 | `docs/README.md` 必须作为当前文档地图，按板块和主题登记现役需求、设计与标准文档 | 地图中的文档引用均能到达盘上文件；每个现役状态文档都能在地图中找到归属 |
| FR2 | 文档层及其根目录必须由 `PROJECT-MANIFEST.json` 的 `docRoot` 声明，检索和检查不得硬编码本仓目录 | 修改声明后，相关工具按新声明工作；声明的路径具有统一的项目根解析口径 |
| FR3 | 文档必须按 core、cli、vsc、desktop、render-core、server 的板块归属组织 | 新文档能依据机制所属代码和业务面确定落点；共享模块不因被多端使用就失去自己的板块 |
| FR4 | 同一目录内文档名必须唯一；同主题需求与设计优先同名，非一对一关系必须显式回指 | 读者不会仅凭同名文件把两个主题当成一个；一对多和需求归属他板块的情况仍有明确入口 |
| FR5 | 引用必须指向可识别的文件和章节；跨板块文档使用仓根相对路径，跨仓引用只允许指向已声明公共源 | 不使用行号或相对位置作为内容锚；未声明外部文档不冒充本仓事实来源 |
| FR6 | 一条机制只能有一个权威正文；需求与设计只描述当前有效状态 | 其他文档引用而非复制权威正文；过程、一次性读数和失效方案不留在状态文档 |
| FR7 | 文档机械检查由产品内建工具提供，使用项目声明的文档域 | 检查入口为 `doc_check`；判据和适用范围由 DOC-CHECK 规定，本仓不依赖自建平行检查器 |
| FR8 | 一份文档只承载本阶段该有的产物：设计文档写设计、目标态与验收标准，不写实施记录，也不把只有实施完成后才存在的产物列成本文档必须有的内容 | 读者读一份设计文档，不会被引去找尚不可能存在的东西；目标态、计划与验收标准仍照写在档内 |

## 3. 非功能性需求

| # | 要求 | 验收 |
|---|---|---|
| N1 | 文档归属和引用规则必须明确到可人工复核 | 读者能按规则判断一个新主题的落点，并指出引用目标 |
| N2 | 文档体系必须仓内自持 | 本仓需求、设计、标准和过程记录不依赖另一个仓代为保存 |
| N3 | 地图和规范必须保持当前状态 | 新增、移动或删除文档时，同轮更新地图和直接引用；不维护易漂移的库存计数 |
| N4 | 检查结论不得超出检查能力 | `doc_check` 的通过只代表其实际判据通过，节号、引文和语义仍须人工复核 |

## 4. 边界

- 文档地图不复制各文档的规则正文。
- 本档不规定批档六段、台账状态机或评审流程。
- 本档不规定段落长度、行号识别和悬空指针的机械算法。
- 提示词是产品代码，住在 `thincoder-core/prompts/`，不在 `docs/` 建第二份正本。
