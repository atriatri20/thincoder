# 产品定性（PROJECT）· 需求

> 本档定义 ThinCoder 产品族、跨端共享契约、产品边界和工作模式。
> VSC 专有需求 = `docs/vsc/requirements/PROJECT.md`；Desktop 专有需求 = `docs/desktop/requirements/PROJECT.md`；团队服务端 = `docs/server/requirements/PROJECT.md`。

## 1. 总体定位

ThinCoder 是通用 AI 编码智能体产品族：CLI、VS Code 扩展和 Desktop 是同级独立客户端，Server 提供团队网关与协同服务。

客户端可以独立安装和使用。多个客户端同时使用时，共享配置、会话和适用的核心能力，不因切换入口丢失工作状态。

## 2. 技术与产品决策

| 项 | 决策 |
|---|---|
| 语言 | 以原生 JavaScript ESM 为主，不使用 TypeScript 或通用源码转译 |
| 依赖 | 优先使用 Node 标准库、宿主 API 和第一方包，避免第三方运行期依赖 |
| 产品关系 | 客户端同级独立；共享能力归 core 或 render-core |
| 服务端关系 | 团队能力由 Server 显式承担，不把客户端变成托管平台 |
| 模型接入 | 直接支持当前主流协议和自定义兼容端点，不为老旧模型保留无需求的兼容层 |

## 3. 跨产品共享契约

| # | 契约 | 当前要求 |
|---|---|---|
| C1 | 配置共享 | 客户端读写同一用户数据目录配置；`defaultModel` 使用 `provider:model`；敏感值可显式引用环境变量，缺失时明确报错 |
| C2 | 会话共享 | 会话按工作目录和槽位存储于共享用户数据目录，客户端可恢复同一会话 |
| C3 | Provider 预设 | 唯一条目源 = `thincoder-core/config-presets.mjs` 的 `PROVIDER_PRESETS`，各端不自建另一份预设表 |
| C4 | 自定义协议 | 自定义 provider 填写名称和 baseURL，并选择 `openai`、`anthropic` 或 `google` 格式 |
| C5 | 模型选择 | 渠道与模型分两级呈现，实际选取单位是模型条目 |
| C6 | 渠道管理 | 添加、删除和 key 管理沿用核心流程语义，各端按宿主实现界面 |
| C7 | 默认渠道 | 按明确的配置与渠道顺序选择，不在多个可用渠道间静默猜测 |
| C8 | Key 存储 | 客户端共享同一配置源；任何加密、掩码或环境引用都必须保持跨端语义一致 |
| C9 | 记忆 | 客户端使用 core 的统一记忆与索引能力，不维护互不兼容的端侧格式 |

## 4. 产品组成

| 产品 | 主要界面 | 发行形态 |
|---|---|---|
| CLI | 终端 TUI、ACP 接入 | npm 包 |
| VS Code 扩展 | Webview 面板 | VSIX |
| Desktop | 原生桌面窗口 | 桌面安装包 |
| Server | Web 控制台与团队 API | 服务端包与部署产物 |

## 5. 产品定性

### 5.1 用户与核心价值

用户是把实现工作委托给 agent、同时保留方向和最终决策权的开发者与团队。

产品承诺：

1. 能完成读取、修改、验证的完整工作闭环。
2. 通过设计、评审和实际运行提高可靠性。
3. 对需求、交付、风险和未完成项保持透明。
4. 通过共享核心和明确边界控制产品与维护成本。
5. 通过记忆和团队协同保留项目知识。

### 5.2 产品边界

- 不重造通用编辑器或 IDE；通过扩展、ACP 和桌面宿主提供接入。
- 不把客户端变成云端托管服务；团队服务由 Server 独立承担。
- 不做模型推理引擎，模型调用通过各家 API 或兼容端点。
- 不把通用工作流引擎作为产品中心。
- 不以堆依赖和堆集成作为能力来源。

### 5.3 定位

ThinCoder 选择“薄而可靠”：将复杂度投入协作、证据、追溯和记忆，而不是无边界功能堆积。

### 5.4 两种工作模式

| | 普通模式 | 工程模式 |
|---|---|---|
| 定位 | 默认直接执行，以纪律、验证和评审保证质量 | 强流程，设计、批准和凭证先于实现 |
| 约束 | 不使用工程模式的机械写权与 spawn 门 | 通过结构和机械约束保证流程 |
| 适用 | 日常开发和交互式任务 | 需要完整留痕和先审后做的规模化工作 |
| 切换 | 用户可随时选择，不在工程模式内开小改旁路 | 同左 |

两种模式的管理语义保持一致，具体差异由 `docs/core/requirements/NORMAL-MODE.md` 与 `docs/core/requirements/ENGINEERING-MODE-V2.md` 规定。

### 5.5 功能范围与演进

核心范围包括 agent 主循环、工具、上下文、会话、配置、记忆、子代理、MCP、检查和恢复能力。

团队网关、团队台账、团队记忆和服务端开发由 Server 的需求文档承载。客户端与 Server 的集成必须保持本地能力和团队能力的边界清晰。

### 5.6 技术与质量约束

| 项 | 约束 |
|---|---|
| 运行平台 | CLI 与 core 遵守当前声明的 Node 下限 |
| 界面 | CLI 使用 ANSI；其他端使用各自宿主能力 |
| 上下文 | 准确和完整优先，不为节省 token 删除必要信息 |
| 国际化 | 面向全球，不假设用户位于中国或使用中文 |
| LLM 调用 | 使用当前 transport，不无理由引入 SDK |
| 验证 | 交付必须实际运行适用检查；文档不得宣称未实现的能力 |
| 依赖与死代码 | 新依赖需要理由；失效代码随当前工作清理 |
