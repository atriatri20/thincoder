# 测试基建（TESTING）— 需求

> 板块：测试方法、寿命、执行分工、集成测试集、散文锚禁令和终端程序自动验证。
> 设计层 = `docs/core/design/TESTING.md`。归属与命名 = `docs/core/design/DOC-SYSTEM.md` §5.1 与 §6。
> 本档规则以用户裁定和项目实测为来源；术语定义保留公开标准出处。

## 0. 概念

**单元测试（unit testing）**：针对单个软件或硬件组件的测试。ISTQB 术语表对 component testing 的定义为：

> "A test level that focuses on individual hardware or software components."

**集成测试（integration testing）**：组合软件或硬件组件，评估它们之间的交互。IEEE 610.12 的定义为：

> "testing in which software components, hardware components, or both are combined and tested to evaluate the interaction between them."

本项目对集成测试的粒度解读：被测对象是组合完成的项目整体，另一侧是用户、操作系统、文件系统、网络或模型服务等外部边界。项目内部模块之间的隔离测试仍属单元测试。

因此，单元测试与集成测试回答不同问题，不因运行方式或文件位置变化而互相转换。

## 1. 总体需求

### 1.1 目标

- 单元测试是开发者的即时反馈回路，回答“这次改动是否正确”。
- 集成测试是发布前的验收回路，从用户可见入口验证真实业务。
- 单元测试是开发期工具，用毕即删；集成测试是交付资产，长期保留并进入 RTM。
- 集成用例只来自业务真实需要的场景或生产真实发生的问题。
- 验证投入与失败代价成比例，不随代码量机械增长。

### 1.2 三个执行轴

| 轴 | 单元测试 | 集成测试 |
|---|---|---|
| 技法 | 隔离单个组件，外部协作者使用桩或假件 | 将项目作为整体，从用户入口验证与外部的交互 |
| 寿命 | 住批次目录，用毕即删，不进入常驻集合 | 住 `test/integration/`，长期保留 |
| 执行 | 谁改谁写谁跑，只跑本改动相关用例 | 父侧在收口或发布时运行，不在实施链中反复运行 |

需要长期业务守卫时，应判断是否存在真实集成场景。没有业务场景时，不以保留单元测试代替集成验收。

### 1.3 防膨胀

测试总量不得随项目规模无界增长。永久测试会在每次相关改动中产生运行、分拣和维护成本，因此集成用例必须有真实业务来源，单元测试不得积累为常驻库存。

集成测试集采用 50–100 用例的规模窗口。超出窗口时应裁减低价值或重复场景，而不是继续按代码量扩张。

## 2. 功能性需求

| # | 需求 | 说明 |
|---|---|---|
| F1 | 改动内只跑单元测试 | 实施者只验证本任务改动相关的单档或子集，不逐轮运行集成测试 |
| F2 | 未跑集成测试必须报告 | 原句为：“not integration-test verified — the parent-side closeout run is the only integration-test run.” |
| F3 | 集成测试归属父侧 | 在收口或发布时按端运行，不放在实施者链内 |
| F4 | verify 不代跑 | 只接收 `verification.status` 声明，不自动执行测试 |
| F5 | 单文件调试直达 | `node --test <档>` 可直接运行单元或集成测试档 |
| F6 | 来源与寿命 | 单元测试住批次目录并用毕即删；集成测试按业务或生产来源常驻 |
| F7 | 层次不重复 | 单元可断言内部实现；集成只断言业务可观察结果，同一断言不在两层重复持有 |
| F8 | 两层永不互转 | 集成用例按业务需要单独设立，不由单元测试改写或提升 |
| F9 | 收口测试行 | 记录本批单元测试清理、集成影响及集成集规模窗口 |
| F10 | 随需求演进 | 需求或行为变化时，由主 agent 评估集成影响，再完成场景设计与实现 |
| F11 | 生产问题收编 | 真实问题处理后，将有长期验收价值的场景转成业务集成用例 |
| F12 | 集成集是发布门 | 发布前必须运行适用集成测试集并全部通过 |
| F13 | 普通模式必选场景 | 集成集必须包含普通模式完整工具流，覆盖正常、边界和错误三态 |
| F14 | 三前端实例化 | 业务场景按 CLI、VSC、Desktop 的实际入口实例化；桌面驱动与隔离见 `docs/desktop/design/E2E-TESTING.md` |

### 2.1 维护模型

| 事项 | 责任 |
|---|---|
| 本批单元测试写、跑、删 | 实施者 |
| 集成影响和规模窗口评估 | 主 agent |
| 新集成场景定形 | 设计责任方 |
| 集成场景实现 | 实施者 |
| 生产问题是否收编 | 用户与主 agent |
| 规则冲突与例外 | 用户裁定 |

空集成集不算通过：没有可执行用例时，入口必须非零退出并说明原因。

## 3. 非功能性需求

| # | 维度 | 标准 |
|---|---|---|
| N1 | slow 是纯别名 | 批次单元测试中的重 IO 用例可用 `slow(name, fn)` 标注；它照跑，不表示跳过或分层 |
| N2 | 文件位置稳定 | 单元测试住批次目录；集成测试住 `test/integration/` |
| N3 | 标注纪律 | 单元测试中实测超过 500ms 的用例使用 `slow()`，仅用于人工识读 |
| N4 | 标注阈值 | 500ms，以实际运行测量为准 |
| N5 | 并发上限 | `--test-concurrency=6`，避免重 IO 并发导致不稳定 |
| N6 | 成本口径 | 重点控制重 IO 和长期维护成本，不用用例数量代替成本 |
| N7 | 与需求同步 | 需求或行为变化必须触发集成影响评估，并留下记录 |
| N8 | 最小可跑起步 | 集成场景最小集覆盖正常、边界和错误；扩面只走业务或生产两个来源 |
| N9 | 自动可跑 | 集成测试不依赖真实付费端点或人工操作 |
| N19 | 规模窗口 | 一仓 50–100 个集成用例；超窗须裁减回窗口内 |
| N20 | 集成域 | 集成测试集统一位于仓根 `test/integration/`；core 与 render-core 不另设集成集，由前端场景覆盖 |
| N21 | 总量受控 | 单元不积累，集成超窗即裁；验证投入与失败代价挂钩 |

空集不判绿。真实端点 smoke 独立于自动集成测试集。

## 4. 范围边界

- 集成测试只从仓根 `test/integration/` 收集，其他位置不作为集成入口。
- 批次目录中的单元测试不进入常驻收集面。
- 不设置独立测试角色。
- 自动集成测试不调真实付费端点，不依赖人工操作。
- 单元测试不因“将来可能有用”而保留。
## 5. 散文锚禁令

读非测试文件并断言某句文本在场、缺席、次数或顺序，会把措辞变化误报成行为回归。此类断言不得作为测试守卫。

设计面 = `docs/core/design/TESTING.md` §6。多端遵守同一语义，各自实现，不要求字节一致。

### 5.1 判定

三个条件同时成立时属于散文锚：

| # | 条件 |
|---|---|
| ① | 断言对象是非测试文件的文本或其派生切片 |
| ② | 断言文本内容在场、缺席、出现次数或相对顺序 |
| ③ | 断言对象不属于下列明确的结构或行为保留面 |

载体补充：

| # | 规则 |
|---|---|
| C1-a | 提示词句子不豁免。无论从磁盘、装配器还是渲染出口取得，断言提示词句子都命中 |
| C1-b | 模型实际收到的工具契约对象，以及工具实际返回或拒绝文案，属于行为和契约面 |
| C1-c | 结构、数值、旗位、退出码、集合成员和警告清单不是散文锚 |
| C1-d | locales 中的产品资源文案按产品行为处理；读取普通源码或文档文本仍命中 |

执行产物，例如函数返回、子进程输出、渲染帧和测试自建临时文件，按行为结果判断。直接读取或 import 非测试文件的静态文案则属于文本锚。

### 5.2 功能性需求

| # | 需求 | 说明 |
|---|---|---|
| F15 | 禁止散文锚 | 满足 §5.1 三个条件的断言不得作为测试守卫 |
| F16 | 发现即移除 | 修改测试时发现散文锚，应删除或改写为真实行为断言 |
| F17 | 结构检查保留 | 文档结构、台账结构、工具契约和其他结构自洽检查不按散文锚处理 |
| F18 | 混装精确处理 | 同时含行为和散文锚的用例只移除锚部分，不误删行为断言 |
| F19 | 新增只允许行为或结构 | 新验收应断言业务结果、执行产物或结构属性，不锁文档措辞 |
| F20 | 多端语义一致 | 各端按同一分类规则实施，不建立跨端文本同步依赖 |
| F21 | 审查按语义 | 对账读取实际断言并分类，不用行号清单或一次数量差代替判断 |
| F22 | 同步验收描述 | 移除错误断言时，同步修正引用它的验收说明 |

### 5.3 非功能性需求

| # | 维度 | 标准 |
|---|---|---|
| N10 | 可复核 | 每处判定都能指出被断言对象及其载体 |
| N11 | 验证不降级 | 移除散文锚后，相关行为和结构验证仍须运行并通过 |
| N12 | 不误伤 | 行为断言、结构检查和 `slow()` 标注不因文本清理而被无关修改 |

### 5.4 边界

- 不改变 `doc_check` 的现有三项判据。
- 不把工具返回文案、协议帧或界面资源误判为普通文档文本。
- 不用文件存在性断言代替文本内容断言的分类。
- 不把历史删除数量作为当前测试质量指标。
## 6. 终端程序自动验证（harness）

终端驱动能力的用户故事和非功能边界由 `docs/core/requirements/TOOLS.md` §4.7 承载。本节只规定自动验证方法，适用于任意需要 TTY 的程序。

### 6.1 方法要求

| # | 条目 | 判据 |
|---|---|---|
| F23 | 真子进程驱动 | 从真实进程和 TTY 驱动，不用业务模块直调冒充终端交互 |
| F26 | 覆盖边界明确 | 写明能测和不能测的面，自动通过不代表未测面已验证 |
| F27 | 确定性 | 模型、网络和时钟使用脚本化替身；隔离 HOME 与 cwd；重复执行结果一致 |
| F28 | 接入既有集成入口 | 终端场景住 `test/integration/`，由集成入口与发布门执行，不新增 runner |
| F34 | 集成设计必做 | 业务行为变化或真实新场景出现时，必须同步设计集成场景、业务判据和需求回指 |
| N14 | 宿主无 TTY 可跑 | 调用方没有真实终端时，harness 仍能创建受控终端并完成验证 |
| N15 | 无外部不确定性 | 不依赖外网、付费端点或跨用例共享状态 |
| N16 | 有硬超时 | 每个用例都能被超时收束为可读失败，不静默挂起 |
| N17 | 失败可诊断 | 失败输出包含退出码、屏幕或输出尾段和输入序列 |
| N18 | 寿命与执行分层 | 终端集成用例不使用 `slow()`，只在集成入口与发布门运行 |

集成设计是否必做由业务行为决定。内部实现变化但没有用户可见结果变化时，不制造集成用例。规模窗口是上限，不是拒绝真实场景的理由。

### 6.2 边界

- 不用伪造 `isTTY` 或业务模块直驱代替真实终端。
- 不用自动断言评价主观视觉体验；这部分仍由人工走查。
- 不调真实付费端点。
- 不改变既有集成 runner 和收集面。
## 7. UAT 验收总表（RTM）

RTM 是集成验收的交付物。它长期留存，与集成用例同寿命；单元测试是内部开发工具，不进入 RTM。

| # | 需求 | 说明 |
|---|---|---|
| F29 | 索引与分册 | 索引位于 `test/RTM.md`，分册位于 `test/rtm/<能力族>.md`；按能力族而非端分册 |
| F30 | 可追溯 | 每个用例行回指业务故事和 `test/integration/` 用例；用例标题以完整 RTM 编号开头 |
| F31 | 验收方可读 | 使用业务语言表达步骤、通过条件、异常和证据 |
| F32 | 签署与更正 | 索引含签署面；签署后正文冻结，更正只能追加到异常与更正区 |
| F33 | 寿命边界 | RTM 不依赖可删除的批档；单元测试不转成 RTM 行 |
| F35 | 判据与读数 | 判据必须在正确实现上可通过；状态文档不写一次读数；代码原始行数按 `docs/core/design/DOC-CHECK.md` §8 写入当前批次机读清单 |
用例表固定为五列：编号、怎么做、怎么算通过、异常、证据。验收标准写在每个用例行内，不另设中间分组层。

编号携带端名或端集合，例如 `CLI 1-1`、`VSC 1-1`。相同故事号在不同端并存时由端名消歧。

### N22：位置与份数

全仓只有一套 RTM：一个索引和能力族分册。端覆盖由索引矩阵表达，不为每端各建一套。

RTM 不新增测试执行入口，不改变集成 runner，也不把人工签署变成机械门。
