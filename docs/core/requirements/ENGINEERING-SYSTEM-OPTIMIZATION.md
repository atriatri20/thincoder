### 1.3 状态机真实边（`ALLOWED_MIGRATIONS`）

```
待讨论 → 待设计 / 在途 / 已废弃
待设计 → 在途 / 已废弃
在途   → 待核销 / 已废弃
待核销 → 已核销 / 在途 / 已废弃
已核销 → 已废弃
已废弃 → （无后继）
```

关键推论：只有 `待核销 → 在途` 一条回工作位的边；`在途` 没有回等待态的边；`已核销` 可被改废弃但批档重开不回收它。

## 2. 结构层根因（先于逐条问题读）

**R1 规则只加不删，没有收敛动作。**
每次踩坑就加一条，旧条不回收。结果不是「更严谨」，是同一件事有多个版本在盘上，读者无法判断哪个现行。

**R2 同一机制多处书写。**
同一规则出现在 persona、discipline、common、子代理 persona、工具描述里，且措辞不同。改一处不改其余，必然分叉。

**R3 状态机按理想路径设计，缺异常路径。**
只考虑「认领 → 做完 → 核销」，没有「认错领 / 做不完 / 暂缓 / 批撤销」的合法表达，于是只能借「待核销」「已废弃」撒谎。

**R4 工具 schema 与描述不按角色收窄。**
能力限制靠执行期拒绝，模型读到的是全量写说明；读到 ≠ 能用，拒绝发生在调用之后，往返由此产生。

**R5 批档与台账双存储，无跨存储事务。**
先写档再写账，失败不互否，产生半状态。

**R6 记录义务高频强制，产品工作多门离手。**
文档决定、债务登记、清扫写作「same round / immediately / same day」；产品实现则要设计、评审、令牌、批档。两边成本不对称，行为自然偏向易做的那侧。

## 3. 问题清单与处置

分级：P0 = 会造成错误行为或账实不符 · P1 = 明显往返与误导 · P2 = 体量与可读性。

### A. 状态机与台账生命周期

#### A1（P0）`在途` 没有退回等待态的边

- **现象**：误认领、做不完、批暂缓时，只能保持 `在途`、或推到 `待核销`、或 `已废弃`。
- **证据**：`ALLOWED_MIGRATIONS` 的在途数组仅 `["待核销","已废弃"]`；`applyRowUpdateTx` 对表外迁移抛错。
- **直接原因**：迁移表没有 `在途 → 待讨论`。
- **结构原因**：R3。
- **后果**：把「没人做」写成「做完待结」（伪结账），或把「仍是债」写成「已废弃」（伪前提）。撤回再新立还会重置 `created_at`，老化计时被洗白。
- **处置**：新增 `在途 → 待讨论`，理由必填、`executor` 清空、`task_book` 解绑；`待核销 → 待讨论` 同理评估。与「认领即承诺」不冲突：那条禁止往里假装，这条允许往外说真话。
- **验收**：误认领行可回到待讨论；`created_at` 不变；回执带理由；不允许无理由退回。

#### A2（P0）核销证明绑定「锚批已收口」

- **现象**：批暂缓 ⇒ 该批行永远无法已核销。
- **证据**：`ledger-close-proof.mjs` 的 `assertCloseOutProof` 要求 `task_book` 在盘、§1 已收口、§3 评审通过。
- **直接原因**：核销的合法性完全由批档状态推导，没有独立的工作完成证据通道。
- **结构原因**：R3 + R5。
- **处置**：核销证明拆成「工作已完成的证据」与「批已收口」两件；批暂缓/撤销时允许凭证据核销或退回，不让批状态绑架行状态。
- **验收**：批暂缓时，已完成行可凭证据核销；未完成行走 A1 退回，不得借 `待核销` 伪装。

#### A3（P0）批档收口默认推进同批全部在途行

- **现象**：收口即把所有在途行推到 `待核销`，无选择参数。
- **证据**：`ledgerReanchorBatch` 只排除 `认账不排期`，其余在途行全推。
- **直接原因**：重锚以 `task_book` 同址为集合，不区分完成与否。
- **结构原因**：R3。
- **后果**：暂缓批一旦收口，9 条未做行全部变成「做完待结」。
- **处置**：收口时逐行要求处置：完成 → 待核销；未完成 → 待讨论（走 A1）；不再默认全推。
- **验收**：含未完成行的批收口后，未成行仍在待讨论，不出现在待核销。

#### A4（P0）批档与台账写入非原子

- **现象**：档已冻结、行仍在途；或档已重开、行仍待核销导致写锁全拒。
- **证据**：`closeBatchRecord` 先 `writeFileSync` 再 `reanchorOnClose` 且捕获异常；`statusBatchRecord` 重开同样先档后账。
- **直接原因**：两个存储顺序写，失败不互否。
- **结构原因**：R5。
- **处置**：重锚/回收失败时收口与重开失败并回滚档，或提供可重试的补偿动作与明确半状态查询面；优先真事务，做不到则禁止静默成功。
- **验收**：注入台账写失败，档与账不得出现一前一后的半状态；回执不得报成功。

#### A5（P1）`已核销` 可改废弃但重开不回收

- **现象**：错核销后无法恢复工作。
- **证据**：`ledgerReclaimBatch` 对已核销进 `unreclaimable`。
- **处置**：要么禁止 `已核销 → 已废弃`（归档即终态），要么重开可回收已核销并记审计；二者取一，不能两套语义并存。
- **验收**：错核销有明确恢复路径；或状态机明确不可恢复且 UI/描述一致。

#### A6（P1）撤回与重开的边角不一致

- **现象**：`close(已废弃)` 不查源态可重复执行；手工 `待核销 → 在途` 可能留下空 `executor`。
- **证据**：`applyRowClose` 仅对已核销查证明；`resolveExecutorTarget` 不含该回退边。
- **处置**：撤回加源态 guard；回退边统一 executor 规则。
- **验收**：重复撤回被拒；回退后 executor 非空或明确为空且有理由。

#### A7（P1）`task_book` 归批要求档已在盘

- **现象**：想先登记「将来归某批」做不到。
- **证据**：`assertTaskBookGate` 要求新指名指针解析到盘上文件。
- **处置**：允许「预定批」指针形态（未建档也可登记），或提供批号预注册；避免为了登记而先造空批。
- **验收**：可先登记归批意图，建档后自动接上。

### B. 工具链与往返

#### B1（P1）写锁对只读命令也要台账号

- **现象**：`bash`/`execute` 不按命令只读分类，一律要号。
- **证据**：`write-gate-ledger.mjs` 的 `LEDGER_ENTRY_TOOLS` 注释含 `npm test / git status` 曾同属要号面。
- **直接原因**：入口按工具名而非按动作性质。
- **结构原因**：R4。
- **处置**：只读命令免号；写命令仍要号。判据必须真实可机检，不靠模型自称只读。
- **验收**：只读命令不再因缺号被拒；写命令仍被拒。

#### B2（P1）批档收口与台账核销是两次动作

- **现象**：只做 `batch close` 不会核销任何行。
- **证据**：`closeBatchRecord` 回执明示「台账核销仍走既有通道」。
- **处置**：在 A2/A3 改完后，提供一次完成的收口动作（逐行处置 + 核销），消除「档冻结了但账还挂着」。
- **验收**：一次动作后档与账一致；无待核销残留。

#### B3（P1）文档指引把建批写成两次前置调用

- **现象**：拒文建议先 `ledger add` 再 `batch create`，但 `batch create` 本身就能同事务建行。
- **证据**：`LEDGER_HANG_STEPS` 两步指引；`createBatchRecord` 同一调用建行。
- **处置**：拒文改为优先 `batch create` 一次完成；只有接管已有行时才要求先查号。
- **验收**：从零开批最少一次调用；拒文不再诱导多一次往返。

#### B4（P1）只读角色失去整把工具的只读能力

- **现象**：explore/plan/consult 无 `git log`、`memory search`、`settings get`、`process list`。
- **证据**：`readonlyToolNames` 只看整把 `readonly`；`dispatch-gates.mjs` 另有 action 级只读名单。
- **直接原因**：两套只读口径，继承面用更粗的那套。
- **处置**：按 action 级只读口径派生只读变体（`git-read`、`memory-read` 等），或给只读角色配受限 schema。
- **验收**：只读角色可查 git 历史与记忆，无需上抛。

#### B5（P1）`doc_graph` 只读变体仍描述 `scan`，且未扫描时必须父代跑

- **现象**：子代理查询 → 报错先 scan → 无 scan 权限 → 上抛 → 父代扫描 → 再查询。
- **证据**：`READ_ACTIONS` 去掉 `scan`；描述仍含完整 scan 段；`READONLY_SUFFIX` 直接写明要找父代理。
- **处置**：只读变体描述删除 scan 段；查询在图缺失时由系统自动触发扫描或返回可读空态，不制造跨角色往返。
- **验收**：只读角色在未建图仓查询不再要求父代介入。

#### B6（P1）只读变体仍展示写操作全文

- **现象**：`ledger`、`team_ledger`、`batch`、`doc_graph` 的子代理描述含其不能执行的写动作。
- **证据**：变体只收窄 action 枚举，描述复用全量文本。
- **结构原因**：R4。
- **处置**：按角色生成描述与 schema；不能做的动作不出现在该角色的描述里。
- **验收**：子代理描述不再包含 create/close/add/update 等不可执行动作。

#### B7（P2）描述与实现不一致

- `eng-designer` 的「≤6 explore」只写在描述，实现不计数（`gateEngCoderSpawn` 对 designer 直接 return null）。
- `coder` 描述称「complete toolset」，实际固定去掉 `question`、`ssh`。
- 两处注释仍称 `batch` 为四/五 action，实际六动作。
- **处置**：要么实现计数，要么删描述中的上限；描述写清排除项；注释改准。
- **验收**：描述中的每个限制都有实现或明确标注为建议。

#### B8（P2）`read_history` 仅 depth 0

- **现象**：子代理需要父会话历史只能上抛。
- **处置**：提供受限的历史读取（当前批相关、只读、限量），或在任务书强制携带所需事实。
- **验收**：子代理不再因缺历史而空转或频繁上抛。

### C. 提示词冲突（全部处理）

#### C1（P0）主 agent 写域自相矛盾

- **证据**：`persona-engineering.md` §Debts 把设计档/提示词列进主 agent 笔域；§Identity 写「Dispatch, do not write」；`discipline-engineering.md` D1 写提示词由 eng-coder 落地。
- **直接原因**：同一角色在不同节被指定为作者与非作者。
- **结构原因**：R1 + R2。
- **处置**：一张写域表定死：主 agent = 需求档/批档/台账/manifest；设计档 = eng-designer；提示词与代码 = eng-coder。其余段落全部指向这张表。
- **验收**：全仓不再有第二处赋予主 agent 设计档或提示词写权。

#### C2（P0）批档生命周期三种说法

- **证据**：persona「frozen records are not deleted」；common「must be deletable at any moment」；designer「deleted at closeout」。
- **处置**：定为「批档是一次性过程档，可由维护者删除；收口不自动删；规范档不得依赖它」。三处统一。
- **验收**：三处同义；D10 的禁止引用与此一致。

#### C3（P0）提示词禁引用 vs coder 必须读设计档

- **证据**：common「Prompt face — no document references」含「see the design doc」；eng-coder「task book references the design document — read it, follow it」。
- **处置**：区分「规范内容的引用」与「执行坐标的引用」。禁止前者，允许后者（设计档是执行依据，不是修辞引用）。
- **验收**：common 的禁令不再覆盖 coder 的执行协议；两档语义一致。

#### C4（P1）三式动作面 vs 四步不跳

- **证据**：三式写「流程是真走不动时才翻」；discipline 写「Every dev task walks the four steps, no skipping」。
- **处置**：明确关系：四步是质量门与顺序，三式是每步内的动作选择；不得把三式读成可跳步，也不得把四步读成每步都要完整文书。
- **验收**：两段不再互相读成相反优先级；补一句「简单改动的最小四步形态」。

#### C5（P1）explore 是否报告范围外观察

- **证据**：`persona-explore.md` 要「what you notice goes into the report」；discipline 禁止范围外上报。
- **处置**：统一为「范围外观察只作线索单列，不进发现、不记账、不上抛为缺陷」。
- **验收**：两档同一口径。

#### C6（P1）设计档九项是否允许缺项

- **证据**：designer「9 items missing one = incomplete」与同节「无接口则省略」冲突。
- **处置**：改为「九项按适用性裁剪，缺项必须写一句不适用理由」，或列出强制子集。
- **验收**：纯文本变更不再被九项总则判 incomplete。

#### C7（P1）fix round 记录是否写入长期设计档

- **证据**：persona 要求每轮 findings + planned changes 落设计档；common 要求长期档只留当前态；designer 说一次性内容会被下批覆盖。
- **处置**：fix round 的过程记录只住批档；设计档只写修后的目标态与必要决策理由。
- **验收**：设计档不再出现逐轮过程史。

#### C8（P1）被拒绝方案写哪里

- **证据**：discipline 说 rejected options 住批档；designer 说 key decision record 含 rejected alternatives。
- **处置**：方案级否决理由（影响长期选择）住设计档的决策句；试验性过程与否决细节住批档。
- **验收**：两处不再互相抢同一内容。

#### C9（P1）上游坐标要不要复读

- **证据**：common 说子代理报告是线索不是证据，要回源；designer 说父/评审给的坐标当作引用不复读。
- **处置**：区分「决策依据的事实」与「定位坐标」。前者回源，后者可直接使用；若坐标成为判据依据则必须回源。
- **验收**：两档不再互相矛盾。

#### C10（P2）重复条款收敛

- 三式在主 persona 与 discipline 同文重复，主 agent 收两遍。
- 「裸档名可解析」「示例路径进围栏」「doc_check PASS」「异步报告自动到达」等多处重复。
- **处置**：每条只留一个权威位置，其余删除或一句话指向；主 agent 收到的重复节去重。
- **验收**：同一规则全仓一处详述；主 agent 装配体量下降且无规则丢失。

### D. 行为与成本

#### D1（P0）记录义务与产品工作成本不对称

- **证据**：多处「same round / immediately / same day」的记录义务；产品实现需设计、评审、令牌、批档。
- **结构原因**：R6。
- **处置**：把记录义务改为「随批一次结清」，取消散落的即时强制；同时降低小改动的流程成本（见 D2）。
- **验收**：单点改动不再触发多次台账/文档往返；记录集中在收口。

#### D2（P1）小改动没有低成本通道

- **现象**：一行修复也要完整设计-评审-令牌-批档。
- **处置**：定义「微批」：单文件、无行为契约变化、有测试的改动，允许简化设计与一次评审；但不许借微批躲设计。
- **验收**：典型一行修复的总调用数与耗时显著下降；行为契约变化仍走全链。

#### D3（P1）评审轮次与冻结窗造成的等待

- **现象（已更正）**：批档的段面写根本不在冻结扫面内——冻结窗口只在 `FILE_MUTATORS` ∪ `file_ops` 上组装（`thincoder-core/agent/helpers.mjs` 的 `FILE_MUTATORS` = `write` ∥ `edit` ∥ `insert_after` ∥ `apply_patch` ∥ `delete` ∥ `hashline_edit`；`batch` 不在集内），`thincoder-core/agent/dispatch.mjs` 只在那个分支里判冻结。真正的等待只来自**设计档整档冻**：评审读全文 ⇒ 整档冻是对的，修轮只能等结算。
- **处置**：不改冻结判据（没有可放行的臂）；把「批档面不在冻结扫面内」写成现状陈述，把等待收成一条纪律——评审点火前把要改的笔改完，点火后只等报告。
- **验收**：盘上不再出现「批档段面被冻结窗拦」的判据或回执文案；同一机制只留一处描述。

## 4. 处理计划

原则：先修会撒谎的状态机，再修冲突的规则，再修工具描述与体量。每批独立可验收，不一次性重写体系。

| 批次 | 内容 | 覆盖 | 依赖 |
|---|---|---|---|
| P0-1 状态机诚实化 | A1 退回边 · A2 核销解耦 · A3 收口逐行处置 · A5/A6 边角 | 状态机 + 台账 | 无 |
| P0-2 批档与台账一致性 | A4 原子/补偿 · B2 一次收口 · A7 预定批 | 批档生命周期 | P0-1 |
| P0-3 提示词冲突清零 | C1–C9 逐条裁定并统一 | 提示词六档 | 无（可与 P0-1 并行） |
| P1-1 工具按角色收窄 | B4–B8 · B3 指引修正 | 工具装配与描述 | 无 |
| P1-2 微批与评审成本 | D1–D3 | 流程与门禁 | P0-1、P0-3 |
| P2-1 体量收敛 | C10 · 删除重复与失效条款 · **设计档不写绝对读数（档数 ∥ 条数 ∥ 行数）：规范面只留量法，绝对值单源，读数住批档** | 提示词 + 设计档书写规则 | P0-3 之后 |

每批验收统一要求：行为前后读数、负例（该拒的仍拒）、无新增常驻测试夹具、文档与代码同轮一致。

## 5. 明确不做的事

- 不再为「体系完整」新增维度、表格或状态。
- 不把台账行数下降当目标；目标是每条状态都说真话。
- 不把所有规则搬进更多文档；重复条款是删除对象，不是搬家对象。
- 不为过验收去扩工具回执面或新增机制。
- 不在本档直接改代码；本档只作问题与计划的单一来源。
