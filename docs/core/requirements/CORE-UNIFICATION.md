# 核心统一（CORE-UNIFICATION）· 需求

> 板块 = 一个共享核与多个宿主薄壳。
> 设计 = `docs/core/design/CORE-UNIFICATION.md`；仓布局 = `TWO-REPO-MERGE.md`。

## 1. 总体目标

各产品共有的机制、提示词和工具描述由 @thincoder/core 提供单一权威实现。端壳只保留结构性不对称的宿主能力、交互和呈现。

## 2. 功能需求

| # | 需求 |
|---|---|
| F1 | 共享面进入 core；端侧差异通过显式参数、回调、配置或装配注入 |
| F2 | core 模块可独立验证，不依赖端壳夹具 |
| F3 | 核内实现有明确来源和负责设计档，不产生另一套平行语义 |
| F4 | 核自带开发期验证；产品从用户入口验证集成结果 |
| F6 | 统一后行为符合当前需求与设计，不要求复制某个旧端错误 |
| F7 | 开发期可使用本地核；生产期使用已发布且版本一致的核包 |
| F8 | 提示词与工具描述唯一副本位于 core |
| F9 | 旧实现、旧加载根和重复描述随负责变更删除 |
| F11 | 配置、会话、记忆、工具、模型、agent、文档等均适用同一核边界 |
| F12 | 可观察行为或对外契约变化必须逐项提交用户裁定 |
| F13 | 配置、命令、输出和事件变化保留兼容；无法兼容时单独上抛 |
| F14 | 当前目录名为 thincoder-cli 与 thincoder-core；引用使用当前路径 |

## 3. 非功能需求

| # | 标准 |
|---|---|
| N1 | 未涉及功能不得无故回归 |
| N2 | 结构变化可回退，写权与业务门不因迁移削弱 |
| N3 | core 不 import 产品实现；提示词加载不依赖产品目录 |
| N4 | 核先发布，产品后发布；VSC 等无依赖解析的产物内嵌核 |
| N5 | 产物中的核版本、提示词与工具描述和仓内核一致 |
| N6 | 文档检查使用当前 doc_check，不恢复旧双仓脚本 |
| N7 | core 不引入未批准的第三方运行时依赖 |
| N8 | 代码结构按 CODE-TIER，文档不套代码行数档位 |

## 4. 契约兼容

- 旧配置能读取或有明确迁移。
- 命令改名保留必要别名。
- 事件语义变化有登记与验证。
- 端侧承载形态可以不同，业务语义不得漂移。
- 用户可见端差按缺陷处理；确有宿主能力限制时提供证据并交用户裁定。

## 5. 子系统责任

需求与设计按同名主题分档：MEMORY、SESSION、CONFIG、TOOLS、PROMPT-SYSTEM、AGENT-LOOP、CONSULTATION、PROVIDER、MCP、TRACES、CHECKPOINT、CONTEXT-COMPACTION、LOGGING、I18N、WORKSPACE 等。

本档只规定共同边界，不复制子系统机制正文。

## 6. 边界

不为了“统一”引入第三套实现，不把结构性宿主差异写成产品分支，不在本档保留迁移阶段、旧相似度读数或历史裁定清单。
