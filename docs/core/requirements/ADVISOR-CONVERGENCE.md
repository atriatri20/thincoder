# 评审收敛（ADVISOR-CONVERGENCE）· 需求

> 板块 = 独立评审的轮次、证据、守卫、凭证交界与完成语义。
> 设计 = `docs/core/design/ADVISOR-CONVERGENCE.md` 与 `ADVISOR-GUARDS.md`。
> 相邻 = `CONSULTATION.md`、`ENGINEERING-MODE-V2.md`。

## 1. 总体目标

评审循环必须形成可用结论。正常路径收敛为通过或需修改；机械失败必须说明发生了什么和下一步。

轮次用于衰减检查范围，不作为封禁发起的计数器。反复出现同类机械失败时，父侧停止重跑并上报用户。

## 2. 功能需求

### 2.1 轮次与证据

| # | 需求 |
|---|---|
| F1 | 代码评审的轮次：Round 1 全量；Round 2 以验证前轮为主，可补明显崩溃、数据丢失或逻辑错误；Round 3+ 严格只验前轮。设计评审不按轮次衰减，见 F37 |
| F4 | 每轮使用全新会话；前轮只以明确注入的文本存在 |
| F5 | 宿主校验引文路径、当前行内容和读取围栏，报告 host-verified 结果 |
| F6 | 轮次、失效、重置和结算分类来自宿主状态，不解析模型自然语言来驱动控制流 |

### 2.2 修正与批准时序

| # | 需求 |
|---|---|
| F7 | 评审后先逐条裁决；要求修正的项目必须落地并经核验，然后才能请求用户批准 |
| F8 | 修正轮只处理评审发现和对应裁决；新增语义或范围必须另行交给用户 |
| F9 | Action 只使用 Fixed、Dispatched、Not an issue、Deferred；Dispatched 不等于已落地 |
| F10 | 未解决的红项必须可见；不得用“原本如此”或“不是本轮引入”代替技术处理 |

响应表是父侧阅读材料，不是宿主控制流协议。

### 2.3 启动、凭证与完成

| # | 需求 |
|---|---|
| F11 | 不完整评审不签发设计凭证，也不计为代码评审已覆盖 |
| F12 | 设计评审请求必须携带与本次凭证一致的 Approval Signal；缺信号时启动前拒绝 |
| F13 | 上下文压缩后，对象声明、文档清单和 Approval Signal 仍在 |
| F14 | 引文只从当前声明范围和允许根解析；文件存在、内容连续匹配、未越界三项同时成立才命中 |
| F15 | 整场墙钟预算约束每次模型请求；预算接近耗尽时提示收敛，超时报告给统计和恢复建议 |
| F16 | 同步与异步结算对“不完整”使用同一谓词 |
| F17 | 设计评审在途时保护被审对象；违规修改不得产生有效凭证或覆盖状态 |
| F18 | 评审 documents 只受理当前项目内现存 `.md`；相对路径按会话项目根，绝对路径照用并做归属判断 |
| F19 | 顶层 type 必填且只能是 code/design；与 object.type 的另一合法值冲突时拒绝 |
| F20 | 设计评审必须有可读 batchDoc，且至少一条未决台账行指向该批 |
| F21 | 失败、范围拒绝和误配拒绝都携带类型、范围摘要、轮次与判据名 |
| F36 | 设计评审的目标域止于本轮评审判得着的面：批档 §1–§3 与评审范围文档。§4、§5、§6 都写在本轮之后，故永在域外——空着不是发现，对象声明点名也拉不进来。读不受限，文件与代码照读，挡的只是「对段的发现」。限设计评审轮：代码评审轮里实施记录已在盘上，判它属于正常射程 |
| F37 | 设计评审每轮都用完整判据全文重审，判据不随轮次衰减：上一轮的发现与修复声明只作背景传入，不缩窄本轮可判的面，也不把本轮限成「只验已点名项」。第 N 轮可报的发现范围与第 1 轮相同——读者看到某轮设计评审的判据被换成一纸收敛清单，就是这条被违反 |

### 2.4 争议与归宿

| # | 需求 |
|---|---|
| F32 | 每项不修必须有理由；前两轮可打回，第三轮起接受有理由的不修项 |
| F33 | 红项的解决包括 Fixed 和 Accepted；零理由未修项始终未解决 |
| F34 | 引文必须是所引行的连续子串；省略号缩略不能充当证据 |
| F35 | 每个前轮条目都必须有 Fixed、Accepted 或 Unfixed 等明确归宿，不得静默消失 |

接受有理由的不修项只结束评审争议，不免除父侧向用户披露残余风险的义务。

## 3. 非功能需求

| # | 标准 |
|---|---|
| N1 | 正常路径有明确裁定，失败路径有结论和恢复选项 |
| N2 | 评审对象由显式参数定义，不遍历 git diff 猜范围 |
| N3 | 在既定节点触发，不为增加次数扩大评审面 |
| N4 | 修正不夹带新语义；提示词与机制文档保持一致 |
| N5 | CLI、VSC 和其他宿主使用 core 同一语义 |
| N6 | 判据能由读者对照当前文件验证；瞬时读数留在执行记录 |
| N7 | 守卫触发必须有可见结果，不静默降级 |
| N8 | 失败提示包含可执行的恢复方向 |
| N9 | 未注册凭证不得进入报告、digest 或 prior；凭证不落文档 |
| N10 | 单元验证不依赖网络、真实 LLM 或长计时等待 |
| N11 | 冻结窗口边界通过回执和结算结果可观察 |

## 4. 项目上下文注入

评审上下文从被评项目自述派生：

| 面 | 来源 | 不可用时的要求 |
|---|---|---|
| 项目指南 | 按项目规则查找 AGENTS.md | 明示没有指南，不静默改用另一套约定 |
| 文档地图 | manifest docRoot 声明 | 明示无法核文档归属 |
| 项目标准 | manifest docRoot.standards | 未声明与声明但不可读必须可区分 |

不为 ThinCoder 自己的目录名设置通用产品默认。声明源不可读时报告具体路径与原因。

## 5. 上下文预算与失败出口

### 5.1 预算派生

可用窗口 = 模型窗口 − 完成预留。

判死线 = `floor(可用窗口 × 0.8)`；压缩触发 = `floor(判死线 × 0.8)`。窗口来自 providerSpec 与 provider 级 context 覆盖；完成预留来自显式 maxTokens、规格 maxOutput 或零。

未知模型使用保守规格。预算是宿主机自限线，不替代服务端约束，也不新增 advisor 专用窗口配置。

### 5.2 机械失败

- 截断、陈旧、凭证落盘失败和无报告都要产生可见结论。
- 结论包含稳定前缀、对象标识、当前尝试、判据名和恢复选项。
- 机制不按累计次数封禁下一次发起。
- 资源保护由异步池和单场预算承担。

## 6. VSC 与多端对位

各端复用 core 的工具面、轮次、证据校验、失败族、异步池、冻结窗口、启动断言、结算和凭证规则。

宿主差异只允许出现在生命周期载体、会话持久化和界面呈现；不得改变 pass、凭证签发、覆盖状态或路径受理语义。

## 7. 范围边界

- 不每轮全量重扫。
- 不解析响应表驱动控制流。
- 不按评审次数封禁。
- 不自动重跑、自动缩范围或自动改判据。
- 不做 basename 全局扫描或模糊引文匹配。
- 不把项目临时目录当长期规则。
- 不把未验证引文当作打回依据。
