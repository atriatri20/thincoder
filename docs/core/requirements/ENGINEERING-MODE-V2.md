# 工程模式（ENGINEERING-MODE-V2）· 需求

> 本档是工程模式的当前需求权威。普通模式 = `docs/core/requirements/NORMAL-MODE.md`；共同原则 = `PHILOSOPHY.md` 与 `docs/core/standards/METHODOLOGY.md`。

## 1. 定位与原则

### 1.1 目标

工程模式通过结构保证“需求、设计、实现、验证”形成可追溯闭环。它的目的不是增加表单，而是防止文档、代码和交付各自漂移。

需求、设计、代码不一致时必须显式处置。测试分为短期开发反馈和常驻业务验收，寿命按 `docs/core/requirements/TESTING.md`。

### 1.2 约束即结构

能由工具参数、角色、状态机、写门和记录结构承载的规则，不只依赖模型记忆。结构约束必须有真实失败代价，且不能让正常路径更困难。

默认仍使用清晰提示、可见报告和停下上报。不得把不可机械判断的语义硬写成假检查，也不得用计数器替代工程结论。

## 2. 范围

工程模式适用于需要设计先行、独立评审、用户批准、受控实施和完整收口的任务。与普通模式的差别是流程强度，不是质量标准。

工程模式内不设置“小改免流程”通道。想直接修改后补流程，应由用户选择普通模式。

## 3. 机制全貌

```text
项目状态与需求
  → 开批与批次记录
  → 设计
  → 独立设计评审
  → 用户批准或整批授权
  → eng-coder 实施、自审和修复
  → 验证与代码评审
  → 用户确认、收口和记录冻结
```

一个交付目标对应一个批次。多个批次可并行，但写域冲突和依赖由调度器处理。

## 4. 项目沟通方法

### 4.1 项目类型

研发项目由当前用户直接决定需求。委托开发项目还涉及委托方、业务负责人和实际用户，必须区分事实、业务决策和验收权。

### 4.2 干系人

| 角色 | 主要决策或信息 |
|---|---|
| 项目经理 | 进度、协调和沟通 |
| Project Owner | 目标、预算和重大取舍 |
| Function Owner | 业务模块的范围和规则 |
| 用户或关键业务用户 | 真实使用方式、反馈和验收证据 |

技术 agent 不代替商务或业务所有者决定预算和业务规则。

### 4.3 生命周期

委托项目可依次形成方案、计划、交付物清单、测试证据、验收和运营记录。每份对外交付物必须有明确所有者与签收方式。

### 4.4 沟通与风险

问题按内容找对应决策者。进度风险按对交付的影响分级，并给出可执行的下一步。bug 报告必须能复现、能跟踪、能核销。

## 5. 运转核心：三类记录

### 5.1 项目状态档

`PROJECT-MANIFEST.json` 记录项目阶段、文档层、代码分类和索引声明。它是机器状态，不是决策日志。

详细需求 = `ENGINEERING-MODE-V2-SPEC-MANIFEST.md`。工具描述必须让 agent 在使用时理解键的用途和错误后果。

### 5.2 台账

台账是项目级需求池与技术待办，使用 SQLite 和六态状态机。查询面向所有角色，写入只由主 agent 执行。

详细设计 = `docs/core/design/LEDGER.md`。台账不导出另一份手写 Markdown 真相。

### 5.3 批次档

批次档记录一轮工作的讨论、设计、评审、批准、实施和收口。六段各有作者，由 `batch` 工具控制段写入和生命周期。

批次档是过程记录，可在其维护价值消失后清理；需要长期存在的规则必须进入需求或设计文档。

### 5.4 咬合

| 记录 | 回答 |
|---|---|
| manifest | 项目当前声明是什么 |
| 台账 | 哪些需求或债务待处理 |
| 批次档 | 这一轮如何执行和收口 |

在途与待核销工作项必须有 task_book。批次收口与工作项结算按当前工具事务执行，manifest 不参与该事务。

## 6. 文档写作约定

文档层和目录由 manifest 声明。当前仓库的归属见 `docs/README.md` 与 `docs/core/design/DOC-SYSTEM.md`。

需求回答要什么，设计回答当前如何实现，批次回答本轮做了什么。状态文档只写当前状态，历史由 git 保存。

同主题优先就地更新所属文档。新增文档前必须查地图和现有所有者，避免同一主题出现两份权威。

设计写当前结构、接口、决策和持久理由。一次性文件清单、原始读数和本轮验收表住过程记录。

## 7. 角色与写权

### 7.1 写权矩阵

| 产物 | 作者 |
|---|---|
| 需求与功能规格 | 主 agent |
| 架构与模块设计 | eng-designer |
| manifest 与台账 | 主 agent |
| 批次 §1 / §4 / §6 | 主 agent |
| 批次 §2 | eng-designer |
| 批次 §3 | advisor |
| 批次 §5 | eng-coder |
| 实现与产品文本 | eng-coder |

explore 只读。普通模式的席位折叠由 NORMAL-MODE 规定。

### 7.2 主 agent

负责需求讨论、记录、派单、用户沟通、裁决、核验和收口。主 agent 不代替设计或实施角色写其专属产物。

派单必须给出已确认设计、准确路径、验收和调度信息。未决语义不得留给实施者猜测。

### 7.3 eng-designer

调查先例、编写设计和批次 §2，核对需求是否可设计。结构决定必须在设计期完成，不能留给 eng-coder。

### 7.4 eng-coder

按批次 §2 实施，运行验证，进行内部审计和修复，并写 §5。发现设计缺口时停下上报，不静默偏离。

### 7.5 advisor

独立阅读证据并评审设计或代码。评审意见是发现，不自动成为用户决定。

### 7.6 互锁

设计评审、用户批准、designToken、批次绑定和写门共同保证实施只在已授权范围内发生。语义责任由角色承担，机械约束由工具承担。

## 8. 运作规则

### 8.1 委派

工程角色的任务书来自绑定批档。eng-coder 取其中的 §2（成文任务书）；eng-designer 读整份记录——§1 承载父侧裁决且具约束力，§2 由它自己写。eng-coder 必须携带 batchDoc、round、有效 designToken，并在多设计会话中携带 designId。

非工程角色使用当前结构化任务书。`files` 是调度清单，不是授权边界；`dependsOn` 表达真实依赖。

### 8.2 评审与批准

设计必须先评审后实施。用户批准即实施启动，除非用户明确要求只批设计或暂停。

整批授权可覆盖该批评审、修正、实施和收口的连续执行，但不取消评审。范围变化、设计语义争议、实施偏离或用户叫停时停止。

### 8.3 提示词

运行期提示词只位于 `thincoder-core/prompts/` 和 `tool-docs/`。它们是产品代码，不在文档层保存第二份逐字正本。

### 8.4 测试

单元测试是当前批次的短期反馈工具，集成测试只来自真实业务场景或生产问题。验收以实际行为和项目发布链为准。

### 8.5 评审凭证

设计评审通过后签发与设计绑定的凭证。凭证有生命周期，并在链终消费。缺失、不匹配和过期必须可诊断。

### 8.6 验证

verify 声明验证结果但不代跑。必须实际运行适用检查；不能验证时明确报告。

### 8.7 文档检查

当前检查器只判断段长、行号锚和悬空指针。范围、解析和豁免由 `DOC-CHECK`、`DOC-GRAPH`、`PATH-RESOLUTION` 规定。

## 9. 情境

`phase` 取 initial-dev / production，影响当前工作重心。阶段由 manifest 保存，并通过工程模式顶层会话的情境行注入。

轮次由批次与 spawn 的 round 表达，不写入 manifest。修复轮复用同一设计和凭证，不重新勘察无关面。

## 10. 兼容与边界

- 不恢复已退役的配置键或旧流程文件。
- 不要求用户项目采用本仓目录形状。
- 不把 git 作为所有能力的前提。
- 不把语义判断包装成机械门。
- 不用历史批次作为当前规则的权威来源。

## 11. 非功能要求

| # | 要求 |
|---|---|
| N1 | 规则归属唯一，接口和状态可复核 |
| N2 | 失败可见，业务失败不得被兜底成成功 |
| N3 | 跨平台、跨项目和跨端语义一致 |
| N4 | 正常路径简洁，修复轮不重复无关工作 |
| N5 | 文档和测试量由维护价值决定，不按代码量增长 |

## 12. 验收

- 角色、写权、凭证和批次生命周期可由实际工具调用验证。
- 需求、设计、实现和验证能相互追溯。
- 无 token、无 batchDoc、过期凭证和越段写入均有明确失败。
- 用户批准、整批授权、暂停和范围变化具有不同且可观察的行为。
- 普通模式不继承工程模式的机械写门。

## 13. 继承机制的当前要求

### 13.1 文档更新纪律（FR21）

当前规则归 `DOC-SYSTEM`、`DOC-DISCIPLINE`、`DOC-CHECK`。状态文档只写当前态，失效表达删除，引用使用节名或符号，不写会漂移的行号。

### 13.2 多端同机制（FR23）

CLI、VSC、Desktop 共享 core 机制。宿主适配可以不同，业务判据不得漂移。

### 13.3 台账提醒（FR24）

只在存在可动作项或状态变化时提示。数量、老化和范围使用同一数据面，不制造重复噪音。

### 13.4 文档体系各仓自持（FR25）

每个项目在自己的仓内维护需求、设计、批次和台账。读取可声明 publicRepos；写入 writableRepos 的例外按 CROSS-REPO-WRITE，不创建跨仓批档。

### 13.5 变更面分流（FR27）

工程模式下产品面一律走完整链。文档面按写权矩阵处理。判不出时按产品面，分类结果不能扩大写门豁免。

### 13.6 批次生命周期（FR28）

交付目标、阶段或条目集变化时另起批次。关闭前检查链完整性；重开需要理由；冻结后修改通过新批次。

### 13.7 父侧轮次与提交（FR29）

派发状态照工具回执，提交不混入用户或他人文件。每轮给用户可读进展或明确等待状态。

### 13.8 台账用法（FR30）

登记、开批认领、实施结算、新债和上抛都在相应事件发生时处理。工程写操作按当前工具要求携带 ledger 与 project。

### 13.9 plan 面排除（FR31）

工程模式不注册 plan 工具，命令入口明确拒绝，并在切换和恢复时清除 planMode。普通模式不受影响。

### 13.10 批准即实施启动（FR32）

评审通过后的用户批准同时授权实施，不另等一句“开始”。用户明确要求只批设计时除外。

### 13.11 eng-coder 令牌诊断（FR33）

designToken 是必带参数。missing、mismatch、expired 使用不同错误，且不回显凭证。

### 13.12 决定当轮落盘（FR34）

需求决定当轮写入所属需求文档或当前过程记录。压缩后重读当前文档与工作项，避免摘要丢失决定。

### 13.13 任务书与当前设计一致（FR35）

批次 §2 引用当前设计与需求，不复制易漂移的判据。设计变更影响在途任务时，必须同步或明确停止旧任务。

### 13.14 整批授权（FR36）

整批指令允许该批全链自动完成。评审仍执行；范围变化、设计争议、实施偏离和用户叫停仍然停止。

### 13.15 文件重叠由调度器处理（FR37）

声明 files 后直接派发。queued 是正常状态；不得为避开重叠而扣住任务或改变设计落点。

### 13.16 需求阶段必须问清（FR38）

新业务的规则、边界、优先级和验收必须由用户确认。代码与文档只能提供事实，不能代替用户决定意图。

### 13.17 落地前先答三问（FR39）

先回答现成功能在哪里、叫什么、谁在用。存在可复用件时优先复用；偏离需要具体能力或契约理由。

### 13.18 业务门必须失败（FR40）

前置条件、状态、权限和业务关系不满足时明确拒绝。技术兜底不得改变业务结果。

### 13.19 文档发现走 doc_search（FR41）

发现式查询先用 doc_search；已知文件再用 grep 定位。过程档命中只是线索，跨仓未声明时必须明确说明。

### 13.20 manifest 只声明项目自身（FR42）

当前键集由 MANIFEST 规格定义。产品内部提示词路径、检查器参数和第二套评审文档指针不进入用户 manifest。

### 13.21 推断不得当事实（FR43）

关键决定使用本轮读到的原文和坐标。摘要、子代理报告和记忆只是线索，无法回源时标 unverified。

### 13.22 机检是下限（FR44）

读数服务于可读性和正确性。指标与真实目标冲突时修正规则或实现，不为通过指标损害内容。

### 13.23 段长判据（FR45）

文档检查以段为单位；提示词按行。长段需要重写或改变结构，不是插入换行掩盖问题。

### 13.24 提示词写作（FR46）

一行一件事，规则、条件、例外和理由保持清晰。运行期文本不引用另一份文档来解释规则。

### 13.25 动手前查文档（FR47）

先了解当前接口、约定和决策。查不到时继续工作，但说明检查过的面。

### 13.26 开批前调研（FR48）

开批前用 doc_search 查项目现状。涉及外部系统、版本、协议或否定断言时，使用一手公开源核实。

### 13.27 行号坐标（FR49）

文档引用使用节名、符号或原文，不把行号作为持久锚。当前 report、gate 和写门的范围按 DOC-CHECK 执行。
