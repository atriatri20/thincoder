# ThinCoder 文档体系评估

> 日期：2026-11-13。本文是诊断报告，不是当前产品或机制规范。
> 范围：根入口、文档地图、core、CLI、VSC、Desktop、render-core、Server 与 RTM。历史批档只确认体积和检索边界，不评价其历史内容。

## 1. 总体结论

入口、板块分层和领域归属明显改善，但当前体系还不能独立支撑实现与验收。

主要风险已经从文档堆积转为：退役内容仍进入检索面、章节引用失效、复杂机制被压缩成无法独立验收的概述，以及跨文档规则互相冲突。

本文收回此前“阶段 1–5 全部完成”“核心死引用已解决”“状态与过程混杂已解决”的结论。`doc_check` 的 PASS 只证明段长、行号锚和文件存在性检查通过，不证明章节、引文、语义或产品行为正确。

## 2. 分项评价

| 维度 | 评价 | 说明 |
|---|---|---|
| 权威入口与地图 | 良好 | 根 README、文档地图和 manifest 已形成清楚的板块入口 |
| 需求与设计分层 | 良好 | 大多数文档能区分目标、边界和实现机制 |
| 当前状态可信度 | 不合格 | 旧文件台账、迁移施工稿与当前规则仍有混线 |
| 引用可靠性 | 不合格 | 文件存在不等于章节有效，已确认多处章节死引用 |
| core 机制完整性 | 部分不合格 | 若干状态机完整，但补偿、重试和检查边界有缺口 |
| 产品端契约完整性 | 不合格 | 协议字段、阈值和异常判据不足 |
| Server 契约闭合度 | 不合格 | 团队记忆、沙盒、权限和恢复语义需要补齐或裁定 |
| RTM 覆盖状态诚信 | 良好 | 覆盖与实际执行结果已分开，但追溯锚仍需整理 |

## 3. 高优先级发现

| # | 发现 | 当前证据 | 影响 |
|---|---|---|---|
| A1 | 旧文件台账设计仍占当前设计入口 | `core/design/LEDGER-SELF-CONTAINED.md` 仍写「台账条目（docs/TODO.md）」并保留 L4/V4 与迁移落点；地图仍登记该档 | 可能引导维护者恢复已退役的 Markdown 台账与检查链 |
| A2 | 退役内容仍进入当前检索面 | `core/design/DOC-MIGRATION.md` 标题写「已退役」，但仍在声明的设计根中；`docs/TODO.md` 仍声称自己是唯一台账 | 地图与全文检索会给出不同的当前状态 |
| A3 | 跨仓检查存在相反规则 | `core/requirements/DOC-CHECK.md` F4 写「跨仓一律不报」；`core/design/PATH-RESOLUTION.md`「声明仓引用」把已声明仓的缺失目标判为 dangling | 同一引用可能被忽略或判悬空，验收口径不稳定 |
| A4 | 无项目时是否运行文档门未统一 | MACHINE-CHECK 需求写「无项目声明时不运行文档检查门」；DOC-CHECK 与路径解析仍保留项目根或会话锚的继续解析面 | 可能漏检，或向无项目目录施加预期外检查 |
| A5 | render-core 缺少共享核契约 | `render-core/design/RENDER-CORE.md` 只概述滚动、帧、composer 与 subblocks，没有关键导出、参数、返回值、阈值和状态迁移 | 修改共享核只能反向读源码，无法独立形成跨端验收 |
| A6 | VSC 消息协议只剩消息目录 | `vsc/design/WEBVIEW-PROTOCOL.md` 写「字段以实际发射、载荷白名单和 webview 消费三面一致为准」 | 字段规范被交回代码，无法仅凭文档审查协议变更 |
| A7 | Desktop IPC 缺少逐通道契约 | `desktop/design/IPC.md` 只列通道目录与通用 `{ok,reason,...}` 信封 | preload、主进程与渲染端缺少共同载荷和错误闭集 |
| A8 | Server 团队记忆没有唯一真源 | Server 需求写「采用服务端数据库」；EVOLUTION 仍列为待确认演进；core MEMORY 仍写 team 层由 gitmem 同步 | 存储、接口和交付状态无法同时成立，需用户裁定 |
| A9 | 沙盒状态与恢复失败语义不完整 | SANDBOX 只写「按当前状态门和忙态执行」；EXECUTION 写「恢复先清卷再解包」，未规定半途失败后的旧数据与工作区状态 | 无法形成完整状态机和恢复负例 |

## 4. 其他已确认缺口

| 领域 | 缺口 |
|---|---|
| 批档与台账 | BATCH-LEDGER-REVIEW-UNIFY 的写序与补偿没有展开各操作的失败和恢复契约 |
| Provider | PROVIDER 没有完整列出可重试状态、尝试次数、退避序列与 Retry-After 边界 |
| 子代理 | tester 的「只跑不改」是角色纪律而非文件系统沙盒，现有简写容易让读者误判隔离能力 |
| CLI ACP | resource_link 的大小、NUL、选区、固定原因标记和支持集没有形成完整当前判据 |
| CLI TUI | 队列容量、消息合并预算和分页大小被「当前」替代，无法独立形成边界验收 |
| VSC 追溯 | RTM 仍引用当前需求与设计中不存在的 I-7、D-W46 |
| Server 成员 MCP | 写类识别、Server 侧审批身份和拒绝传播未闭合 |
| Server 权限 | owner/manage/readwrite/read 与 can.view/can.write 缺少共同能力矩阵 |
| Server 团队账 | 只列部分迁移边，aged 使用「当前老化阈」但没有值或配置来源 |
| Server Gateway | 上游非 2xx、流中 error、无 DONE 截断的转发和记账状态不完整 |
| Server 普通 key | 轮换缺少原子性、旧 key 失效和标签保留契约 |
| 发布与环境 | RELEASE 与 TEST-ENV-ECS 仍混有当前操作契约、过程描述和历史读数 |

## 5. 正面结论

- 文档地图按 core、CLI、VSC、Desktop、render-core、Server 分板，需求、设计、标准、发布、批档和 RTM 的职责清楚。
- BATCH-RECORD、台账状态机、异步结果消化、session/context 和设计凭证等抽查面仍保留重要状态与失败边界。
- Server 的后端判权、防枚举、秘密零回显、计量事务和 runner 故障隔离原则较一致。
- RTM 已区分「有／待补／缺」的覆盖状态与实际运行结果，没有伪造通过状态。
- 当前状态文档没有千行档；大体积主要位于历史批档。本批不为体积继续压缩文档。

## 6. 修复优先级

1. 清理旧台账、迁移档和退役内容的现役／检索边界。
2. 修复跨仓检查、无项目文档门等直接冲突；业务选择不明确时请用户裁定。
3. 恢复协议字段、状态机、阈值、补偿和失败恢复等必要契约。
4. 补齐 Server 的沙盒、成员 MCP、权限、恢复和轮换语义。
5. 修复章节引用并整理 RELEASE、测试环境手册和 RTM 追溯。
6. 每批改后运行 `doc_check report`，另做语义与章节复核。

## 7. 验证边界

本评估为只读审查，没有运行产品测试、完整集成测试或真机验收。定点代码阅读只用于判断文档是否另有机制补足，不构成实现符合性审计。

CLI 47 按用户决定不补。Desktop 没有盘上的集成用例，这是覆盖事实，不是运行失败结论。团队记忆真源、快照恢复业务策略和若干 Server 权限边界需要用户或业务负责人裁定。
